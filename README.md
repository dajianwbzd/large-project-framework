# 大型项目开发框架（Large Project Framework）

> 给 AI 编码智能体用的**多角色协作开发框架**：12 个专业角色共享同一个工作区，用需求卡驱动任务、事件循环编排执行、契约与机器检查收口。
> 它要解决的问题只有一句话：**让"一个人 + 一个 AI 会话"也能跑出有多角色分工、有验收证据、可中断续作的大项目。**

当前版本：**v5.28.0**（版本口径以 `agent.md` frontmatter 为准）

---

## 这是什么 / 不是什么

**是什么**

- 一套 **Markdown 指令契约**（主控编排 `agent.md` + 12 个角色 `skills/*/SKILL.md` + 契约/验收清单）
- 一套 **Python 自检脚本**（26 个脚本 + 23 个回归用例，只依赖 Python 3 标准库）
- 一套 **落盘工作区规范**（`project-state/`：契约、需求卡、测试卡、记忆、进度、问题、代码）

**不是什么**

- 不生成业务代码骨架（初始化的是**协作骨架**，不是脚手架）
- 不是 CI / 不是调度器（"几点开跑"在宿主侧；框架只提供起跑条件、闸门与收工动作）
- 不保证需求合理、不保证证据真伪——它保证的是**流程不悄悄跳步、产物有出处、结论带范围**

---

## 为什么要 12 个角色

单会话写大项目会稳定地失败在三个地方：上下文越写越满、改 A 坏 B、三天后没人记得为什么这么定。

本框架把"谁来干、干到什么程度算完、证据放哪"写成**可检查的文件契约**：

- **主控（`agent.md`）** 只做编排、裁决与派发，不亲自写业务代码
- **12 个角色**（产品经理、架构师、UI 设计师、前端、后端、数据工程师、测试工程师、安全审计、集成工程师、运维工程师、代码解析师、项目经理）各自有独立 SKILL 与产出落盘位置
- 每个角色只在自己那一段上下文里工作，产物写进 `project-state/`，下一段由主控按**契约与卡片**续接

## 快速开始（三步）

```bash
# 1) 把整个目录复制到你的项目根（agent.md 所在目录即工作区根 WORKSPACE，目录名可自定）
# 2) 让 AI 助手读你项目里的 agent.md，并声明"按大型项目开发框架执行"
# 3) 冷启动：生成工作区摘要（≤15s、≤6k token）
python -X utf8 scripts/recall.py <项目根>
```

Windows + 中文路径建议一律 `python -X utf8`（否则 `open()` 默认编码会踩 GBK）。

各平台落地方式不同，但本质一样——**Markdown 指令集 + 本地脚本，不绑定任何一家 Agent 平台**：

| 平台 | 落地方式 |
|---|---|
| DeepSeek Harness（dsh） | 把本目录注册成技能入口（`skills/<名>/SKILL.md` 指向本目录 `agent.md`），用户手动调用；角色派发用 `subagent` |
| Claude Code / Codex / Cursor 等 | 把 `agent.md` 放进项目并写进项目指令文件；角色用子代理逐个派发 |
| ZCode / Trae | 作为子智能体定义或项目内指令加载 |

## 目录结构

```
.
├── agent.md                  # 主控编排层：L0 速览、工作区约定、运行模式、六阶段主线、作战序列、纪律
├── 工作区地图.md              # 用户层导航页（派生物，由 scripts/workspace_map.py 生成，勿手改）
├── skills/                   # 12 个角色 SKILL（含配套手册与模板）
├── scripts/                  # 26 个自检 / 审计 / 生成脚本
│   └── tests/                # 23 个回归用例（改脚本必先跑）
├── project-state/            # 共享工作区（框架层，主控与角色的工作区）
│   ├── 契约/                 # 语义真源区：PRD、架构、接口、安全、设计令牌、代码规范…
│   ├── 需求卡/               # 一需求一目录：card.md + 思路 + 验收记录 + 证据
│   ├── 测试卡/               # 一次系统级测试活动一目录：tc.md + 覆盖矩阵 + 发现项 + 证据
│   ├── 记忆/                 # 决策日志（ADR）、变更日志、复用台账、指导发现台账…
│   ├── 进度/                 # 每角色一 json 的进度与账本（派生物）
│   ├── 问题/                 # CR、审核记录与事故单证
│   ├── 代码/                 # 代码级角色的产出区
│   └── config.json           # 项目档位、路径注册、各项策略开关
└── 方案/                     # 方案视图区：原始资料 / 产品稿 / 原型图（人读视图，不是第二事实源）
```

## 运行模式

| 模式 | 何时用 | 行为 |
|---|---|---|
| **快速模式 quick**（默认） | 小项目、内部工具、demo | 精简流程，仍保留关卡与落盘 |
| **完整模式 full** | 用户明确要求，或项目经理按升级判据 U1–U7 评估后用户知情同意 | 六阶段主线全跑，产品稿/原型/契约/测试卡齐备 |
| **探索模式 explore** | "进入打磨期"、攻坚一轮 | 按 `契约/探索域.md` 领探针 → 拦不住就建修复卡 → 三分支处置，机检闭环 |
| **极速修复 turbo-repair**（临时叠加） | "就改这几个小 bug，别建卡" | 不派子代理、不建新卡；命中退出线（≥4 文件 / 触及契约·接口·数据模型·权限·生产 / 同一问题 3 轮没好）立即退回正常流程 |

另有两条常开能力：**指导模式**（体检框架用得对不对，G01–G11 检查项）与**跑批运行**（无人值守，起跑前六查、每轮 `--guard`、收工五件）。

## 机器可核的检查（这是它和"提示词合集"的区别）

| 命令 | 作用 | 退出码约定 |
|---|---|---|
| `python -X utf8 scripts/framework_lint.py <项目根>` | 结构 / 编号 / 引用 / 注册表体检 | 0 通过，1 有 ERROR（不许提交） |
| `python -X utf8 scripts/workspace_map.py <项目根> --check` | 工作区地图对账 | 0 / 1 / **2 = 无法检查** |
| `python -X utf8 scripts/recall.py <项目根>` | 冷启动摘要 | 0 |
| `python -X utf8 scripts/migrate.py <项目根> [--apply]` | 老项目补建新结构（默认 dry-run，`--apply` 前自动备份） | 0 |
| `python -X utf8 scripts/regression_audit.py <项目根>` | 回归防线：修过的 bug 不许二进宫（哨兵用例） | 0 / 1 / 2 |
| `python -X utf8 scripts/scope_audit.py` · `explore_loop_audit.py` | 探索域覆盖 / 探索闭环 | 0 / 1 / 2 |
| `python -X utf8 scripts/solution_audit.py <项目根>` | 方案视图区（原始资料 / 产品稿 / 原型图） | 0 / 1 / 2 |
| `python -X utf8 scripts/reuse_scan.py <项目根>` | 先例复用盘点 | 0 / 1 / 2 |
| `python -X utf8 scripts/path_audit.py <项目根>` | 路径执法（产物不许乱放） | 0 / 1 / 2 |
| `python -X utf8 scripts/guide_audit.py <项目根>` | 指导体检（G01–G11） | 0 / 1 / 2 |
| `python -X utf8 scripts/test_scope_audit.py <项目根>` | 测试范围与档位是否被偷偷降档 | 0 / 1 / 2 |
| `python -X utf8 scripts/workspace_hygiene.py <项目根>` | 工作区清理清单（默认只报告） | 0 |
| `python -X utf8 scripts/task_estimate.py --guard` | 跑批闸门 | 0 继续 / 3 收工 / 4 未到点 / 5 查不到 / 2 没闸门 |

**`2 = 无法检查 ≠ 没问题`** 是本框架反复强调的一条：检查器跑不动时不许把它当成通过。

## 六阶段主线（完整模式）

1. 需求与边界（产品经理：PRD、用户确认、`[待澄清]` 清零）
2. 架构与契约（架构师：数据模型、接口、权限矩阵、安全隐患定档）
3. 设计（UI 设计师：设计令牌、方向稿、设计契约校验 + 用户确认关卡）
4. 实现（前端 / 后端 / 数据工程师按卡落盘，集成工程师管联调）
5. 验证（测试工程师：测试卡、覆盖矩阵、四级审查；安全审计出四查结论）
6. 交付（运维：发布通道、回滚路径、证据与《发出记录》）

每阶段都有关卡，**关卡只回答"能不能继续"，不替用户做决定**。

---

## 三条设计原则（为什么值得读一眼）

- **落盘即证据**：没写进工作区的产出 = 没干过。对话不是交付物。
- **单一真源 + 派生物**：契约在 `project-state/契约/`，地图/进度/json 都是派生物，可重算，不许手改。
- **摩擦即登记**：使用者卡住、绕流程、同一处反复改，当场记进台账；同类 ≥3 条就是下一版该改的条款。这个框架的每一版都来自真实摩擦点。

## 环境要求

- Python 3（脚本仅用标准库，无第三方依赖）
- Windows / macOS / Linux 均可；Windows 中文路径请用 `python -X utf8`
- 任意能读写本地文件、执行命令的 AI 编码智能体

## 关于本仓内容

- 本仓是**框架本体**，不含任何真实客户项目、真实服务器地址或商业资料。
- 文中出现的 `示例工作台A`～`示例工作台H`、`示例平台C` 等均为脱敏占位名。
- 框架的**实战编年**（记录每个机制来自哪个真实项目摩擦）不随仓发布，只保留指针；机制来历可按 `（vX.Y.0…）` 标注检索 `注意事项.md` / `验收标准.md` / `完成定义.md`。
