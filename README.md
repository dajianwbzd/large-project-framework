# 大型项目开发框架（Large Project Framework）

> 给 AI 编码智能体用的**多角色协作开发框架**：12 个专业角色共享同一个工作区，用需求卡驱动任务、事件循环编排执行、契约与机器检查收口。
> 它要解决的问题只有一句话：**让"一个人 + 一个 AI 会话"也能跑出有多角色分工、有验收证据、可中断续作的大项目。**

当前版本：**v5.28.0**（版本口径以 `agent.md` frontmatter 为准）

**简体中文** | [English](README.en.md)

## 这是什么 / 不是什么

**是什么**

- 一套 **Markdown 指令契约**（主控编排 `agent.md` + 12 个角色 `skills/*/SKILL.md` + 契约/验收清单）
- 一套 **Python 自检脚本**（26 个脚本 + 23 个回归用例，只依赖 Python 3 标准库）
- 一套 **落盘工作区规范**（`project-state/`：契约、需求卡、测试卡、记忆、进度、问题、代码）

**不是什么**

- 不生成业务代码骨架（初始化的是**协作骨架**，不是脚手架）
- 不是 CI / 不是调度器（"几点开跑"在宿主侧；框架只提供起跑条件、闸门与收工动作）
- 不替代任何**单点执行技能**（部署、发布、出图、写软著……那些有自己的操作手册，见 [与独立 Skill 的协作](#与独立-skill-的协作)）
- 不保证需求合理、不保证证据真伪——它保证的是**流程不悄悄跳步、产物有出处、结论带范围**

## 核心机制（读这一节就够懂它在干什么）

### 1. 卡是驱动单位

一切工作挂在卡上，**没有卡就没有派发、没有验收**：

| 卡 | 一个目录 | 里面有什么 |
|---|---|---|
| **需求卡** `需求卡/card-NNN/` | 一张需求 | `card.md`（req / AC / anchor / entry / 状态）+ 思路 + 验收记录 + `证据/` |
| **测试卡** `测试卡/tc-NNN/` | 一次系统级测试活动 | `tc.md` + 覆盖矩阵 + 发现项 + `证据/` |
| **CR** `问题/` | 一次变更请求 | 变更理由、影响面、批准留痕、执行单证 |

需求卡走五状态：`todo → in_progress → done（开发自验后）→ reviewing（主控派验收）→ 合并 GO 保持 done / NO-GO 回退 in_progress`，阻塞置 `blocked`。**状态不是靠嘴说的**：置 `done` 必须有落盘留痕，验收记录不许空壳（`guide_audit.py` G03）。

### 2. 主控 + 12 角色 = 上下文分层

- **主控**（`agent.md`）只做编排、裁决、派发与验收，**不亲自写业务代码**
- **12 个角色**各有独立 SKILL 与产出落盘位置：产品经理、架构师、UI 设计师、前端、后端、数据工程师、测试工程师、安全审计、集成工程师、运维工程师、代码解析师、项目经理
- 每个角色只在自己那一段上下文里干活，产物写进 `project-state/`，下一段由主控按**契约与卡片**续接；主控不读全文，按 **L0 速览 / L1 索引 / L2 正文** 三层按需加载

这解决的是单会话写大项目的三个必死点：上下文越写越满、改 A 坏 B、三天后没人记得为什么这么定。

### 3. 单一真源 + 派生物

- 语义真源在 `project-state/契约/`（PRD、架构、接口、数据模型、权限矩阵、安全、设计令牌、代码规范）
- `工作区地图.md`、`进度/*.json`、方案导出件都是**派生物**：可重算，**不许手改**，刷新即覆盖
- 目录分两层：**用户层**（`交付/`、`方案/`、`工作区地图.md`——给你看的）与 **框架层**（`project-state/`——主控与角色的工作区）

### 4. 落盘即证据，创建者 ≠ 验证者

- **没写进工作区的产出 = 没干过**；对话不是交付物，`tmp/` 里的东西不构成证据链
- 写卡的人不能给自己判 `done`，实现方不能同时当验收方（兼岗也不行）
- 验收结论只能引用落盘证据；"应该没问题"不算验证

### 5. 问题追踪、记忆与自增强

- **决策可追溯**：关键决策按 ADR 风格记 `记忆/决策日志.md`（背景 / 决策 / 理由 / 备选 / 后果），**不删旧决策**，改变就新增一条并标记 Superseded
- **摩擦即登记**：使用者卡住、绕流程、同一处反复改，当场记 `记忆/指导发现台账.md`（原话照抄、七列）——**这个框架的每一版都来自真实摩擦点**
- **修过的 bug 不许二进宫**：修复卡置 `done` 的前提是它有真实哨兵用例且最近一次通过（`regression_audit.py`）

### 6. 机器可核，而不是"请遵守"

框架里凡是说"必须"的地方，尽量都配一个脚本；**退出码是判据，自然语言描述不是**。
三态约定贯穿全仓：`0` 通过 / `1` 有 ERROR / **`2` = 无法检查，≠ 没问题**。

## 运行模式

框架有 **3 个项目档位**（写进 `config.json` 的 `mode`）+ **3 个正交开关**（不改档位）。

### 快速模式（quick，默认）

**默认就是它**：原型、demo、小工具、单模块功能，以及一切没被明确判为"大"的项目。

裁剪面**只有三样**：角色数（按需挑子集，最小闭环 = 产品经理 + 对应开发 + 测试工程师）、文档深度（卡内 3–5 条要点、不产出完整 PRD）、测试密度（测试卡密度降为 `ship`）。

**不许裁的六样**（缺了就不是"轻流程"，是"没有框架"）：需求建卡、卡状态流转与验收留痕、用户确认关卡、创建者 ≠ 验证者、产出落盘、路径纪律。

> **三条硬纪律**：① 主控不得以"这看起来是个大项目"为由**静默**升完整模式；② 判不准就往快速模式走（快速→完整只是把已有的卡接着走，完整→快速则要把 12 角色流程与关卡回退）；③ 切档必须写 `config.json` 的 `mode` **并**注明是谁提的、依据是什么。

### 完整模式（full）

多模块系统、前后端/多角色协作项目。进它只有两条正当入口：**用户明确指定**（"走全流程 / 按大型项目做"），或**项目经理评估 + 告知用户**后切。

评估判据 **U1–U7**（命中一条即应评估，多条强烈建议切）：

| 信号 | 为什么快速模式承不住 |
|---|---|
| U1 多模块/多服务、前后端分离需联调 | 需要稳定契约面（`api.yaml`）与集成核对 |
| U2 多里程碑或工期跨周 | 进度、风险、验收时点需要独立汇总臂 |
| U3 有对外交付件（方案书/报价/验收单/发布包） | 交付收口与对外动作有审计链要求 |
| U4 认证授权 / 敏感数据(PII) / 合规目标 | 安全审计不得与实现兼岗 |
| U5 要上线 / 生产变更 / 客户端交付 | 不可逆对外动作，签署不能由实现方自代 |
| U6 迁移或破坏性结构变更 | 需要技术债评估与 DDL 评审 |
| U7 多人/多团队并行接入 | 协作面本身就是风险项 |

判据看的是**交付形态与不可逆性**，不是代码行数——行数大的单模块 CLI 仍可在快速模式跑得很好，200 行的支付回调必须走完整模式。

**六阶段主线**：需求与边界（PM）→ 架构与契约（架构师）→ 设计（UI，低保真可点击原型 + 逐页高保真，两次用户确认）→ 实现（前端/后端/数据，集成管联调）→ 验证（测试工程师 + 安全审计）→ 交付（运维：发布通道、回滚路径、证据与《发出记录》）。每阶段有关卡，**关卡只回答"能不能继续"，不替用户做决定**。

### 探索模式（explore）

项目已能跑起来、不再大改需求、进入**持续验证期**时用。入口是用户/排期点名（"进探索模式 / 进入打磨期 / 跑一轮攻坚"），写 `config.json` 的 `mode=explore`。

**闭环五步**：按 `契约/探索域.md` 的地图领探针（单因子，一条只造一个错）→ 没拦住就**建修复卡**（复用需求卡模板，`source: 探索#S-NNN`，`anchor`/`entry` 必填）→ 卡走现有五状态 → 修完复验 → **产品经理评估三分支**：沉需求卡（规格缺失）/ 沉测试卡（覆盖缺失）/ 只归档（一次性问题，写理由）→ 卡归档不删除。机检 `explore_loop_audit.py`、`scope_audit.py`。

### 极速修复模式（turbo-repair，叠加档）

用户点名的临时快档，**不改变 `mode`**：客户反馈小 bug、要连着改几轮看效果时用。只有用户说了"极速 / 极速修复 / 快速解决 / 别建卡别派子代理"才进，**执行者不得自选**，跑批轮次里也不得进。

| 可以省 | 不许裁 |
|---|---|
| 子代理派发（主控内联，直接按角色 SKILL 改） | 台账（`问题/极速修复台账.md` 十二列，含 `basis` 依据与 `pack` 体验包） |
| 建卡（省 token 的主体）——但必须读既有卡/测试卡/用例库作依据 | 改动前回退点 |
| 全量测试（只跑冒烟 smoke / 定向 targeted） | 自检证据（命令 + 结果） |
| 迭代轮次之间的确认关卡 | **"未独立验证"必须写明**：不许置卡 `done`、不许宣称已验收 |

**强制退出线**（命中一条立刻回正常流程并在台账记 `exit_reason`）：X1 一次改到 ≥4 文件 / X2 触及契约·接口·数据模型·权限·敏感数据·生产变更·迁移 / X3 同一问题 3 轮没好 / X4 测试发现问题面超出预期 / X5 用户改口 / X6 正式交付包、对外件、上线前一轮。

### 三个正交开关（不改档位）

| 开关 | 何时开 | 它做什么 |
|---|---|---|
| **指导模式**（默认 on） | 任何时候 | "体检框架用得对不对"：`guide_audit.py` G01–G11 查需求没建卡、没留痕就置 done、环境被降级、变更无单证就执行等痕迹；只**发现 + 定位到既有条款 + 给最小修复动作**，不当第二指挥官、不替人改文件 |
| **跑批运行** | 用户说"跑到几点 / 多少 token"且人不在场 | 无人值守契约：起跑前六查 → 每轮 `task_estimate.py --guard` → 收工五件（停安全点 / 落盘 / 记账 / 四问报备 / 分清收工与没活干） |
| **方案视图区** | 完整模式必建，快速模式按需 | 项目根 `方案/`：`原始资料/`（唯一归档点）+ `产品稿/` + `原型图/`（均带导出日期与源路径），人读视图，**不是第二事实源** |

跑批闸门的退出码就是接口：

```
0 CONTINUE    继续本轮派发与收口
3 STOP        立即停在安全点，转收工（不许"再跑一轮看看"）
4 NOT_STARTED 不是开跑时刻：不派活、不做实现
5 UNKNOWN     有条件没查到：先补数据、不派活
2 无闸门      契约缺失或一条条件都没有 → 先补条件（不许当成"没到收工"）
```

## 与独立 Skill 的协作

这套框架**不吞并单点技能**，两者是**分层**关系。分清三层，才知道该找谁：

```
调度层   谁决定"什么时候开始"        AI员工排班调度 / cron / 人
   ↓
编排层   谁决定"派给谁、做到哪、证据够不够、该不该停"     本框架
   ↓
执行层   谁决定"这一步具体怎么操作、有哪些坑"     阿里云ECS部署 / SaaS网站生成器 / 元技能生成器 ……
```

**一句话分工**：**框架管"该不该做、谁来做、做到哪算完、证据在哪"；独立 skill 管"这一步的手脚怎么动"。**

### 三个典型协作形态

**① 框架 → 独立执行技能（框架是编排方，skill 是手脚）**

例：**阿里云ECS部署**。完整模式走到阶段⑥交付时，是角色**运维工程师**按框架要求出发布清单、回滚路径与《发出记录》，**具体怎么登录控制台、怎么用云助手传包、nginx/systemd 怎么配、有哪些坑**——那些全在 `阿里云ECS部署` 这个技能里。

- 框架不复制部署手册，只规定：不可逆动作要先过确认关卡、上线前一轮必须全量测试（对应极速修复退出线 X6）、部署结果要落 `交付/` 与证据目录
- 技能也不该自建第二套进度与证据——它的部署报告回到框架的落盘位置，才算进证据链

**② 独立调度技能 → 框架（skill 是宿主，框架是被驱动的执行体）**

例：**AI员工排班调度**。框架**明确不含调度器**——"几点开跑"永远是宿主的事。排班技能负责把目标写成班次、到点唤起、监管产物、失败分类停放、出晨报；框架负责被唤起后**每一轮判断该不该继续跑、以及怎么安全收工**。

两者的接口就是三条：

| 接口 | 约定 |
|---|---|
| **起跑** | 宿主 prompt 里只写"工作目录 + 第一条命令 `--guard` + 退出码 0 才开跑"，**不写业务判断**（框架自带闸门） |
| **收工条件** | 只存在一处：`project-state/跑批契约.json` + `task_estimate.py --guard`。**不许抄进 prompt**（抄一份就是第二份手抄清单，必然漂移） |
| **不嵌套** | 定时任务不许再去创建/调度另一个定时任务，每次触发必须自包含 |

宿主 prompt 模板（可直接抄）：

```
大项目跑批：工作目录 <项目根>。先跑 python scripts/task_estimate.py --guard；
退出码 0 才按 agent.md「事件循环」推进，每轮派发前重判闸门；
退出码 2 / 3 / 4 一律按「跑批运行」收工（停在安全点、落盘、记运行日志、报备）后结束。
```

**③ 并列互补（互不调用）**

例：**SaaS网站生成器**（从零搭站的方法论）、**元技能生成器**（生成/优化 skill）、**信息图生成器** 等——它们是独立工作面，框架既不需要包住它们，也不该在项目里再造一遍它们的规矩。真要在一个大项目里用，就当某个角色的"专用工具"，产物照样落框架的工作区。

### 为什么要这样分

- **单一真源**：流程真源只有 `agent.md` 一处，操作真源只有各 skill 一处，不互相抄、不互相漂移
- **可替换**：换一个部署技能、换一个调度平台，框架不用改；换框架，技能照样能单独用
- **各自诚实**：框架只说"流程不跳步"，技能只说"这个操作怎么做、有哪些坑"——谁都不假装覆盖对方

## 快速开始（三步）

```bash
# 1) 把整个目录复制到你的项目根（agent.md 所在目录即工作区根 WORKSPACE，目录名可自定）
# 2) 让 AI 助手读你项目里的 agent.md，并声明"按大型项目开发框架执行"
# 3) 冷启动：生成工作区摘要（≤15s、≤6k token）
python -X utf8 scripts/recall.py <项目根>
```

Windows + 中文路径建议一律 `python -X utf8`（否则 `open()` 默认编码会踩 GBK）。

各平台落地方式不同，但本质一样——**Markdown 指令集 + 本地脚本，不绑定任何一家 Agent 平台**：

| 平台 | 落地方式 |
|---|---|
| DeepSeek Harness（dsh） | 把本目录注册成技能入口（`skills/<名>/SKILL.md` 指向本目录 `agent.md`），用户手动调用；角色派发用 `subagent` |
| Claude Code / Codex / Cursor 等 | 把 `agent.md` 放进项目并写进项目指令文件；角色用子代理逐个派发 |
| ZCode / Trae | 作为子智能体定义或项目内指令加载 |

│   ├── 代码/                 # 代码级角色的产出区

## 机器可核的检查（这是它和"提示词合集"的区别）

| 命令 | 作用 | 退出码约定 |
|---|---|---|
| `python -X utf8 scripts/framework_lint.py <项目根>` | 结构 / 编号 / 引用 / 注册表体检 | 0 通过，1 有 ERROR（不许提交） |
| `python -X utf8 scripts/workspace_map.py <项目根> --check` | 工作区地图对账 | 0 / 1 / **2 = 无法检查** |

## 三条设计原则（为什么值得读一眼）

- **落盘即证据**：没写进工作区的产出 = 没干过。对话不是交付物。
- **单一真源 + 派生物**：契约在 `project-state/契约/`，地图/进度/json 都是派生物，可重算，不许手改。
- **摩擦即登记**：使用者卡住、绕流程、同一处反复改，当场记进台账；同类 ≥3 条就是下一版该改的条款。
