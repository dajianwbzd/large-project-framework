# 指导手册（Guidance Manual）

> 版本：v5.1.0。项目经理指导模式的**处方层**：`scripts/guide_audit.py` 负责**发现**，
> 本文件负责**怎么修、谁来修、下次怎么不再犯**。两者靠检查号配对，
> `python scripts/guide_audit.py --selfcheck` 校验**三方配对**（脚本 ↔ 本文件 ↔ 回归用例，
> 任意一方缺号即退出 1）。
>
> **两条贯穿全篇的诚实要求**：① 脚本每次输出都带**覆盖面声明**（「结论只在 G01–G11 内成立」），
> 逐条盲区见 §5；② 新发现的绕过必须变成下一个检查号（§7），否则指导模式只会用一张
> 永远不变的清单回答永远在变的问题。
>
> **为什么单独一份文件而不是塞进 SKILL.md**：`skills/项目经理/SKILL.md` 每次派发都进上下文，
> 处方是**按需下钻**的长文（对齐 v4.9.0 三档加载：清单住契约文件、正文只留指针）。
> 本文件也不进 `project-state/`——每个项目抄一份必然漂移，是老病根。

## 0 怎么跑（三步）

```bash
python scripts/guide_audit.py <项目根>              # 人看的报告（带处置与责任人 + 覆盖声明）
python scripts/guide_audit.py <项目根> --json       # 机器读（含 coverage 字段）
python scripts/guide_audit.py <项目根> --check G05  # 只看某一项（覆盖声明跟着缩小）
python scripts/guide_audit.py <项目根> --write      # 另写 project-state/指导体检-<日期>.md
python scripts/guide_audit.py --selfcheck           # 校验本文件与检查号三方配对
```

1. **跑探测**（零 token，脚本干活）：得到「哪个检查号 + 在哪张卡/哪个文件 + 什么证据」。
2. **对处方**：按检查号读本文件对应小节，取出「最小修复动作 + 责任人 + 人话解释」。
3. **讲给操作者听**：先讲症状，再讲为什么，最后讲这一次改什么。**一次最多讲 3 条**。

> **报告末尾的「覆盖面与盲区」不是免责声明**：它把「这 11 类查过且干净」和「从未查过」
> 分开写。转述结论时**必须带上范围**——把「G01–G11 内干净」说成「环境没问题」，
> 就制造了一次新的假保护（§1 第 4 条）。

## 1 边界：指导模式不是第二指挥官（先读这条，比处方重要）

1. **只做四件事**：发现 → 定位到既有条款 → 给最小修复动作与责任人 → 教下次怎么避免。
   **改什么、要不要改、由谁改，仍归主控与用户**——项目经理给的是诊断与处方，不是命令。
2. **不替任何人改文件**：唯一例外是 `--write` 写出自己那份体检报告。发现问题的角色自己改，
   这样责任面不糊（对齐 `协作规范.md` 的写隔离纪律）。
3. **判据只能来自既有条款**，不许现场自造标准（对齐 注意事项 33 临时兼岗纪律③）。脚本里每条
   检查都挂了出处；**说不出出处的怀疑，一律降为 WARN 并标「待人工确认」**，不许当 ERROR 报。
4. **不许把「没查过」说成「查过且干净」**（项目经理三条通用铁律②）。脚本跑不到的维度，
   报告里要显式写「本项未覆盖」，而不是沉默。**v5.1.0 起这条由机器执行**：脚本每次输出都带
   覆盖面声明（终端、JSON 的 `coverage`、`--write` 的落盘报告三处都有），
   转述时**必须把范围一起说**——省掉范围就是造假。
5. **报 ERROR 必须能被复核**：每条发现都要能指到具体文件与具体文字，不能是「感觉不对」。

## 2 通用处置模板（三句话讲清一件事）

- **第一句（症状，用他的话说）**：「你这次的 X 做法，会让 Y 出问题。」
- **第二句（为什么，讲后果不讲纪律）**：说清"代价出现在什么时候"，不要背条款。
- **第三句（这一次改什么）**：给**最小**动作——能被立刻执行的一条命令或一次改动，
  不要给"以后要规范流程"这种没有动作面的建议。

> 反面示范：「你没有遵守需求卡的落盘纪律。」——这是指责，不是指导。
> 正面示范：「这张卡没有进度记录，意味着三天后你自己也说不清当时做了什么；
> 现在补三行（时间 + 命令 + 结果）就行。」

## G01 需求未建卡 / 卡引用悬空

- **怎么认出来**：报告说「PRD 有 N 条 REQ，但 M 张卡一张都没承接」，或「引用了不存在的卡
  card-0NN」（来自 `任务清单.md` 或某张卡的 `deps`）。
- **判据出处**：注意事项 7（需求卡是驱动开发的唯一"需求"来源，改需求 = 改卡片）；
  需求卡模板「落盘」段；`任务清单.md` 由架构师拆解并与卡互相引用。
- **最小修复动作**：① 缺卡 → 产品经理按模板建 `需求卡/card-NNN/card.md`，把 REQ 写进
  frontmatter `req:`；② 悬空引用 → 把 `任务清单.md` / 卡 `deps` 里的卡号改成真实存在的卡，
  或删掉这条依赖（**不要留着一个指向空气的依赖**，它会让人以为有前置条件）。
- **责任人**：产品经理（建卡）/ 主控（排产与依赖图）。
- **讲给操作者听**：「不是"先写代码后补卡"，而是没卡就没有这件事的身份证。代码写完再建卡，
  验收时没人说得清它对应哪条需求，出了问题也回溯不到源头。现在补卡 5 分钟，
  上线后补就要重跑一遍验收。」
- **下次怎么避免**：把「看 PRD → 数 REQ → 建卡」当成一个动作，而不是两步分开做。

## G02 契约未定就开工

- **怎么认出来**：已开工（in_progress / reviewing / done / blocked）的卡，正文里写的
  `契约/xxx.md` 指的文件不存在；或引用还是 `<...>` / `xxx` 占位没填实。
- **判据出处**：六阶段主线的 ②a「契约先行」（配置中心 / API / 数据模型 / 环境等契约产出后
  才能批量开工）；注意事项 21（路径纪律，引用必须解析得到）；需求卡模板「上下文」段。
- **最小修复动作**：先落一份**最小**可用契约（哪怕只有接口签名、字段表、表结构），
  再把路径填进卡；确实不需要契约的卡，把占位行**删掉**而不是留着不填。
- **责任人**：该卡 `assignee`（契约本体通常由架构师产出）。
- **讲给操作者听**：「契约是"我们约定好长什么样"。它不在，两个角色就会各自猜一套——
  你写的接口叫 `userId`，他调的叫 `user_id`，联调那天才发现。先花 10 分钟把签名写死，
  比联调时吵一小时便宜得多。」
- **下次怎么避免**：卡置 `in_progress` 前，把卡里每个 `契约/...` 链接点开一次。

## G03 置 done 无进度留痕 / 验收记录空壳

- **怎么认出来**：状态已是 `done` / `reviewing`，但「进度日志」的实质字数不足 20；
  或存在 `验收-<路>.md` 但正文实质字数不足 60（只有标题和一个 `<填>`）。
- **判据出处**：需求卡模板「进度日志」段（**置 done 前本区必须有完整记录**）；
  注意事项 16（验收结论只能基于工作区证据得出，"整体看起来好了"不算数）；
  注意事项 19（验收合并 GO/NO-GO 归项目经理，不归主控）。
- **最小修复动作**：回填真实记录（时间 / 做了什么 / 跑的命令 / 结果 / 结论）；
  空壳验收按该路验收标准重做，证据落 `需求卡/card-NNN/证据/`，并在报告里写「环境 + 命令 + 结果」。
- **责任人**：该卡 `assignee`（进度日志）/ 对应验收路角色（测试 / 集成 / 安全）。
- **讲给操作者听**：「"做完了"不是证据，"我跑了 `pytest -k login`，8 项全过"才是。
  这张卡的进度日志是空的，意味着三天后你自己也说不清当时做了什么——出了问题只能重做一遍。」
- **下次怎么避免**：开工就写第一行，收工补一行；不要攒到最后一次性回忆。

## G04 待澄清未清零 / 需求确认物缺失

- **怎么认出来**：`clarify_open` 大于 0 却已开工；或 `req_confirm` 登记了确认物但文件不存在
  （假登记）；或已开工却没有 `需求确认-产品经理.md`，也没有 `source`（修复卡标识）。
- **判据出处**：注意事项 34（贯穿式澄清循环：`[待澄清: ...]` 可被 grep 计数，每轮 ≤5 问附候选）；
  需求卡模板 frontmatter 对 `clarify_open: 0` 的说明（**>0 = 未就绪，不得下发开发**）；
  验收标准 38（用户澄清与需求确认运转）。
- **最小修复动作**：把 `[待澄清]` 逐条问用户（≤5 问/轮、附候选选项），答案**写回** PRD/卡，
  清零 `clarify_open`，补 `需求确认-产品经理.md`（含版本 + 日期 + 授权留痕）。
- **责任人**：产品经理。
- **讲给操作者听**：「卡上写着 2 个待澄清就开工，等于把"我不知道"变成了"你猜"。
  这两个问题现在问用户 5 分钟就有答案；等做完了发现猜错，返工是 5 小时。」
- **下次怎么避免**：把「能不能开工」做成一个**可数**的门槛——`clarify_open` 为 0 才开工，
  不是"我觉得差不多清楚了"。

## G05 环境被降级 / 混用（用户点名场景）

- **怎么认出来**：`契约/环境.md` 里 dev / test / prod 三列表内，**prod 列的值与 dev 或 test 相同**
  （端口 / 库名 / `DATABASE_URL`）；或验收 / 测试卡证据标注的执行环境是 dev / 本地，而项目档位是三环境。
- **判据出处**：注意事项 14（环境一致性，先定档位再按其执行）、注意事项 15（测试数据纪律）；
  `契约/环境.md`「三库三套数据铁律」——**三库强隔离**（`DATABASE_URL`/端口互不相同）、
  **验收证据只认 test**、**禁止用"我在本地 dev 能跑"代替 test 验收**。
- **最小修复动作**：① 恢复三环境独立目标（prod 的端口 / 库名与 dev、test 互不相同）；
  ② 用 dev 证据验过的卡，在 test 环境**重跑一遍并替换证据**；③ 如果这个项目本来就是单环境，
  那就**改档位**（`profile` 与 `契约/环境.md` 一起改），而不是把 prod 伪装成 test。
- **责任人**：运维工程师。
- **讲给操作者听**：「把线上库换成测试库，短期看是"改动没风险"，实际是两件事同时坏：
  ① 你验证的是假数据，真实用户的脏数据（空值、超长、并发）从来没被测过；
  ② 出事时你以为有回滚，其实改的是测试库——生产数据早被写坏，而且没有备份。
  这条不是效率问题，是"事故不可逆"问题。」
- **下次怎么避免**：把 prod 的目标（库名 / 端口 / `DATABASE_URL`）写死在 `契约/环境.md`
  且由运维单人维护；每次变更单都带上「版本指纹」行（对齐 `变更申请单模板.md` §4）。

## G06 变更未审批就执行

- **怎么认出来**：`问题/变更申请单/CR-*.md` 的审批栏（G 段）主控「署名」列为空 → 视为**在飞**；
  若同时执行留痕栏（H 段）已有内容 → **未批准就执行了**；已署名但没记时间 → 不合格示例（空栏）。
- **判据出处**：注意事项 24（生产治理与应急：上线后一切生产变更先落 `问题/变更申请单/`，
  **审批栏缺签不得执行**）；`契约/环境.md`「prod 严格管理」（任何写操作先提交 SQL 修改申请单，
  经运维 + 项目经理审批后才可执行）；`变更申请单模板.md` G 段标题「缺任一 → 不得执行」+ §4 校验清单。
- **最小修复动作**：① 未执行的单据 → 补签（主控放行；数据 / 配置类加安全审计署名）；
  ② 已执行但未批 → **先停手**，补单并**如实**记录时间线，再按模板 §5 反例评估是否需要回滚；
  ③ 确实紧急的走「紧急变更单（可事后 24h 补）」，并留下用户知会时间。
- **责任人**：运维工程师（发起）/ 主控（放行）。
- **讲给操作者听**：「审批栏不是流程装饰。它存在的理由只有一条：出事时能回答
  "谁同意这次改动、当时依据是什么"。空着栏就执行，等于把可追溯性换成了省下的 3 分钟——
  真出事的时候，没人能替你证明这次改动是被允许的。」
- **下次怎么避免**：把「提交申请单」当成执行的**前置命令**，而不是执行后的补充说明。

## G07 证据落错地方

- **怎么认出来**：`tmp/` 内出现名字含「验收 / 证据 / 报告 / 交付 / 截图 / card- / tc-」的条目；
  或卡卷宗内单个文件超过 5MB。
- **判据出处**：注意事项 21（路径纪律：临时脚本 / 中间文件只进 tmp，收工即清，
  **证据不落 tmp**）；注意事项 35（工作区整洁与清收，项目经理常设职责）；
  需求卡模板「落盘」段（**>5MB 大产物留 `产物/`，卷宗里只放指针**）。
- **最小修复动作**：证据归位到 `需求卡/card-NNN/证据/`（对外交付件进 `交付/`）；
  大产物移到 `产物/`，卷宗里改成指针（路径 + 哈希）；**确认 tmp 无在飞任务后**再清。
- **责任人**：项目经理。
- **讲给操作者听**：「tmp 是草稿纸，会被清掉。证据放在草稿纸上，等于把验收结论建在一张
  会被扔掉的纸上——明天有人要复查，什么都找不到。而且清 tmp 的人不知道那是证据，不会手下留情。」
- **下次怎么避免**：把"存证据"固定成做完这一步就立刻执行的动作，别攒着回头搬。

## G08 卡卷宗混入禁入物

- **怎么认出来**：卡目录内出现代码源文件（`.py` / `.js` / `.ts` / `.sql` 等）、
  构建产物或依赖目录（`node_modules` / `dist` / `build` / `target` / `.venv`）、
  压缩包或二进制；另外 PDF / Word 这类交付文档会报 WARN（确认是否该进 `交付/`）。
- **判据出处**：需求卡模板「卷宗纪律」——**只放记录与证据，禁入**代码副本（代码在 `repos/`，
  放指针）、临时脚本（走 `tmp/`）、构建产物。
- **最小修复动作**：删掉卷宗里的代码与构建产物，改为**指针**（`repos/<路径>:<行>` 或提交哈希）；
  临时脚本搬进 `tmp/`；交付类文档按判据决定进 `交付/` 还是只留指针。
- **责任人**：该卡 `assignee`。
- **讲给操作者听**：「卷宗是档案袋，不是工具箱。把代码复制进卷宗，等于同时维护两份代码——
  改了真代码忘了改卷宗里的那份，下一个人读到的是过期的实现，比没有还糊涂。」
- **下次怎么避免**：卷宗里只写「指针 + 哈希」，永远不写「副本」。

## G09 卡无归属人 / 状态或编号非法

- **怎么认出来**：`assignee` 为空，或不是启用角色；`status` 不在
  `todo / in_progress / done / reviewing / blocked`；目录名与 frontmatter `id` 不一致；
  `req` 与 `source` 都为空（追溯链断）。
- **判据出处**：需求卡模板 frontmatter（字段语义 + 状态机单一语义）；
  注意事项 27（扩展角色表的口径——角色名以 `agent.md` 角色定义表为唯一事实源）。
- **最小修复动作**：补 `assignee`（必须是启用角色；角色没启用就走**临时兼岗**并按纪律登记）；
  `status` 改成合法枚举；目录名与 `id` 对齐；`req` / `source` **二者必填其一**
  （普通需求卡填 REQ，修复卡填 `tc-NNN#发现项号`）。
- **责任人**：主控。
- **讲给操作者听**：「没有归属人的卡 = 没人负责的卡。它会在看板上永远停在那里，
  谁都觉得是别人的事。状态写错更麻烦——`doing` 这种不在状态机里的值，
  会让所有按状态统计的报表和检查**静默漏掉它**。」
- **下次怎么避免**：建卡时一次把 frontmatter 填全，别留空。

## G10 有卡无落盘

- **怎么认出来**：某角色有非 `todo` 的卡，但 `进度/<角色>.json` 不存在；
  或已有卡进入 `done` / `reviewing`，但 `进度/overall.json` 不存在。
- **判据出处**：注意事项 16（**发现角色产出缺失，先打回补齐再谈验收**）；
  `agent.md`「角色产出落盘机制」（每角色一份进度 json）。
- **最小修复动作**：该角色补齐 `进度/<角色>.json`（当前状态 / 产出 / 待办）；
  确未参与则改该卡 `assignee`，并在 `运行日志.md` 记明原因；补 `overall.json` 汇总。
- **责任人**：该卡 `assignee` / 主控。
- **讲给操作者听**：「没有进度文件的角色，在框架里等于没来过。不是不信任，
  而是"他说他做了"没法验收——验收必须有落盘的东西可看。补一份 20 行的 json，
  比事后争论两小时快。」
- **下次怎么避免**：角色首次参与时由主控**当场**建好骨架，别等验收才发现缺。

## G11 发现未沉淀成检查点 / 归属悬空（自增强回路）

- **怎么认出来**：`project-state/记忆/指导发现台账.md` 不存在（WARN）；或台账里某一行的
  「归属」栏为空 / 只写 `-`（**零归属**）；或归属写的检查号在脚本 `CATALOG` 里没有、
  写的 `CR-YYYYMMDD-NNN` 在 `问题/变更申请单/` 下没有对应单据（**假登记**）；
  或「现有检查能否抓到」填了「是 / 否」以外的值。
- **判据出处**：注意事项 43（**靠 G01–G11 之外发现的绕过，先登记、再归属，零归属 = 未收口**）；
  注意事项 20①（踩坑即加规则，不许只修不断根）；测试卡纪律②（发现项零归属 = 未收口，**口径同源**）。
- **最小修复动作**：① 台账缺失 → `python scripts/migrate.py . --only guidance-ledger --apply`；
  ② 零归属 / 归属悬空 → 先判定「现有检查到底抓不抓得到」：抓得到就**写出那个号**
  （写不出号 = 抓不到）；抓不到就按 §7 三步把发现升成一个**新检查号**（脚本 + 手册 + 回归
  三处同时改），再把台账那行的归属改成新号。
- **责任人**：项目经理（登记与归属）/ 主控（决定升格为检查号并改脚本）。
- **讲给操作者听**：「这一条不是说你做错了，是说**这次的坑还没有变成规则**。你今天踩的坑，
  三个月后换个人会一模一样地再踩一次，因为坑只留在你脑子里。把它记成一行台账；
  反复出现或者一旦发生就不可逆的，进一步变成第 12 个检查号——下次它就自动被拦住了。」
- **下次怎么避免**：把「报告问题」固定成「**先登记一行**，再讨论要不要改」——
  没登记的问题在框架里等于没发生过（同注意事项 20③「无记录 = 未处理」）。

## 3 快速模式下怎么调整（执行者与降噪）

**执行者切换**：快速模式启用角色少，项目经理常由主控代管（见 `agent.md` 运行模式要点 6 / 10）。
**指导模式是正交开关**（`config.json` 的 `guidance`），**不绑定项目经理角色**：
PM 未启用时由**主控内联**执行（复用既有「临时兼岗」机制，注意事项 33，不新造机制）。

**按实时情况降噪**（脚本自动做，不需人记）：

| 条件 | 调整 |
|---|---|
| `mode` 为快速 | G02 的「契约引用未填实」不再报（快速模式本就允许无契约）；G04 缺确认物降为 WARN |
| `profile` 为 A（单环境） | G05 整体沉默（单环境项目不适用三库条款，对齐"档位未定不得硬套"） |
| 尚无开工痕迹 | G01 的 REQ 覆盖只记 INFO、不报错（新项目第一次体检不会被自己的模板吓到） |
| `mode` 为快速 | G11 的「台账不存在」降为 INFO（流程类在快速模式只提醒）；**但零归属 / 假登记仍是 ERROR**——那张台账既然存在，就说明有人在用，写了个查不到的号不是"没来得及"，是**已登记的错** |

**重点转移**：快速模式下指导模式的重点从「流程合规」转到「**别把不可逆的事做错**」——
改库 / 线上变更类（prod 目标混用、审批缺签）永远保留，流程类（缺卡、缺留痕）
作为提醒而非拦截。判据很简单：**这件事做错了能不能撤销**。

## 4 与既有工具的分工（不要重复跑）

| 工具 | 回答的问题 |
|---|---|
| `framework_lint.py` | 框架 / 项目**结构与引用**合不合规（编号、引用、注册表、漂移） |
| `path_audit.py` | 文件**在不在该在的地方**（游离条目、tmp 残留、大文件） |
| `workspace_hygiene.py` | **垃圾清没清**（分级清理，默认只报告） |
| `retro_calibrate.py` | 上轮**行动项落没落地**、该不该复盘 |
| `task_estimate.py` | 估得准不准、**钱烧到哪了** |
| `style_audit.py` / `db_audit.py` / `git_audit.py` | 风格 / 数据 / 版本控制三条线的**技术判据** |
| **`guide_audit.py`（本手册配套）** | **机制有没有被绕过**（没建卡、没留痕就 done、环境降级、无单证改库） |
| 同上（G11） | **绕过有没有变成下一个检查号**（自增强回路的入口：台账登记与归属） |

前六类都**默认"机制被使用了"**——它们检查的是机制内部的一致性与质量。
本工具反过来问：**这个机制到底有没有被用**。两者互补，不重叠。
其中 G11 更进一步：**连"这张清单本身会不会变"也要查**——它是本工具的自指部分，
判据与 G01–G10 同源（注意事项 20① / 测试卡纪律②），不新造标准。

## 5 诚实边界：这些维度的探测器**还没做**，别当成"已查过"

> **本节的清单由 `scripts/guide_audit.py` 的 `COVERAGE_UNCOVERED` 维护，那是唯一事实源**
> （脚本每次输出都按它念一遍；`--selfcheck` 会校验本节覆盖了它的每一条，少一条即报）。
> 本节负责解释**为什么**、以及**真想查该怎么办**。**每条开头加粗的那个词就是脚本念的维度名**——
> 两边用词必须一致，这一点由 `--selfcheck` 机器守着（改词就得两边一起改，否则报 ERROR）。

- **真实运行环境**（"是不是真的换了库"）：只能核文档声明（`契约/环境.md` 的 dev / test / prod 列值），
  真实 `DATABASE_URL` 在 `.env`（不入库）。要真查得在目标机上跑
  `psql -c 'show port'` 一类命令并按验收标准留证。**所以本项是"声明层"检查，
  不是"运行时"检查——不许把它说成"已验证环境没问题"。**
- **证据真伪**（"验收是不是真的跑过"）：只能看有没有记录与证据，**伪造的记录看不出来**。
  防伪靠 `契约/审核规范.md` 的蒙混信号（S1~S8），由人（审计 / 合并角色）来做。
- **角色产出真伪**（"角色是不是真的干活了"）：`进度/<角色>.json` **存在 ≠ 内容真实**，同样靠穿透审核。
- **需求是否合理**（"需求对不对"）：本工具只管需求有没有被卡的机制承载，**不管需求本身是否合理**。
- **没被想到的绕过手法**（v5.1.0 新增，也是最要紧的一条）：G01–G11 是一张**已知**清单，
  **没被想到的绕过不会出现在任何地方**。G11 只回答「发现了有没有记下来」，
  **不回答「有没有发现」**。所以这张清单必须长——靠人和用户发现新坑，按 §7 升成新检查号；
  一个季度都没新增过检查号的项目，要么真的没新坑，要么**没人把坑记下来**。

> 报告里对这几类要显式写「本项未覆盖」——沉默会被读成"没问题"，
> 那是比没查更坏的结果（对齐项目经理通用铁律②：区分「查过且干净」与「从未查过」）。

## 6 常见借口表（指导模式版）

| 借口 | 怎么回 |
|---|---|
| 「先做完再补卡」 | 补卡不等于有卡——事后补的卡，验收链是断的，要重跑 |
| 「就这一次，线上急着要」 | 急也走紧急变更单（可事后 24h 补），急不能省掉"谁同意的" |
| 「测试库跟线上一样」 | 一样的数据不会一样地脏；而且出事时你回滚的是测试库 |
| 「我本机跑过了」 | 本机能跑不等于 test 能跑，验收证据只认 test 环境 |
| 「进度文件我回头补」 | 现在补 20 行，事后争两小时；而且打回补齐是硬规则 |
| 「这东西不算证据，随便放」 | 验收结论只能基于工作区证据，放 tmp 等于没留 |
| 「契约还没定，先写起来」 | 那就先写 10 分钟的契约；两个人猜两套，联调时要还回来 |
| 「状态随便写一个」 | 非法状态会让报表和检查静默漏掉这张卡 |
| 「这个坑我记在脑子里了 / 微信上说过了」 | 脑子里不算登记：台账里那一行**归属栏必须填**，填不出号就按 §7 升成检查号 |
| 「先记下，回头再沉淀」 | 归属栏空着 G11 就报 ERROR——**零归属 = 未收口**，和卡上的发现项一个口径 |
| 「G01–G10 都没报，说明环境没问题」 | 那是**范围外**的话：没报只说明这 11 类痕迹不在，覆盖声明（§5）每次都会跟你念一遍 |

## 7 发现升成检查号（自增强回路：G11 → 新检查号）

> 这是**指导用户**与**框架自增强**的接缝：G01–G10 抓已知的绕过，G11 抓「新绕过有没有被
> 记成规则」。本节是 G11 的处方——**怎么把台账里的一行真的变成一个检查号**。
> 口径与「踩坑即加规则」（注意事项 20①）同源，只是这里服务于指导模式自身。

**什么时候该升**：台账里「现有检查能否抓到」填**否**，且满足任一条——
**反复出现 / 一旦发生不可逆 / 换个项目同样会犯**。
一次性的手滑不用升（写进 §6 借口表就够）；把检查号当垃圾桶，下一个检查号就没人看了。

**三步（缺一不可，顺序不能反）**：

1. **先写手册**（本文件）：新增 `## GNN` 小节，**六件套照抄既有格式**（怎么认出来 / 判据出处 /
   最小修复动作 / 责任人 / 讲给操作者听 / 下次怎么避免）。**判据出处必须指到既有条款**——
   指不到就说明该改的是条款，而不是加一个检查号（临时兼岗纪律③：只兼有明确判据的活）。
2. **再写脚本**（`scripts/guide_audit.py`）：`CATALOG` 加 `"GNN": (症状, 最小修复, 责任人)`，
   实现 `check_gNN(...)`，并在 `main()` 里调用。**检查号只能往后加**：不插入、不复用已废弃的
   号——旧报告、旧台账里的号必须永远指同一件事，否则历史记录会指向另一个含义。
3. **最后写回归**（`scripts/tests/test_guide_audit.py`）：加一条用例，且**必须验证过它会因
   变异而失败**（把判据改坏一次，看用例真的红——「一个测不出错的用例和一个永远返回
   0 ERROR 的检查器一样没有价值」）。

**收口**：`python scripts/guide_audit.py --selfcheck` 回到 0（**三方配对**：脚本 ↔ 手册 ↔
回归，任一方缺号即 ERROR），并把台账里那条发现的「归属」改成新号。

**不许做的事**：

- 跳过手册只写脚本——查出问题没人知道怎么修（v5.0.0 要堵的正是这个洞）；
- 跳过回归——新检查号下次悄悄失效没人拦得住；
- 为了"看起来干净"把「能否抓到」一律标「是」——**标「是」也要写出是哪个号**，
  写不出号码就是抓不到，那是在给自己发合格证（同 v4.4.0「假保护」教训）。
