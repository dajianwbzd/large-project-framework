# 完成定义（Definition of Done，DoD）

项目级统一质量底线：任何需求卡从 `in_progress` 变为 `done` 之前，都必须通过本清单的完整检查。它与卡片「验收标准」互补——验收标准回答"做对了东西吗？"（任务级、每卡不同），完成定义回答"它准备好了吗？"（项目级、每次相同）。**两者同时满足才算完成**，跳过任何一方都会留下"看似完成实则未完成"的工作。

## 完成定义 vs 验收标准

| 维度 | 卡片「验收标准」 | 完成定义（本文件） |
|---|---|---|
| 范围 | 单张需求卡 | 全项目所有变更 |
| 变化 | 每张卡各不相同 | 固定并复用 |
| 回答 | 我们构建了*这个东西*吗？ | 它*准备好*了吗？ |
| 制定者 | 产品经理写卡时定义 | 项目初始化时定义一次 |
| 示例 | "用户可通过邮箱链接重置密码" | "测试通过、无回归、契约一致、记忆已同步" |

## 检查清单

### 9.15 运行模式默认快速（v5.3.0：怎么决定是不是快速模式）

> 判据来源：agent.md「运行模式」节 + `config.json` 的 `mode` / `profile` + 注意事项 45 + 验收标准 #49；门禁：`python scripts/framework_lint.py <项目根>` 的 **I 组（I01~I08）**。

- [ ] **`mode` 有显式声明**：`config.json` 的 `mode` 为 `quick` / `full`（**缺省即 `quick`**；空值按默认走，不建议）；`mode` 与 `profile` 自洽——**`quick` + `profile=C`（标准三环境）= ERROR**（快速模式却按三库要求），`quick` + `profile=B` = WARN
- [ ] **`full` 有入口凭据**：只有两条正当入口——① **用户明确指定**（留痕引用原话要点）；② **项目经理按 U1~U7 评估为大项目 + 已告知用户**（逐条"是/否 + 依据" + 告知时间）。**只改 `mode` 不写依据 = 静默切档**，⑥ 验收前置检查打回
- [ ] **切档留痕在位**：《主控工作计划》的「运行模式」段写明**当前档位 + 怎么进来的**（默认起步 / 用户原话要点 / 评估结论 + 告知用户的时间）；**降级（完整→快速）同样留痕**，且已产生的契约与关卡不回退删除
- [ ] **判据是交付形态与不可逆性，不是代码行数**：多模块联调 / 多里程碑 / 对外交付件 / 认证授权与敏感数据 / 上线与客户端交付 / 破坏性迁移 / 多团队并行（U1~U7）——命中一条即应评估
- [ ] **不确定就往快速模式走**：正向切档（快速→完整）只是接着往下走，反向切档会让已铺开的文书变沉没成本；**"我觉得它挺大的"不是入口**，那是评估意见，得先告知用户

### 9.16 快速模式的裁剪面（v5.4.0：什么可以裁、什么一律不裁）

> 判据来源：agent.md「运行模式 → 快速模式的裁剪面」+ 验收标准 #8 + 注意事项 33；工具：`python scripts/guide_audit.py <项目根>`（G01/G02/G03/G11）+ 回归 `scripts/tests/test_guide_audit.py` **T-K 组**。

- [ ] **只裁三样**：**① 角色数**（按需挑子集，最小闭环=产品经理+对应开发+测试工程师）· **② 文档深度**（卡内需求描述压到 3-5 条要点、不产出完整 PRD、不单独出架构文档）· **③ 测试密度**（`test_card_cadence` 降 `ship`；单测等按项目实际豁免并注明依据）
- [ ] **不可裁六项都在位**：**需求建卡与卡卷宗结构**（`需求卡/card-NNN/`：`card.md` + 思路 + 验收记录 + `证据/`；**没有卡不开工**）· **卡状态流转与验收留痕** · **用户确认关卡**（Create → Confirm → Deploy；"迭代轮次之间不设关卡"≠"建卡前不用给用户看"）· **创建者 ≠ 验证者** · **产出落盘**（进度 json + 描述性文件）· **路径与留痕纪律**（八域 / 根级白名单 / 证据不进 `tmp/`）

- [ ] **"免维度"不等于"免承接"**：被裁剪的维度若项目实际需要，仍要有人（含兼岗者）按**既有判据**做完，或按升级条件启用该角色 / 切完整模式（见本清单「模式适配」与注意事项 33）

- **界面维度（v3.19.0）**：含 UI 面的项目，④ 前须过【关卡③】设计确认（用户/客户点头），⑥ 期每个 `ui: true` 卡走设计还原走查；设计未确认就批量实现 = 整批前端返工风险
- **按系统（v3.17.0）**：到测试卡触发点（里程碑收口 / 上线前，见 `config.json` `test_card_cadence`）时，按 `测试卡/tc-NNN/` 的**覆盖维度矩阵**执行系统级测试；**收口条件 = 覆盖维度全跑完（每条有证据）+ 发现项零无归属**（归属 ≠ 修完）
- **模式适配（v5.3.0 加运行模式默认纪律；v5.4.0 加快速模式裁剪面；v3.16.0；v3.19.0 加界面维度；v4.1.0 加临时兼岗；v4.4.0 加整洁收口；v4.5.0 加长时估算；v4.6.0 加成本与关卡；v4.7.0 加复盘与职责校准；v5.0.0 加指导模式与客户技术说明；v5.1.0 加指导清单自增强）**：快速模式/小项目由主控按 config.json `profile` 裁剪适用维度（如免三路中的集成/安全、免生产部署维度、免第 8 节设计走查、验收标准 #23 架构图契约豁免），裁剪写入 overall.json 并告知用户；**裁剪的是"适用维度"不是放低"到位标准"**——被保留的维度仍逐项全过。**未启用角色的工作按 `agent.md` 运行模式要点 10「临时兼岗」承接**（登记承接者与判据来源、不得假扮原属角色、命中"必须升级"条件即转正）——**"免维度"不等于"免承接"**：被裁剪的维度若项目实际需要，仍要有人（含兼岗者）按**既有判据**做完，或按升级条件启用该角色/切完整模式。**§9.9 工作区整洁不随模式豁免**（任何模式都产出中间文件）；**快速模式下项目经理职责由主控代管时，收口由主控执行并在 overall.json 留痕**。**§9.10 长时任务估算与容量控制同样不随模式豁免**——只要用户给了时间窗（整夜/半天），无论开几个角色都要有**估时 + 估 token + 依据 + 置信度 + 命中概率 + 无人值守四查**；**长时无人值守还须过可实施性关卡并挂事中成本流水**（否则整夜编排要么干烧要么烧穿）。快速模式下估算由主控代出并在 `主控工作计划.md` 标明"主控代估"（**替身可代出估算，但不减免依据与置信度要求**）。**§9.11 复盘与角色职责校准**在快速模式下**随触发判据自动豁免**——小项目收口卡数到不了 `every_n_cards`（默认 20）就不会触发，**这是设计而非疏漏**（复盘的价值随样本量增长）；但**一旦 `--due` 报"到点"就必须逐项过**，且**"没到点"要在报告里说明是基于卡数而非"忘了做"**；快速模式无独立项目经理时由主控汇总事实，**"只汇事实不做角色 judgment"的边界不因代管而放宽**。**§9.12 派发简报装配纪律同样不随模式豁免、也几乎不构成负担**——它**不新增任何文书**，只是把本来就要写的简报内容排个序；哪怕只派一次子代理，A/B/C 顺序（共享块在前、卡块居中、角色块在后）也是零成本就能做对的，反之每一次派发都在为可避免的重复计费买单。**§9.13 指导模式**在快速模式下**不豁免但会自动降噪**（脚本按 `mode` / `profile` / 开工痕迹裁剪报项），且**判据收敛为"这件事做错了能不能撤销"**；**无独立项目经理时由主控内联执行**（复用临时兼岗，不新造机制），**"不是第二指挥官"与"发现项零归属 = 未收口"两条边界不因代管而放宽**；**面向客户的技术说明在快速模式下同样要过确认关卡**（对外动作不因模式而免确认）。**§9.14 指导清单自增强**同样**不随模式豁免**，且几乎不构成负担——**覆盖声明与三方配对都是脚本行为**（零 token、零额外文书，只是让结论带上范围），快速模式下唯一的差别是**台账缺失只提醒不报错**（流程类降噪）；但 **"零归属"与"假登记"在任何模式下都是 ERROR**（台账存在就说明有人在用，写个查不到的号不是"没来得及"），**"没被想到的绕过不会出现在任何地方"这条边界也不因模式而放宽**。**§9.15 运行模式默认快速（v5.3.0）与 §9.16 快速模式裁剪面（v5.4.0）是另两个面，不随模式豁免**——前两个小节说的是"**快速模式内部**保留哪些维度"，**§9.15 说的是"怎么决定是不是快速模式"、§9.16 说的是"快速模式内部什么不能裁"**（两节正文见下，判据与条目在那里，此处不重复；另见注意事项 45、验收标准 #49 与 #8）
- 对项目一次性定制这份清单，然后原样复用。每个迭代都重新谈判的完成定义就不是完成定义。

## 警示信号

- "完成了，只是还没跑"：未经验证的工作不算完成。
- 把"构建通过"或"测试通过"当作完成的同义词，跳过回归、文档、契约或记忆同步。
- 因截止日期压力而适用不同标准。
- 把卡片「验收标准」当作全部门槛，没有长期质量底线。
- 契约不符或记忆未同步就置 `done`（静默偏离）。
- 未经审查就宣布完成。
- **跳过环境自检直接验证**：在未知环境上得出的结果不可信。
- **用"本地能跑"代替 test 环境验收证据**：dev 环境证据 ≠ 验收通过。
- **环境清单与实际环境不一致仍继续开发**：环境漂移是"效果天壤之别"的头号来源。
- **分析/调研结论无来源支撑**："我估计""应该可以"不是依据；关键事实必须可追溯到来源（URL/实验/代码证据），来源不明标注"待核实"。
- **产物写进根目录/别人的项目/只存在于 tmp**：路径错位 = 证据链断裂（v3.14.0 路径纪律）；临时文件不是交付物，验收只认正式路径。
- **测试卡收口时发现项还有"待定/回头再说"**：无归属 = 未收口（v3.17.0）——每个发现项必须落到 A 回退需求卡 / B 新建修复卡 / C CR 或《忽略决策记录》。
- **"界面差不多就行、功能对了最重要"**：三路验收（测试/集成/安全）分别看功能、契约、安全，**都不看界面是否照设计做**——设计与实现的一致性必须由 UI设计师 在**真实运行界面**上独立走查（v3.19.0），前端自评"照设计做了"不构成证据。
- **"设计稿还没给用户看，前端先做着"**：含 UI 面的项目【关卡③】设计确认是硬关卡——设计未定就批量实现 = 做完再被否，返工面是整个前端（乙方交付场景尤甚）。
- **"设计规范写完了，但代码里全是裸色值"**：设计规范不是文档摆件——实现只引用令牌符号、走查按 `代码复查规则库.md` 域7 核，界面一致性是可验证的完成条件，不是主观印象。
- **"权限模型写在代码里就行"**：没有 `契约/安全与数据.md` 的角色矩阵就没有判据——越权测试与安全审计无从判定"该不该放行"，越权与泄漏只能等出事（§9.7）。
- **"内网/后端不对外，不用加密"**：跳过传输加密、弱哈希（MD5/SHA1/明文）、密钥入库都是系统性风险；生产明文 HTTP、密钥不进轮换剧本 = 未完成（§9.7）。
- **"上架前才发现没有签名证书、没有回滚路径"**：客户端交付（签名/公证/自动更新/商店上架/分级合规）不是收尾杂活，是交付门禁（§9.8）。
- **"改断言/期望值让用例变绿"**：单测与验收都禁止——改标准让用例过 = 作弊（§1、前端/后端 skill 单元测试节）。
- **"工作区乱点不影响开发"**：脏乱让证据不可信、交付找不到文件、子代理写错地方（v4.4.0 §9.9）——每次工作收尾就清一遍，攒到交付前再清，中间文件早已分不清谁是在飞资产（部署分片/回滚备份误删即中断在飞任务）。
- **"交付完了" = 活干完了**：交付后未收口 = 批次未收口——`交付/` 里旧版本与打包中间物堆积、`tmp/` 残留未清，下批验收要在垃圾堆里找证据（§9.9）。
- **"旧文件都删了，反正有新版"**：正式产出与旧版本走**归档**（可逆），只有明确无用的才自动删；**证据、`交付/发出记录.md`、`project-state/` 下的正式产出（其根级散落的一次性中间件除外）、`.git/` 永不进清理候选**，**已发给客户的副本永不自动删**（不可逆对外动作）。
- **"根目录那个脚本像临时的，删了省事"**：**归位 ≠ 清理**——根级散落物的处置属结构变更，走 `path_audit.py` + 主控裁决；脚本名像临时 ≠ 是临时，删错工具比留个文件贵。
- **"今晚让 agent 自己跑一整夜"（窗口不清、依赖未清）**：长时无人值守最典型的事故不是跑错，是**停在一个必须人工的依赖上空转到天亮**（v4.5.0 §9.10）——开工前先清 `待办/自然人.md` 未闭环项、排除对外与不可逆动作、挂 token 预算熔断；**有一个自然人待办在飞，就不进整夜序列**。
- **"估得差不多就行，明天再看"**：估算不带依据与置信度 = 没估算（§9.10）——成本主驱动是**子代理派发轮次 × 每轮上下文规模**，不是"还剩几行代码"；卡收口不回填 `进度/估算实测.csv`，第二次估算就没人信。
- **"项目经理把今晚的序列排好了"**：**估算是项目经理出，编排权在主控**（§9.10）——项目经理给的是「估时 + 估 token + 依据 + 置信度 + 候选序」，最终序列/先后/汇报时点由 `agent.md` 主控决定；项目经理越界排产 = 绕过主控的窗口与预算判断。
- **"排满了，应该能跑完"（v4.6.0）**：**报不出 P 就不算排完**——三点估算给区间、σ 按 √Σσ² 合成、P < 下限（默认 0.80）就裁尾；**"排满但可能烂尾"不是成绩**。而且**估时只是内部调度量，不得对外当成交付日期承诺**（AI 时代的工期预测是噪音）——`--p-min` 被悄悄放松、或把 P 写成"大概没问题"，等于没有这道闸。
- **"卡里没写有问题，那就是没问题"（v4.6.0）**：**「没人查过」≠「查过且干净」**——候选没写 `AC`/`契约就绪` 的进 `undeclared` 清单，**不许因为"没人报问题"就当作通过**；可实施性关卡的判据只有一个：**一个开发在没人可问的情况下，能不能把这些卡做完？** 答不上来就不进长时编排（FAIL 退出码 1），发现项**必须指名修复者**——不指名的发现等于没发现。
- **"先把夜里跑完，成本早上一起算"（v4.6.0）**：**只有事后账本等于没有熔断**——每轮不加 `--spend`、不看 `breaker`，整夜就是"烧到天亮才知道烧了多少"；**累计值必须由流水各行重算**（手改累计列 = 伪造台账），**没有 `cost_table` 就留空不猜价**（token 与熔断照常生效）；超支要**三分归因**（估算偏低/轮次失控/范围漂移）——混为一谈等于没复盘。
- **"脚本报错了，按经验估一个吧"（v4.6.0）**：三条通用铁律同样管项目经理——**脚本失败不许静默兜底**（报错原文 + 失败原因 + 人工判断须标注来源）、**区分「查过且干净」与「从未查过」**、**没人确认 ≠ 默默通过**（到点无人回记「未获确认」，不许写成"通过"）。
- **"这个复盘会拖太久，等有空的迭代再开"（v4.7.0）**：`--due` **报"未到点"是设计（按收口卡数），但"忘了做"不是**——到点未开、或陈旧提醒出现却无人回应，都要在报告里说明**为什么这次没开**；复盘的意义正是**趁偏差还小的时候纠**，攒到"有空"往往已经是一堆卡带着同一个错收口了（§9.11）。
- **"这轮没到点，那我隔两周再看一眼"（v4.7.0）**：**时间只是陈旧提醒，不是触发器**——闲置两周没有新卡，复盘只会拿到一份零新数据的报告；三天干完 40 张卡却正该复盘。**墙钟时间不映射工作量**（§9.11）。反过来，"按时间排复盘"也会与已有 `test_card_cadence` 形成**第二套节拍器**，两套迟早打架。
- **"这个角色这个迭代返工最多，建议把他裁了"（v4.7.0）**：**只汇事实，不做角色 judgment**——`--assemble` 给的是"谁多轮返工、哪类卡估不准"的量化输入，**职责去留的判断归主控与用户**；越界下"该裁谁"的结论 = 拿事实角色扮演裁决者（§9.11）。
- **"行动项先记下来，证据回头补"（v4.7.0）**：**没有 `--核验证据` 的行动项等于没人认领**——下一轮只能判 `unverified`，而它**照样让 `--actions` 退出码 1**。证据是机制 K 的全部意义所在（§9.11）。
- **"这条都落地了，逾期标记就免了"（v4.7.0）**：**落地与逾期是两件事，两列正交、不许合并**。「真落地了但到点没人在核收」正是最危险也最容易被忽略的一类——合并成一列会让它记成 `landed` 静默通过（§9.11）。
- **"这个来源没数据，那就是没问题"（v4.7.0）**：**「未查过」不许渲染成「没有异常」**——"这个角色成本是 0"和"这个角色成本我没查到"是两件完全不同的事；成本按累计列逐行差分还原，不可得退回 `cost_table`，**都没有就留空不猜价**（§9.11）。
- **"卡号得写在简报第一行，不然子代理不知道干哪张卡"（v4.8.0）**：把随卡变化的字节放最前 = **第一个 token 就分叉**，A 段之后写得再规范也全部重复计费——卡号属于 **B 卡块**，该让位就得让位（**人觉得顺的顺序 ≠ 缓存友好的顺序**，§9.12）。
- **"A 段里顺手填个日期/项目名，反正每次都跟着替换"（v4.8.0）**：**A 段零插值是硬约束**——任何随卡或随角色变化的字节都会把分叉点提到该处、**A 段整体失效**。随卡变的放 B/C 段，固定不变的写成**固定路径指针**（§9.12）。
- **"每个角色自己组装自己的简报更灵活"（v4.8.0）**：**这正是被打散命中率的原状**——共享内容的位置或措辞只要有一处不同，公共前缀就在那里断掉；**A 段必须逐字相同**，灵活的部分（角色特有约定、专项指令）放 C 段（§9.12）。
- **"模板写对了就行，派发时来不及照抄"（v4.8.0）**：**模板正确 ≠ 实际派发正确**——本条的核验对象是**派发前简报原文**；而且**子代理读取顺序也要照 A→B→C**，读入内容落在同一相对位置，公共前缀才成立（§9.12）。
- **"lint 跑过了，说明缓存省下来了"（v4.8.0）**：**骨架检查只防"顺序被改坏"，不构成命中证据**——实际命中须由网关侧 `trackCacheUsage` 观测，**未观测时不得写"已命中缓存/已省 token"**（§9.12）。
- **"G01–G11 都没报，说明环境没问题"（v5.1.0）**：**这是范围外的话**——没报只说明这 11 类**已知**痕迹不在（§9.14）——覆盖声明每次都会念一遍盲区（真实运行环境 / 证据真伪 / 角色产出真伪 / 需求是否合理 / **没被想到的绕过手法**），**转述时省掉范围就是造假**；"范围内无问题"永远不能升级成"没有问题"。
- **"这个新坑我记下来了，回头再加检查"（v5.1.0）**：**记在心里、记在微信里、记在对话里都不算登记**——台账那一行**归属栏必须填**，且只能指向**真实存在**的东西（检查号 / `问题/变更申请单/` 下的变更单 / `scripts/` 下的检查脚本）；指向一个查不到的号 = **假登记**（同 v4.4.0「假保护」），**零归属 = 未收口**（同测试卡纪律②）。**"回头"是这件事最常见的死法**（§9.14）。
- **"加个检查号嘛，脚本里加一行 CATALOG 就行"（v5.1.0）**：**跳过手册或回归的号活不过下一次改动**——`--selfcheck` 会直接报 ERROR（三方配对：脚本 ↔ 手册处方 ↔ 回归用例任一方缺号即不配对），而**没人知道的检查号等于没有这个检查号**；另外**检查号只能往后加**——插入号或复用废弃号会让旧报告与旧台账里那行指向另一个含义，**历史记录会静默改名**（§9.14）。

### 9.17 再调用冷启动：一条命令 + 机读块（v5.6.0：状态从"现场排查"变成"确定性输出"）

**判据**：每批收口后或会话中断后再进来，**第一条命令是** `python scripts/recall.py <项目根>`（≤15 s / ≤6 k token），
按摘要点到名的 1–3 项下钻；**系统级状态的唯一真相源是测试卡的 `覆盖矩阵.md` / `发现项.md` 机读块**，
卡级唯一真相源是卡 frontmatter，`进度/overall.json` 与 `任务清单.md` **降级为可对账的派生物**（详见 `注意事项.md` 46 与 `验收标准.md` #50）。

**为什么立这一节**：旧做法（再调用时读账本 + 运行日志 + 十几份对账表现场重建状态）的代价是**结构性的**，不是
"某个人慢"：实测某真实工程状态面 **185 万 token**，其中活状态只有 **2.8 万 token（1:66）**——**66 倍全花在读已被
写过的散文**。而"再写几份对账表"只会让这个比值更差（多写的表本身就是新的散文）。

**这一节最容易读反的几处（口语化误解 → 真相）**：

- **"没有机读块 ⇒ 结论是空的 ⇒ 就按没问题吧"（v5.6.0）**：**读不到 ≠ 没有问题**——摘要里那行「**未知**」说的是"系统级状态**不可知**"，把它转述成"系统级没问题"就是造假（同通用铁律②，§9.1）。同一个错误在本轮新代码里犯了 **5 次**（账本没有卡状态面却报「少了 62 条」、读不到机读块却印「未通过 **0** 项」、**清单勾选 0 条被当成"没有滞后"**（真相是那个视图没在用）、计数标签印「未迁移 0」而下面正列着 4 处缺块、**done 卡没有任务行被报成"任务行未勾"**（真相是那些卡在该视图的覆盖面之外））——**`x or 默认值` / `len([])==0` 这两个写法出现时，先问「空」与「缺」在这条路径上是不是两件事**（§9.17）。

- **"这个派生视图看着没人用 ⇒ 那就别对账了"（v5.6.0）**：判一个对账线该不该留，看的是**框架自己的约定**，不是**抽样看到的执行现状**。`任务清单.md` 曾因"实测某工程 1014 行、勾选 0 条"被判定为**规划件、不参与对账**并裁掉整条对账线，而框架模板与验收前置检查第 3 项都明写它**要三方一致**——**抽样看到的"没在用"是执行问题，不是约定问题**；正确做法是把"没在用"做成**报告里的一个状态**（未启用/未维护/在维护三态分开印），而不是拿它当"这条线不用查"的理由。**"看着没用"这个判断杀掉的检查线，比它拦住的假差异更贵**（§9.17）。

- **"摘要说这卡是 `in_progress`，那状态就清楚了"（v5.6.0）**：**摘要交代状态、不交代产出质量**——"卡还在飞"和"卡里的东西对不对"是两件事，查工作区实际产出那一步不能省；摘要的作用是**把要读的范围从 71 张卡缩到 1–3 张**，不是替你做判断（§9.17）。

- **"超出了预算，把计数砍了让它短点"（v5.6.0）**：**超预算只裁明细、永不裁计数**——把"我没输出"渲染成"没有"正是本条要治的病；明细可截断但必须显式标注，且**被省略的明细不影响任何计数**。判据很硬：**同一个项目，`--budget` 调小后任何计数变小即不合格**（§9.17）。

- **"退出码 2，看着像正常结束"（v5.6.0）**：**`2` 是"无法检查"，不是"没问题"**——老 schema、路径不通、缺 `project-state/` 都会走 2；**把"无法检查"当"检查通过"用，等于把体检报告上的空栏读成健康**（同 §9.10 的闸门纪律：**"查不到"不许算"已满足"**）（§9.17）。

- **"路径校验按文档写的'相对项目根'就行"（v5.6.0）**：**校验器的基准必须从真实产物取证，不能从文档约定推**——真实工程是**相对 `project-state/`** 写（还有带前缀、通配根 `证据/D1-*`、甚至整行命令的写法）；按文档拍一个基准的代价是**每次再调用都产生同一批假阳性**，而**假阳性第三次以后人就开始整体忽略这个检查器——它等于没有，却还占着"已体检"的位置**。规则要"**全试一遍都不成立才算失败**"，且**修宽之后必须重跑变异用例**证明判别力没丢（§9.17）。

- **"变异用例全绿，说明检查器验过了"（v5.6.0）**：**变异用例对"没改坏却也报"是结构性失明的**——本轮判据修正**前**那一版，**18 个变异全绿的同时**，干净夹具报了 1 个严重项（把真实存在的文件判成证据缺口），**本轮全部真实的检查器 bug 都是"干净用例"抓到的，没有一个变异用例能抓到**。所以检查器**必须成对**：①干净用例证明**不乱拦** ②变异用例证明**能拦**。**缺①的测试套件比没有更危险——它给人"已验证"的错觉**（第 3 次确认，前两次见 v5.5.0 风格检查器与 `workspace_hygiene`，§9.17）。**另半条**：改宽判据（修假阳性）之后**必须回跑变异用例**证明真阳性没被一起修没——修宽是最容易把判别力一起修丢的动作。

### 9.18 定位锚点：发现项与修复卡要写清「改哪里 + 怎么复现」（v5.7.0：把"每次重新定位"变成"下一轮直接下钻"）

**判据**：测试卡发现项的机读块是 **7 列** `id | severity | owner | ref | state | anchor | entry`，
`anchor`（`路径` / `路径:行` / `路径#符号`，真不知道写 `未知`）与 `entry`（一条可复跑的命令 / 触发路径 / 最小用例）
**不得同时为空**；修复卡（`source` 非空）的 frontmatter 同要求；
**未闭环发现项的锚点由 `recall.py` 摘要直接印出**（§2 `⤷ F-0x [severity] 锚点=… 复现=…`），下一轮从这里下钻
（详见 `注意事项.md` 47 与 `验收标准.md` #51）。

**为什么立这一节**：框架原本只有**正向链**（`REQ → card → T-xx → 用例`），**没有反向链**（`现象 → 代码位置 → 相关卡`）
——于是每次修问题都要**重新全量找文档和代码**，而那正是最贵的一步（实测某工程状态面 185 万 token、活状态 2.8 万，§9.17）。
锚点是**在发现现场顺手落下的坐标**：写发现项的人当时就在那一处，**不落下来，后面每传一手都要重新找一遍**。
（用户原话：真人的思路是按一些需求去排查、每次全量找文档和代码很费时间和 token、先看代码比较快。）

**这一节最容易读反的几处（口语化误解 → 真相）**：

- **"锚点写行号更精确，那就连行号一起校验"（v5.7.0）**：**精确 ≠ 可作判据**——行号会随**任何无关编辑**漂移（在文件头加一行注释就让它全部"悬空"），拿它当判据等于把这条检查做成**假阳性发生器**，而假阳性第三次以后人就开始整体忽略它（§9.17 同款结局）。**只有路径参与校验**（`路径:行` 里剥掉 `:行` 再验路径），**写错行号不会被报是刻意设计、不是漏检**——先例是同行的 aider：`Tag` 的 `line` 只用于渲染，**索引身份用 `file + symbol + kind`**。判断一条字段能不能当判据，问的不是"它准不准"，而是"**它会不会因为无关改动而变**"。

- **"旧格式的机读块解析后两列为空 ⇒ 报没写锚点"（v5.7.0）**：**格式旧 ≠ 内容缺**——5 列旧块补空之后和"真的没写"**完全同形**（这是"空与缺"第 6 次，也是第一次出现在**跨版本**维度）。故解析器保留每行**原始格子数**，列集不符时报**一次整块级** `TC-FINDINGS-FORMAT-STALE`（迁移期可降级）**且与逐行"无锚点"互斥**；**报格式旧时只跳过锚点两条检查**，`owner`/`ref`/`state` 继续查——**为了修一个假阳性而弄丢三条真检测力，那比假阳性更坏**。凡是"新增字段"的迁移，第一问永远是"**这个字段在旧数据里长什么样**"。

- **"修复卡没有 `anchor` 键 ⇒ 判 E"（v5.7.0）**：**"键不存在"与"键在但值为空"必须分开报**——前者是**还没迁移到新模板**（只提示、单列在摘要 §7），后者才是真缺。合成一条 = **任何旧工程在升级当天全部修复卡一起变红**，那不是检出是噪声（同上，噪声第三次以后被整体忽略）。等价判据：**任何新增必填字段，都要先回答"存量数据怎么办"，答案不许是"一起报错"**。

- **"字段加上了、校验写了，这条就落地了"（v5.7.0）**：**只写不印 = 又一个"声明了从不读"**（v5.5.0 假保护的同一形状）——锚点的**全部收益面**在"下一轮能直接下钻"，故 `recall.py` 摘要必须把未闭环发现项的 `锚点/复现` **真的印出来**（本轮新判据 R9：**新增必填字段必须同一次改动里就有消费者**）。检查一个机制是否落地，看的是"**它的输出有没有人读**"，不是"它的校验有没有跑"。

- **"变异用例全绿 + 干净用例全绿 ⇒ 这组断言有判别力"（v5.7.0）**：**反向断言有个结构性风险——检查器压根不存在时它们也全绿**（"永不报警"通过任何 `must_not`）。故本轮的锚点断言额外做了**检查器自身变异**：`python scripts/tests/mutate_recall_checker.py scripts` 把 `recall.py` 改瞎四处（不查锚点路径 / 去掉格式旧闸门 / 抹掉"键缺失 vs 值为空"之分 / 不剥行号），**断言对应变红才算有牙**（4/4 抓住）。这是 §9.17「成对」的**第三边**：①干净用例证不乱拦 ②变异数据证能拦 ③**变异检查器证"能拦"那句不是空话**。

### 9.19 测试用例资产与反 mock 判据（v5.8.0：把「每轮现想用例」变成「攒下来的资产 + 失败驱动增量」）

**判据**：项目有 `project-state/代码/测试/用例库.md`（模板 `代码/测试/用例库模板.md`），机读块 `<!-- machine:cases -->` **7 列**
`id | scope | method | data | anti_mock | source | last`；`CAS-NNN` **全局唯一、只增不减、永不复用**（作废写 `last=retired` **保留行**）；
**`anti_mock` 必填**（四类判据任选组合：独立通道复核 / 负向证据 / 环境指纹 / canary 数据）；
**成本纪律 = 固定回归基线 + 失败驱动增量 + 预算内轮换探索**，方向由项目经理出、用例由测试工程师设计、主控编排；
检查器 `python scripts/case_audit.py <项目根>`（**0 干净 / 1 有 ERROR / 2 无法检查，不是没问题**），`--hotspots` 给热区
（详见 `注意事项.md` 48 与 `验收标准.md` #52）。

**为什么立这一节**：改之前测试工程师的用例**是每轮现推的**——skill §2 把卡片「验收标准」反推成黑盒操作清单，
**同一份 AC + 同一份契约 ⇒ 同一份清单**，所以"每轮都一样"是机制决定的、不是人不认真；
而**想要不一样就得每轮重想一遍 = 烧 token 且丢掉上轮判据**。另一头，验收断言只查"期望的响应出现了"，
**没有一条判据问"这个响应是不是真来自系统"**——前端 mock 层、伪造响应、缓存、假接口都能让它通过。
用户的三个诉求（不够全 / 被 mock 骗 / 换新用例烧 token）**是同一个根因的两面**：**没把判据攒成资产，也没给资产配"反伪造"这一维**。

**这一节最容易读反的几处（口语化误解 → 真相）**：

- **"用例全绿 = 测过了"（v5.8.0）**：**检查器只判「填得对」，不判「测得全」**——`case_audit.py` 核的是字段齐全、编号唯一、指针存在；**覆盖方向是人的决定**（PM 出方向、主控排范围），机器判不了。报告里把"0 ERROR"写成"质量已保证"即不合格（同 §9.17 的加冕教训）。**"没有用例库"报退出码 2 并明写"无法检查，不是没问题"**——把 2 读成"干净"是本条最贵的一种读反。

- **"反 mock 判据写得短 ⇒ 判它不合格"（v5.8.0）**：**机器只查「有没有」，不查「够不够强」**——`直查库` 三个字与一整套通道复核**同样放行**。判别强度是**测试设计判断**，把它塞进机器 = 又一个假阳性发生器（同 §9.18 行号、§9.17 同款结局）。提强度要用**人的**手段：PM 在复盘里问"这条为什么上次没抓到"、把同类发现项并成热区（`--hotspots`）。

- **"格式旧 ⇒ 内容缺"（v5.8.0）**：**列集不是 7 列时整块只报一次 `CASES-FORMAT-STALE`，且不许同时报「anti_mock 缺 / last 缺」**——旧 5 列块补空之后与"真的没写"完全同形（"空与缺"第 7 次）。**报格式旧时只跳过新增列的检查**，`source`/`last`/指针继续查；迁移期 `--allow-unmigrated` 降级为 WARN、不阻断。

- **"每轮换新用例才叫测得全"（v5.8.0）**：**恰好相反**——**每轮全新 = 把上轮的判据全丢掉**（回归价值归零），而且烧 token（用户第三个诉求正是这个）。纪律是**固定回归基线 + 失败驱动增量**：先跑老用例，再按**发现项 / 用户反馈 / 探索**新增；**"每轮原样重复"同样不合格**（不测新风险）。**这条纪律必须同时挡住两头**——只写"不许重复"会退化成每轮重造，只写"不许全新"会退化成不测新风险。

- **"新增的机读字段只要写进模板就落地了"（v5.8.0）**：**没有消费者的字段 = 没有**（判据 R9）——`anti_mock` 列若不是**被 `--hotspots` 与前置检查第 18 项真的读**，它就只是表格里多一列；`last` 列也只有"下一轮真的照着回填、并先跑基线"才有意义。**检查一个字段是否落地，看它的输出有没有人读**，不是看它有没有被校验（§9.18 同款）。

### 9.20 单轮测试量档位（v5.9.0：把「每轮都全量」变成「用途定档位，省的账要写在纸上」）

**判据**：每张测试卡 `tc.md` 的 frontmatter 声明三键——`test_depth`（`full` / `targeted` / `smoke`）、`delivery_use`（`deliverable` / `demo` / `internal`）、`depth_note`（非 `full` 必填：这一轮**不测什么** + 依据）；
**交付包/对外（`deliverable`）与上线前一轮（`cadence_round` 以 `ship` 开头）必须 `full`**；
非全量档**必须同时有** `depth_note` 与 `not_doing`（省下来的面必须写在纸上）；连续 ≥3 张 `smoke` 报 WARN（冒烟是例外不是常态）；
检查器 `python scripts/test_scope_audit.py <项目根>`（**0 干净 / 1 有 ERROR / 2 无法检查，不是没问题**），报告同时印**档位分布**（详见 `注意事项.md` 49 与 `验收标准.md` #53）。

**为什么立这一节**：v5.9.0 之前框架里**只有"多久开一轮"的节拍**（`config.json` 的 `test_card_cadence`），而**"这一轮测多少"没有任何字段承载**——于是"每轮全量"不是谁的决定，而是**没有字段就没人需要做那个决定**的默认结果（测试卡模板的 `not_doing` 不填不报错，等于没有）。用户的诉求正是这一处：**交付包当然要全量，但"修了个小功能给用户看一眼"不必全量**；省钱不能靠自觉，得**有字段 + 有人定 + 有判据拦**。

**这一节最容易读反的几处（口语化误解 → 真相）**：

- **"调低测试卡密度就等于少测了"（v5.9.0）**：**频度与单轮范围是两件事**——`test_card_cadence` 管"多久开一轮"（改它**不**改变单轮测多少），`test_depth` 管"这一轮测多少"。只调频度而每轮仍全量，**总测试量并没有按预想下降**；两条要分开谈、分别留痕。

- **"定了定向档，所以这轮只测受影响面"（v5.9.0）**：**机器只核"声明得对"，核不了"执行是否真按档"**——`test_scope_audit.py` 判的是字段齐备与不自相矛盾（交付包必须全量、非全量必须有"不测什么"），**判不了"定向档是不是真的只测了受影响面"**（同 §9.19 的"机器核不了用例真跑过"）。影响面判断与"能不能省"永远是人定的。

- **"`demo` 用途定了 `full` ⇒ 报过测"（v5.9.0）**：**保守选择允许**——宁可多测不可少测，`demo` 定 `full` **不报错**。机器不替人做"这轮可以省"的判断；**把多测也报成错 = 假阳性发生器**（同 §9.18 行号、§9.19 反 mock 强度）。

### 9.21 宿主工具口径（v5.10.0：把「某个宿主的能力」变成「按宿主分支的一条纪律」）

**判据**：本批凡涉及浏览器 / 移动端 / 网页验证的卡，证据里写清**宿主与所用工具**——**ZCode 宿主**＝内置安卓模拟器/ios-simulator 插件 + Browser Use；**dsh 宿主**＝**BrowserSkill**（`browser_*` 工具族）+ 上传 `bsk upload`；**两种宿主都不许自行拉起浏览器/模拟器进程**（`chrome --remote-debugging-port` / Playwright / Selenium / `emulator.exe`——批处理脚本除外且必须用持久 profile），命令行兜底须写明原因，框架脚本一律 `python -X utf8`；**口径本体只在 `agent.md` 任务执行纪律 17 一处**，角色 SKILL 只引用、不复写工具名（详见 `注意事项.md` 50 与 `验收标准.md` #54）。

**为什么立这一节**：v5.10.0 之前框架把"宿主"当成 ZCode——纪律 17 写死"验证工具优先用 ZCode 内置能力"，测试/前端/后端/运维/UI 五个角色 SKILL 各抄了同一句。**一句宿主专属指令被抄进 N 个文件，换个宿主整句失效、改一处漏 N 处**（用户 2026-09-28 的「增加 dsh 使用」正照到这一处）；同一版还把 v5.8.0/v5.9.0 只落在 dsh 副本的 18 个文件同步进 ZCode 副本，两份副本恢复**内容级**一致。

**这一节最容易读反的几处（口语化误解 → 真相）**：

- **"框架支持 ZCode，也没说不支持 dsh"（v5.10.0）**：**没写 ≠ 可用**——纪律 17 当时**只写了 ZCode 分支**，照做的人会把 dsh 上不存在的插件名当成可用工具。**"宿主能力"不是"某个宿主的能力"**：写纪律前先问一句"换宿主这句还成立吗"，不成立就写成分支。

- **"两份副本已经一致了，所以不用管了"（v5.10.0）**：**"一致"是当时的一致**——同一 git 仓库的两份工作副本（`大型项目开发框架\` / `dsh代码开发智能体\`）**改一处必须两侧同改**，漏一侧就是又一份分叉（v5.8.0/v5.9.0 就是这么分叉的）；且"一致"只到**文件级对拍**，两侧 `tmp\`、`__pycache__\` 产物未清。

- **"验收第 20 项过了 ⇒ 确实没偷偷起浏览器"（v5.10.0）**：**机器核不了"有没有起进程"**——本项靠证据自述 + 主控抽查，**证据没写用哪套工具 = 未收口，不等于"没做过"**（同 §9.19"机器核不了用例真跑过"）；**不为此新增检查器**（硬塞进脚本 = 假阳性发生器）。


### 9.22 浏览器资源取用与归还（v5.11.0）

**判据**：本批凡使用了宿主内置浏览器/模拟器的卡与测试卡，正文必须有 `machine:browser` 机读块（**七列**：`id | card | session | tabs | take | return | evidence`；`BRW-NNN` 全局唯一且升序；**"开"与"关"写在同一行**），frontmatter 有 `browser_tab_cap`（**项目经理给的预算**，默认 3）；`return` 空 = 未归还；`tabs` 超预算、跨卡独占时段重叠、声明了浏览器取证却无机读块，均为 ERROR；证据指针必须真实存在。检查器 `python scripts/browser_resource_audit.py <项目根>`：**0 = 干净 / 1 = 有 ERROR / 2 = 项目里没有任何卡 = "无法检查"，不是"没问题"**。共享实例的独占时段分配与强制清场归**集成工程师**（`skills/集成工程师/SKILL.md` §8），预算归**项目经理**（§20），取用与归还登记归**使用者自己**（`agent.md` 纪律 17 ④），SOP 骨架 `project-state/契约/浏览器资源调度规程模板.md`。

**为什么立这一节**：v5.10.0 已经把"用哪套工具"写清楚了（ZCode / dsh 两套口径，纪律 17），但**框架里没有任何一处管"开了几个、还了没有"**——"开启浏览器"是产出物上的一行，"关闭"不是，于是 **GO 了的卡会把会话留在后台**，下一轮再取用时撞上一个已经被拖垮的实例（真实工程 2026-09-29 的事故：三名队友并行起会话、各开 7~15 个 tab，扩展被拖垮，整批取证作废，只能全局停火重派）。**根因不是纪律不严，是"还"这件事没有字段承接**——没有字段的纪律，在收口时看不见。

**最容易读反的几处**：
- **"卡 GO 了，浏览器当然已经关了"（v5.11.0）**：**GO 只说产出合格，不含资源归还**——`return` 空着就是遗留资源，检查器报 ERROR。这一条与 §9.21 的方向相反：那一条是**做过没写**不算数，这一条是**没写就不算还**。
- **"预算没写在卡上，但大家都知道是 3 个 tab"（v5.11.0）**：**默认值 ≠ 有人批过**——`browser_tab_cap` 不写进 frontmatter 就只是检查器的兜底，没有人在这一卡上做过"批多少"的决定；检查器记 WARN 而不是 ERROR，正是因为**它只能指出"这个决定没落纸"，判不了该不该批**。
- **"退出码 2 = 没问题"（v5.11.0）**：**2 = 项目里没有任何卡 = 无法检查**——与 §9.19/§9.20 同一条读法；把"没查到"念成"没问题"就是新的假保护。


### 9.23 极速修复模式与模式播报（v5.12.0；v5.12.1 补「排查依据」与「客户体验包」：用户点名的临时快档，不是第三个项目档位）

**判据**：极速修复模式（`turbo-repair`）**只在用户点名时进入**（`极速` / `极速修复` / `极速修复模式` / `快速解决`，或明确说「别建卡、别派子代理、直接改」）；进入后**主控内联执行、不派子代理、不建需求卡/测试卡**，测试只做 `smoke` / `targeted`（复用 `test_depth` 取值）；**一轮一行**记入 `project-state/问题/极速修复台账.md` 的 `machine:turbo` 机读块（**v5.12.1 增至 12 列**：`id | at | source | basis | symptom | files | depth | evidence | pack | exit | exit_reason | verified`——`basis` 空 = ERROR（形状不符记 WARN）、`pack` 空 = ERROR（`-` = 本轮不涉及交付面；路径不存在记 WARN）；`TRB-NNN` 全局唯一升序；`exit` 与 `exit_reason` **成对**——都空 = 仍在极速中、一空一满 = ERROR；`files ≥4` 未退、同一 `symptom` ≥3 行未退、`depth=full` 均为 ERROR）；**硬退出线 X1~X6**（一次改动 ≥4 文件 / 触及契约·接口·数据模型·权限·敏感数据·生产·迁移 / 同一问题连续 3 轮未好 / 发现面超预期 / 用户改口 / **正式交付包·对外件·上线前一轮**——**面向客户的快速体验包不在此列**，但须写 `pack` 并在包里写明"哪些面只做了冒烟、未独立验证"）；极速轮次 `verified` 常态为 `否`，**不得置卡 `done`、不得作为 ⑥ 第 22 项通过的凭据**；检查器 `python scripts/framework_lint.py <项目根>` 的 **K 组**核台账自洽——**没有台账 = 本项目没用过极速修复，记 INFO 跳过**（不是 ERROR，也不是"无法检查"），**有台账却没机读块 / 写得不自洽 = ERROR**。**模式播报（纪律 29）**：每次开工与每次切档的**首行**给一行固定格式横幅（模式名 + slug + 依据 + 叠加或裁剪声明 + 测试档位），**三个档位名固定**：完整模式 `full` / 快速模式 `quick`（默认档）/ 探索模式 `explore`（v5.25.0 立档、v5.27.0 卡驱动闭环）；**叠加层名固定**：极速修复模式 `turbo-repair`（临时叠加），且 **`config.json` 的 `mode` 认 `quick` / `full` / `explore`**（详见 `注意事项.md` 53 与 `验收标准.md` #56）。

**为什么立这一节**：`quick` 已是默认档，但它省的是**角色数与文档深度**——**建卡（"卡是驱动单位"）、派子代理（纪律 22）、按档收口测试**这三件事，在「改一行文案」与「改一个模块」上付**同一个固定成本**，用户 2026-09-30 说的"连续调好几次看效果"正撞在这一处。而「这个改动看起来很小」**不能由执行者自判**——判断权与受益权在同一个人手里（方法级判据 R17），所以快档的**入口留在被服务的人手里**、**出口是硬线**（≥4 文件 / 不可逆面 / 3 轮未好 / 交付与上线）。**v5.12.1 补两条**：① 快档省的是**记账动作**（建卡、派子代理、留痕），**不是判断的出处**——用户澄清「极速修复**也是要根据客户的反馈和正常开发形成的需求卡测试卡等进行排查和修复的**，并不是直接丢给大模型」，所以台账要有 **`basis`**（依据哪张卡/哪条用例）与判据 **R18**；② 本模式的典型用途正是**给客户快速体验 + 小功能变更**，于是"交付面"要显式区分**体验包**（正当、须登记 `pack`、须写明哪些面只做了冒烟）与**正式交付包**（仍出局）——**区别不在产物大小，在承诺**。

**最容易读反的几处**：

- **"极速修复是第三个项目档位"（v5.12.0）**：**不是**——它是**叠加在项目档位之上的临时模式**：一个 `full` 项目也可以被点一次名做极速修复；**不写 `mode`、不做升降级留痕**，退出后回原档位。把三态塞进 `mode` 会让"项目档位"与"这一轮怎么干"锁死，一处漂移全盘误判。

- **"极速下省掉的测试，后面想起来再补"（v5.12.0）**：**省下的测试不得当成"已经测过"**——这是本模式最容易出的假保护（冒烟过了就当回归过了）。退出极速后**已改的代码不推倒**，补建卡与证据、按档补跑；极速轮次下**实现与自检是同一双手**（创建者≠验证者被打破），所以 `verified` 必须显式写"否"、不许宣称已验收。

- **"项目里极速台账是空的 ⇒ 没问题"（v5.12.0）**：**空 ≠ 干净，只 = 没用过**——K 组记 **INFO 跳过**（不是 ERROR，也不是"无法检查"，同 §9.19/§9.20/§9.22 的读法）；**有台账却没写机读块 / 写得不自洽 = 用过却没留下可核的账 = ERROR**。**机器也核不了"这一轮到底派没派子代理、有没有真的只跑冒烟"**——那靠台账自述 + 主控抽查，证据没写 = 未收口（同 §9.21）。

- **"极速 = 直接把问题丢给模型"（v5.12.1）**：**不是**——省的是**派子代理与建新卡**，**不是省排查依据**：`basis` 必须指向既有**需求卡（`anchor`/`entry`/AC）/ 测试卡（覆盖矩阵、发现项 7 列）/ 用例库 `CAS-NNN` / 相关契约**（冷启动先跑 `recall.py`；确无对应卡的新小变更才写 `no-card`），**`basis` 空着就动手 = 乱改 = 不合格**（判据 R18：省流程 ≠ 省依据）。

- **"产物看起来不大，就直接发给客户当交付包"（v5.12.1）**：**不是**——本模式的目标场景**恰恰**是"给客户快速体验 + 小功能变更"，所以**体验包是正当产物**，但它与**正式交付包**的区别是**承诺**：体验包可以说"看效果"（`pack` 列登记 + 包内写明"哪些面只做了冒烟·未独立验证"），**`delivery_use=deliverable`、承诺可用与上线前一轮仍必须 `full`**（X6 不变）。


### 9.24 先例复用评估（v5.13.0：开工初期把"隔壁做过了"变成必须落盘的判定，而不是靠想起来）

**判据**：项目开工初期（**建第一张需求卡之前**）必须做过一次**先例复用评估**——项目经理问用户历史项目根并把答案写进 `project-state/config.json` 的 **`reuse_roots`**（**缺这一键 = ERROR `REUSE-ROOTS-MISSING`，"没问过用户"≠"没有历史项目"**；用户确认无历史项目时写**显式 `[]`** 记 INFO 并在计划里注明依据；声明的根在本机不存在只记 **WARN `REUSE-ROOT-MISSING`**，**不得读成"没有历史项目"**）→ 跑**只读**扫描器 `python -X utf8 scripts/reuse_scan.py <项目根>`（列历史项目的需求卡 / 测试卡 / 契约 / 用例库 / 组件 / 代码模块 / 项目自建脚本候选，用**字符 n-gram 加权重合度**排序；`--write` 另写人读报告 `project-state/复用盘点-<YYYYMMDD>.md`，**不覆盖同名**）→ 判定逐条落 `project-state/记忆/复用台账.md` 的 `<!-- machine:reuse -->` 机读块 **8 列**（`id | date | source_project | source_ref | kind | verdict | target | evidence`，`RU-NNN` 全局唯一升序、只增不改；`reuse`/`adapt` 的 `target` 不得写 `-`、`evidence` 不得空、字段内不得含 `|`）→ 每张需求卡 frontmatter 回填 **`reuse`**（`new`/`reuse`/`adapt`）与 **`reuse_ref`**（`RU-NNN` 或 `-`），且**卡的 `reuse` 必须与所引台账行的 `verdict` 一致**（不一致、或 `reuse: new` 却写了 `RU-NNN` → ERROR `REUSE-CARD-LEDGER-MISMATCH`）。检查器 `python -X utf8 scripts/reuse_scan.py <项目根> --check`：**退出码 0** 才算过，**1 = 有 ERROR，2 = 无法检查（项目根不对 / 缺 config）＝不是"没问题"**（发现项码：`REUSE-ROOTS-MISSING` / `REUSE-LEDGER-HEADER` / `REUSE-LEDGER-ID` / `REUSE-LEDGER-ROW` / `REUSE-CARD-FIELD-VALUE` / `REUSE-CARD-REF-DANGLING` / `REUSE-CARD-LEDGER-MISMATCH` 为 ERROR；`REUSE-LEDGER-MISSING` / `REUSE-CARD-FIELD-MISSING` / `REUSE-ROOT-MISSING` / `REUSE-ROOT-NO-PROJECT` 为 WARN；`REUSE-ROOTS-EMPTY` / `REUSE-SELF-ROOT` 为 INFO）。三角色产出缺一即未收口：项目经理 §22（净收益对比「复用 vs 重造」）、产品经理 §14（`思路/产品经理/盘点-先例复用.md`）、架构师 §13（`思路/架构师/盘点-先例复用.md`）——对应 `R-pmgr-75` / `R-pm-27` / `R-arch-46`。**扫描全为只读**：历史项目一个字节都不改；**搬运资产由主控显式搬运并在 `记忆/决策日志.md` 登记来源**，跨项目写入方向仍禁（`agent.md` 统一路径管理第 3 条不变）。（详见 `注意事项.md` 54 与 `验收标准.md` #57。）

**为什么立这一节**：框架此前只有**跨项目隔离的禁令**（「A 项目的角色/子代理禁止读写 B 项目根」——防串味，本身是对的），**却没有任何"跨项目复用"的通道**：没有字段、没有入口、没有角色职责要求"开工前先看看隔壁做过什么"。于是**"重新造"不是谁的决定，而是没有字段就没人需要做那个决定的默认结果**；而历史项目的需求卡、测试卡、契约与代码**本来就是为被复用而留的**（NAS `\\nas\work` 下六个本范式工程），不用等于白留。用户 2026-10-09 提「开发项目工作之间相互借鉴的部分不够……更多考虑需求卡或者代码复用而非重新开发」，正是要把这件事从**主控临时想起来**变成**开工前必须落盘的判定**。**方法级判据 R19**：**一条纪律如果只有禁令、没有通道，它就会把自己变成"禁止借鉴"**——凡是"该做而没人做"的事，几乎都能在一分钟里找到"**它没有任何字段承接**"这个根因（同 R16 一脉）；**要让复用真的发生，得给判定一个字段、给扫描一个命令、给角色一条职责、给不一致一个报错码，四样缺一，"借鉴"就只是手册里的良好愿望**——**判断一个机制是真的在跑还是只是被写着，看的不是有没有"鼓励复用"的话，而是"不复用"要不要签字（`verdict` + `evidence`）**。

**最容易读反的几处**：

- **"用户没提历史项目 ⇒ 就是没有历史项目"（v5.13.0）**：**不是**——`reuse_roots` 缺键报 **ERROR**（"**没问过**"与"**没有**"是两件事，同通用铁律②"查不到"≠"查过且干净"）；只有**用户确认后写显式 `[]`** 才算"确实没有"，且要在《项目计划》/《主控工作计划》注明依据；**声明的根在本机不存在只记 WARN**（NAS 可能没挂上），**不得**读成"没有历史项目"。

- **"`reject` 就是什么都不填"（v5.13.0）**：**不是**——**不复用是一个决定，不是省略**：`reject` 行的 `evidence` 必须写清为什么不划算（契约不兼容 / 适配成本 > 重做 / 技术栈不同 / 质量不达标），**"没想到"不是依据**；`reuse`/`adapt` 必须有 `target` 落点且 `evidence` 写出真实来源路径（悬空 = **假证据**，同 §9.17 锚点纪律：只有路径部分参与机核、行号不核）。

- **"台账判 reuse、卡上写 new 只是笔误"（v5.13.0）**：**不是**——**口径必须唯一**：先有台账行、后有卡字段，不一致报 `REUSE-CARD-LEDGER-MISMATCH`（含 `reuse: new` 却写 `RU-NNN`）。两处说法不一样，**下一个项目读到的就是假账**。

- **"相似度分数高 ⇒ 该复用"（v5.13.0）**：**不是**——分数只是**字符 n-gram 重合度**，用于**排序线索**，**不做语义理解**；"分数高"≠"该复用"（还得过净收益与契约兼容判断），**"没扫到"≠"没做过"**（历史项目可能没按本范式留痕、可能不在声明的根里）。**复用率不是 KPI**：判据是**净收益 > 0**，为好看的复用率硬套不兼容的旧契约比新造更贵。

- **"顺手把 GitHub 开源项目也扫进来"（v5.13.0）**：**不是本版范围**——本版**只做"同范式历史项目"**（用户明说第二件事"可以放一放"）；**开源社区检索是第二期**，要开就按新机制立项（新检查号 + 新脚本 + 新列义），**本期不留半成品代码、不许顺手夹带**。



### 9.25 方案视图区（v5.16.0：给"给人看的那一版"一个固定位置，同时不制造第二真源）

**判据**：完整模式项目根有 `方案/` 与 `原始资料/`、`产品稿/`、`原型图/` 三子目录及 `方案/README.md` 索引；`方案/产品稿/`、`方案/原型图/` 的导出件都标 `导出日期：YYYY-MM-DD` 与 `源路径：…`；客户原始文件唯一归档到 `方案/原始资料/` 并逐行登记 `清单.md`；对外正式件仍走 `交付/` + `发出记录.md`；`方案/` 根层无游离文件；检查器 `python -X utf8 scripts/solution_audit.py <项目根>` 退出码 0（**1 = 有 ERROR；2 = 快速模式未建 / 无法检查，不是"没问题"**）。责任分工：项目经理建与维护（`R-pmgr-81/82`）、产品经理导出产品稿（`R-pm-29`）、UI设计师导出原型图（`R-ui-31/32`）；老项目用 `python -X utf8 scripts/migrate.py --apply --only solution-area` 补建（幂等、只建不改）。

**为什么立这一节**：真源（PRD、prototype.spec.json、designs/*.html）是**给角色和机器读的**，它们住在 `project-state/契约/` 深处是对的；但用户与客户要的是**"打开就能看的那一版"**，而这个需求此前没有位置承接——于是每次看都要临时导出、发微信、截图，**看过的那一版下次找不到**；客户给的方案原件也常散在根目录与聊天记录里，**收到了没登记、登记了没消化**。本节把"给人看"和"给机器读"分开：**视图可以有第二份，事实源不许有第二个**。方法级判据 R21（v5.16.0）：**凡是"用户随时要看"的东西，都必须有一个固定位置；凡是这个位置上的文件，都必须能指出它的真源在哪**——没有固定位置，用户就得反复问；没有真源指针，视图就会悄悄变成"唯一版本"，改完谁都不知道该信哪个。

**最容易读反的几处**：

- **"`方案/` 里的是正本，以后改这里"（v5.16.0）**：**不是**——`方案/产品稿`、`方案/原型图` 是**导出视图**，可覆盖重生成；正文只改真源（`契约/产品需求文档.md`、`契约/UI资源/`），导出件必须带 `导出日期` 与 `源路径`。在 `方案/` 里直接改正文 = 造第二真源，下一个读的人会拿到一份对不上契约的稿子。

- **"目录建了，用户就随时能看到了"（v5.16.0）**：**不是**——建目录只解决"有地方放"，**"看得到"要靠关卡与验收现场展示**（【关卡①】刷产品稿、【关卡③/④】刷原型图、收口更新 `方案/README.md` 索引与最后刷新行）；检查器也核不了"人有没有真看到"，报告不得把"目录齐"写成"用户已看过"。

- **"原始资料消化完就可以删了"（v5.16.0）**：**不是**——`原始资料/` **只进不改**，消化进契约时写**指针**（路径 + 消化到哪个 REQ）；删原件的后果是"契约里说的依据找不到了"，与 #59 的"证据指针必须真实存在"同一条读法。

- **"快速模式没建 `方案/` 就是不合格"（v5.16.0）**：**不是**——快速模式按需建，未建记 INFO、检查器退出码 **2 = 无法检查**（同 §9.19/§9.20/§9.22 的读法），**不是失败、也不是通过**；但一旦建了，台账与标注判据照此节执行。

- **"`方案/` 建在根上，顺手把交付件也放进去发给客户"（v5.16.0）**：**不是**——`方案/` 是**内部人读视图**；对外正式件仍按 2.2 判定走 `交付/`，并发 `发出记录.md` 登记。把内部视图当交付通道，等于把"未收口的稿子"直接推到客户面前。
