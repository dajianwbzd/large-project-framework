# Git 工作流（版本控制治理）

> 运维工程师产出并维护（项目初始化时建立，**首次接入版本控制前先定档**；此后随仓库/分支模型变更更新）。
> **L0 摘要**：本项目用哪个仓库（云效 Codeup）、默认分支叫什么、分支怎么命名、提交怎么写、谁合并、冲突怎么裁、错了怎么退、卡与提交怎么对账——一份文件回答完，并用脚本机检。
> **判据可机器核验**：§7 的机读块被 `scripts/git_audit.py` 直读；本文件里的人读条款与机读块是**同一套判据的两种写法**，改条款要同步改机读块（改完跑一次脚本自证）。

## 治什么问题（真实教训，不是假想）

| # | 真实问题 | 后果（已发生/极易发生） |
|---|---|---|
| 1 | 项目代码**没有版本控制**（真实案例：某项目跑了 30+ 张卡、两个代码库，至今不是 git 仓库） | 一次脚本误操作把某角色的进度 JSON **永久覆盖、无法恢复**——没有历史可回滚、没有提交可追责"谁改的"、没有分支可隔离实验 |
| 2 | 多角色并行改同一仓库，**无分支纪律**，靠"分区写入"侥幸避让 | 两人改同一文件必撞；撞了没有归属规则，谁先改谁倒霉 |
| 3 | 合并冲突**没有归属与裁决人** | 冲突靠"一把梭取一边"草率解决，把别人的修复静默冲掉（见 §4.5 反例） |
| 4 | 提交信息与卡片/证据**脱节** | 验收时不知道这张卡对应哪个 commit，回退不知道回退到哪 |

> 本契约与既有纪律的关系：`agent.md`「任务执行纪律 9（Git 纪律）」是**底线**（原子提交/提交前卫生/主干可部署），本契约是它的**可执行细化**（分支模型 + 冲突归属 + 机检脚本）；路径侧纪律见 `契约/环境.md` 与 `scripts/path_audit.py`，二者在"批次收口"同点位执行。

## §0 项目定档区（项目初始化时填，未定档不得开工）

| 定档项 | 取值 | 说明 |
|---|---|---|
| 仓库类型 | **云效 Codeup 新建仓库**（用户 2026-09-10 定） | 不做 GitHub/Gitee 备选；已有远端须在"例外说明"里写清理由 |
| 远端地址 | `git@codeup.aliyun.com:<组织ID>/<代码库路径>.git` | SSH 形态；本机 SSH key 已可用（框架仓库实测同形态） |
| 默认分支名 | **`master`**（二选一**写死**，不许 master/main 混用） | 同项目内所有代码库统一；改则改 §7 机读块的 `default_branch` |
| 保护分支 | `master`（**只接受合并，禁止直推**） | 服务端设置，见 §1.1 第 6 步；本地替代纪律见 §2.3 |
| 代码根 ↔ 仓库 | **一个代码根的每个代码库各自一个仓库** | 代码根从 `project-state/config.json` 的 `paths.repos` 解析（本项目：`<填 repos/xxx>`），**不凭记忆猜** |
| 负责人 | **运维工程师**（默认），建仓/远端/.gitignore/保护分支/首次推送全归其职责 | 主控在《主控工作计划》里把"项目接入"排成运维的第一张卡（§1 硬动作） |
| 契约责任人 | 运维工程师维护本文件，主控在批次收口核对执行情况 | 「登记 ≠ 归位」同理：定档了没执行 = 没定档 |

**定档即判据**：`git_audit.py` 的检查 ②③⑥⑦⑧ 全部以本区与 §7 机读块为准（默认分支/分支正则/提交正则/敏感词/大文件阈值/未合并分支过期天数）；定档项留空 = 脚本只能回退内置默认（不报错，但结论只作参考——**内置默认不是本项目的决定**）。

## §1 新项目接入（硬动作，缺此项不得开工）

**为什么是硬动作**：框架其余全部纪律（回滚、追责、隔离、验收证据指向 commit）都建立在"代码在版本控制里"之上；没有仓库时它们全是空转。真实项目实测：跑 30+ 张卡不建仓，等到出事才发现"没有可回退的过去"。

### 1.1 云效 Codeup 建仓（网页，运维工程师执行）

| 步 | 动作 | 关键选择与理由 |
|---|---|---|
| 1 | 打开 `https://codeup.aliyun.com` 并登录（阿里云账号） | 与框架仓库同一账号体系 |
| 2 | 顶部「代码管理」→「代码库」→ 右上「新建代码库」 | — |
| 3 | 填**代码库名称**（中文可读）+ **代码库路径**（英文/数字，进 URL） | 一个代码根一个库，名字带项目前缀便于辨认 |
| 4 | **可见性：私有** | 项目代码默认私有；"组织内公开"仅在用户明确要求时选 |
| 5 | **初始化设置：全部不勾**（不勾 README / 不勾 .gitignore 模板） | 勾了会在远端产生一条你本地**没有**的初始提交，首次推送会变成"非快进"而被迫 rebase——省这一步 |
| 6 | 创建后进「设置 → 分支设置 / 保护分支」：对 `master` 开启**禁止直接推送** + 合并请求需评审 | 这是**服务端硬闸门**（本地纪律可绕过，服务端不能）；本地脚本看不到这条，必须在网页核对 |
| 7 | 「设置 → 成员」把协作账号加为**开发者**（推分支/提 MR）；管理员只给运维 | 权限最小化：能推分支 ≠ 能直推保护分支 |

权限与凭据：SSH 走 `ssh -T git@codeup.aliyun.com` 自检（返回欢迎语即通）；HTTPS 走个人访问令牌。凭据**不写进仓库**（`.env` 不入库，见 1.4）。

### 1.2 本地接入七步（每步附命令）

```bash
# 1) 定位代码根（从 config.json 的 paths.repos 取，别猜）
cd <代码根>                                   # 例：repos/workbench

# 2) 初始化，默认分支名与 §0 定档一致
git init -b master                            # git ≥2.28 支持 -b；本机 git 2.55 实测可用

# 3) 落 .gitignore 基线（内容见 1.4），必须在首次 add 之前

# 4) 先看一遍"将要入库的东西"（这一步是第 5 条的防线，不可省）
git add -A && git status --short              # 逐行确认：无 .env / 无 *.key / 无 >10MB 文件

# 5) 首次提交（**也要带卡号**——先建“项目初始化”卡，一卡一分支纪律从第一天开始）
git commit -m "chore(init): 初始化 <项目名> 代码库骨架 [card-001]"

# 6) 接远端（§1.1 建库时页面上给的 SSH 地址）
git remote add origin git@codeup.aliyun.com:<组织ID>/<代码库路径>.git

# 7) 首推并建立跟踪关系
git push -u origin master
```

### 1.3 校验命令（三条全绿才算"接入完成"，结果落盘为证据）

| 校验 | 命令 | 期望 |
|---|---|---|
| 远端配置 | `git remote -v` | 两行（fetch/push）且地址为云效 |
| 首提交 | `git log --oneline -1` | 有且信息合规：`chore(init): … [card-001]` |
| 推送成功 | `git push -u origin master` + `git ls-remote --heads origin` | 推成功；远端列出 `refs/heads/master` |
| 一键复核 | `python scripts/git_audit.py <代码根>` | 无「GIT-001 未接入版本控制」「GIT-002 无远端」类 finding |

### 1.4 `.gitignore` 基线（缺一项都算未接入完成）

```gitignore
# 密钥与本地配置（永不入库）
.env
.env.*
!.env.example
*.key
*.pem
*.p12

# 运行期数据与临时区（v3.18.0 六域：data/ 与 tmp/ 不进仓库）
data/
tmp/
*.log

# 依赖与构建产物（可再生，不入库）
node_modules/
__pycache__/
*.pyc
build/
dist/
产物/
```

> `.env.example`（模板、无真实值）**必须入库**：环境变量清单靠它传递（对齐 `契约/环境.md` 与 `契约/配置中心.md`）。

### 1.5 密钥扫描（入库前与收口时各跑一次）

```bash
git grep -nE "(api[_-]?key|secret|password|passwd|sk-)" --cached      # 扫**已暂存/已入库**内容
git ls-files | grep -E "(^|/)\.env$|\.key$|\.pem$|id_rsa"             # 扫文件名单
```

判读：命中的**不一定是真凭据**（变量名、文档说明、示例值都会命中）——逐条判定；真凭据按 §5.3 处置（**先轮换再谈改历史**）；判定为"变量名/示例"的放过要留《忽略决策记录》（`问题/审核记录.md`），**命中但忽略必须留记录**。

### 1.6 大文件判断（>10MB 走 Git LFS 或移出仓库）

```bash
git ls-tree -r -l HEAD | sort -k4 -nr | head -20     # 已入库体积 Top20（第 4 列 = 字节数）
git ls-files -z | xargs -0 du -k | sort -nr | head -20   # 工作区体积 Top20（KB）
git count-objects -vH                                # 仓库总占用
```

处置二选一：① Git LFS（`.gitattributes` 写 `*.<ext> filter=lfs`，成员需装 git-lfs）；② **移出仓库**——大文件放 `产物/` 或外部存储，仓库只留生成脚本/下载指针（推荐，零依赖）。已入库的大文件改 LFS **需要重写历史**（`git lfs migrate import --above=10MB`），先与团队约窗口期。

### 1.7 反例表

| 反例 | 真相 |
|---|---|
| "先在本地写代码，建仓回头再说" | 回头的代价是**没有历史**：覆盖/误删不可恢复，追责无据（真实案例已发生）。建仓是最便宜的保险，5 分钟的事 |
| "勾了 README 初始化，反正内容一样" | 远端多一条本地没有的提交 → 首推被拒（非快进）→ 新手此时常 `--force` 把远端的删掉。空库创建最省事 |
| "`.env` 我删掉再提交就行了" | 删文件 ≠ 删历史：老提交里还在。密钥一旦入库按 §5.3 走（轮换优先） |
| "项目根建一个仓库把所有东西一起管" | 框架是**一项目根多代码库**：每个代码根各自一个仓库，否则回滚粒度、权限粒度、CI 触发全都混在一起 |
| "远端地址随手填个 GitHub" | §0 定档为云效（用户定），换远端须用户确认并改 §0，不许悄悄换 |

## §2 分支模型（一卡一分支，分支名与卡号强绑定）

### 2.1 五种分支

| 分支 | 用途 | 命名 | 归属人 | 生命周期 |
|---|---|---|---|---|
| `master` | **保护分支**：只接受合并，始终保持可运行 | 固定名 | 运维（设置保护）/ 集成（合并执行） | 永久 |
| `feat/card-NNN-<slug>` | 新功能（绝大多数开发卡） | 卡号 + 短描述 | **= 卡片 assignee** | 建 → 推 → 合并 → **删** |
| `fix/card-NNN-<slug>` | 缺陷修复（卡级 Bug / 验收打回） | 同上 | = 卡片 assignee | 同上 |
| `hotfix/<事故号>-<slug>` | 生产急修（绕过常规排期） | 事故号 + 短描述 | 运维指定 + 主控确认 | 直出 `master` 后**必须回合并到开发线** |
| `chore/<主题>` | 无卡的基础设施杂活（CI 配置、脚本、.gitignore） | 主题短描述 | 发起角色 | 建 → 推 → 合并 → 删 |

### 2.2 命名细则（正则即判据，见 §7 机读块）

- `feat|fix` 必须带卡号：`^feat/card-\d{3,}-[\w.-]+$`、`^fix/card-\d{3,}-[\w.-]+$`
- `hotfix` 带事故号：`^hotfix/[\w.-]+$`；`chore` 带主题：`^chore/[\w.-]+$`
- slug 允许中英文与 `-` `_` `.`，**禁空格、斜杠、标点**（分支名要在命令行/URL/CI 变量里干净传递）
- 分支名里的卡号必须**真实存在**：建分支前先建卡（`需求卡/card-NNN/card.md`；系统级测试轮用 `tc-NNN`）

| 反例 | 问题 |
|---|---|
| `dev` / `test` / `zhangsan` / `feature-login` | 无卡号 → 无法对账"这张卡改了哪些提交"，也无法判"谁该合" |
| `feat/card-7-login`（卡号不满 3 位） | 编号位数与卡卷宗目录不一致，脚本与人对不上 |
| `feat/card-001-登录/注册` | 含斜杠 → 分支名被拆成目录层级，命令与 URL 全乱 |
| `master2`、`master-new` | 变相绕过保护分支纪律；要并行线请用 `feat/` 分支 |

### 2.3 生命周期与命令

```bash
git switch -c feat/card-101-报表导出            # 建（开工前，从最新 master 起）
git push -u origin feat/card-101-报表导出        # 推（首推建立跟踪；之后每完成一小步就推）
# …开发：小步提交（§3）…
git switch master && git pull --ff-only         # 合并前先同步主分支
git merge --no-ff feat/card-101-报表导出         # 或走云效合并请求（推荐，留评审记录）
git branch -d feat/card-101-报表导出             # 合并后删本地分支
git push origin --delete feat/card-101-报表导出   # 删远端分支（保持分支列表=在飞任务列表）
```

**保护分支的本地纪律**（服务端保护是硬闸门，本地先守，免得反复被拒）：任何提交不直接落在 `master`；`master` 上的合并动作只由集成工程师/主控按 §4 执行。

### 2.4 归属人 = 卡片 assignee

分支归属人负责：这条分支的提交质量（§3）、自验证据（§6）、合并前的自清（§4.1）。**别人不许往你的分支推东西**——要改，走 CR 或自己开卡开分支；这比"谁都能推"少一半冲突。跨角色协作卡（如前后端同卡）拆成各自的卡与分支，用契约（`api.yaml`）对接，不用同一分支互相盖。

## §3 提交规范

### 3.1 格式与类型

```
<type>(<scope>): <subject> [card-NNN]
```

| type | 用途 | 例 |
|---|---|---|
| feat | 新功能 | `feat(report): 报表导出支持行数上限 [card-101]` |
| fix | 缺陷修复 | `fix(auth): 修复刷新令牌过期判断 [card-102]` |
| refactor | 重构（行为不变） | `refactor(store): 拆分订单状态机 [card-118]` |
| docs | 文档/契约 | `docs(api): 补 /orders 分页参数说明 [card-120]` |
| test | 测试代码 | `test(report): 补导出边界用例 [card-101]` |
| chore | 杂活（CI/.gitignore/依赖） | `chore(ci): 加 lint 阶段 [card-090]` |
| hotfix | 生产急修 | `hotfix(#2026-0911-01): 修复支付回调 500 [hotfix-2026-0911-01]` |

- `[card-NNN]` 是**对账锚点**（系统级测试轮用 `[tc-NNN]`，急修用 `[hotfix-<事故号>]`）——没有它，验收时就回答不了"这卡对应哪个提交"
- **一次提交一件事**：把"给报表加上限 + 顺手重命名变量 + 升级依赖"塞进一个提交，回滚时只能整坨退
- 主体写**为什么**（对齐 agent.md 纪律 9）；合并提交信息由集成工程师写，说明"合了什么卡/解决了什么冲突"

| 反例 | 问题 |
|---|---|
| `update` / `修改bug` / `1` | 无法检索、无法分类生成 changelog、无法判断影响面 |
| `feat: 一大堆功能` | 一次提交多件事 = 回滚粒度为"全部"，等于没有回滚能力 |
| 提交信息写了卡号但卡里没有这个分支 | 对账时悬空（§6.3 会抓到） |

### 3.2 提交前必跑（自验命令，结果贴进卡卷宗证据）

```bash
git status --short                 # 确认只提交本卡相关文件（夹带 = 违反范围纪律）
git diff --cached --stat           # 看一眼变更规模（>300 行/超 5 文件考虑拆）
git grep -nE "(api[_-]?key|secret|password|sk-)" --cached   # 密钥自扫（§1.5）
<本卡自验命令>                      # 编译/单测/lint/接口自测 —— 全绿才提交（对齐 完成定义.md）
```

### 3.3 不许提交的三类

| 类别 | 例子 | 处置 |
|---|---|---|
| **密钥/凭据** | `.env`、`*.key`、`*.pem`、token、连接串 | 走环境变量/平台 secrets；已入库按 §5.3 处置 |
| **大文件** | >10MB 的数据集/录像/构建包 | 走 Git LFS 或移出仓库（§1.6） |
| **生成物/运行期数据** | `产物/`、`build/`、`dist/`、`node_modules/`、`data/`、`tmp/` | 进 `.gitignore`（§1.4）；已入库的 `git rm --cached` |

## §4 合并与冲突协议（**重点**）

### 4.1 合并前置条件（五条全过才允许发起合并）

| # | 条件 | 核验命令（集成工程师/主控照跑） |
|---|---|---|
| 1 | **自验通过**：卡的自验命令全绿 | 命令 + 输出在卡卷宗 `证据/<角色>/` |
| 2 | **证据落盘**：卡卷宗有 diff/日志/自验输出 | `ls 需求卡/card-NNN/证据/` 有内容（§6.2） |
| 3 | **无未提交改动**（工作区干净） | `git status --porcelain` → 空 |
| 4 | **已同步最新主分支**（不是"我本地旧 master 上合的"） | `git fetch origin && git log --oneline HEAD..origin/master` → 空 |
| 5 | **卡状态到位**：卡已 `done`（开发自验完），不是 `in_progress` 就抢合 | 读 `需求卡/card-NNN/card.md` frontmatter |

> 任一条不满足 = **打回**，不"先合了再说"；"先合了再说"的代价由集成工程师与主控在冲突/回滚时偿还。

### 4.2 谁来合、谁来裁（冲突归属规则）

| 冲突类型 | 裁决人 | 依据 | 动手改代码的是谁 |
|---|---|---|---|
| 代码与技术冲突（同一函数/接口两种实现、字段语义撞车） | **集成工程师** | `契约/api.yaml`、`契约/技术栈.md`、`契约/代码复查规则库.md` | **冲突双方的**角色各改自己那半边（集成工程师不代写实现代码） |
| 契约冲突（两边行为都对但契约没定清） | 架构师（经集成上报） | 契约优先；契约定不清 → 提 CR 改契约 | 契约责任角色（架构师/产品经理） |
| 范围与优先级冲突（两个卡的要求互相排斥） | **主控** | 《项目计划》《主控工作计划》与里程碑 | 主控改卡/改计划后，各角色按新卡改 |
| 僵持（一轮内谈不拢） | 升级：集成 → 主控 → 用户 | 见 4.6 升级路径 | — |

**归属判断法（谁改哪半边）**：冲突段落的"意图来源"是谁的卡，就由谁改——`git log -L <文件>:<行段>` 或 `git blame` 能指出两侧改动的卡号；**不许由发现冲突的人（通常是后合的人）替对方拍板实现**。

### 4.3 合并执行（两条等价路径）

**路径 A（推荐，留评审记录）：云效合并请求（MR）**
代码库 → 分支列表 → 目标分支 `master` ← 源分支 `feat/card-NNN-…` → 新建合并请求；填"关联卡 card-NNN + 验收证据指针"；评审人按 4.1 核验后合并（服务端保护分支会强制 MR）。

**路径 B（本地命令行，等价）**

```bash
git switch master
git pull --ff-only origin master                  # 主分支必须是最新
git merge --no-ff feat/card-NNN-<slug>            # --no-ff：保留"一卡一个合并点"，便于整卡回滚
git push origin master
```

> `--no-ff` 的理由：一卡一个合并提交 → 卡出问题时可 `git revert -m 1 <合并提交>` 整卡回退；线性快进合并会把卡与卡的提交混成一条线，无法整卡回退。

### 4.4 冲突解决五步（**可执行**）

```bash
# 1) 触发：merge 报冲突（退出码 1，不是“失败”，是“等你处理”）
git merge --no-ff feat/card-NNN-<slug>
#    Auto-merging <文件>；CONFLICT (content): Merge conflict in <文件>
#    Automatic merge failed; fix conflicts and then commit the result.

git status --short                                # 2) 看冲突清单（UU = both modified）
cat <冲突文件>                                     #    看清 <<<<<<< ======= >>>>>>> 三段

# 3) 判定归属：两段改动分别来自哪张卡（谁的那半边谁改，见 4.2）
git log --oneline -1 <各侧提交>                    #    或用 git blame / git log -L 定位意图来源

# 4) 解决：**保留双方意图**，重写该段（不是二选一）
#    例：一边加"行数上限"、一边加"权限校验" → 解决后两者都在

git add <冲突文件> && git commit --no-edit         # 5) 完成合并提交（信息由集成工程师补写卡号）

# 5') 放弃这次合并（还没 commit 时）
git merge --abort
```

**红线**：不许用 `-X ours` / `-X theirs` **一把梭**"解决"冲突——它不报冲突、静默丢弃一侧改动（4.5 反例）；不许在没读懂两侧意图的情况下 `git checkout --ours/--theirs <文件>` 整文件覆盖。

### 4.5 冲突解决后**必须复跑受影响回归**（硬性，不是"建议"）

理由（真实反例，可复跑）：`-X ours` 一把梭后 **merge 退出码 = 0、无任何冲突提示**，但对方的改动已被静默丢弃——只有回归能抓到：

```bash
# 反例实测（v3.22.0 自检，临时仓库）：
git merge -q -X ours feat/card-101-报表导出       # [退出码] 0（静默成功，无冲突提示）
grep -n "out = " src/report.py                    # 只剩一侧实现：out = rows if (…权限…) else []
python tests/regression_check.py                  # -> AssertionError: 回归失败：行数上限失效（card-101 被冲掉）
# 正确解决的同一场景：regression_check.py -> 回归通过：权限校验 + 行数上限同时生效
```

因此：**冲突解决（含"没报冲突但动了合并结果"的任何合并）之后，必须复跑受该冲突影响的回归/自验命令**——复跑范围至少覆盖**冲突双方卡各自的验收标准**，命令与输出贴进卡卷宗证据；抓不到回归 = 证据不足，不算解决完。回归通过前，被合并的卡不置 `done`。

### 4.6 禁止项与升级路径

| 禁止 | 说明 |
|---|---|
| `git push --force` 到 `master`（或任何保护分支） | 会重写他人已基于其上的历史；**任何情况下都不许** |
| `git push --force` 到他人分支 | 同上；功能分支要改写历史用 `--force-with-lease`（且仅在确认无人基于其开发时） |
| 在保护分支上直接提交/直推 | 违反 §2.3；服务端会拒（若没拒 = 保护分支还没设，先补 §1.1 第 6 步） |
| 冲突未解决就 `git add` 全量提交 | 会把 `<<<<<<<` 标记提交入库（后续编译报错才发现） |
| 未跑受影响回归就宣布合并完成 | §4.5 明令；这是"合完了但合错了"的唯一防线 |

**升级路径**：冲突双方各自主张僵持 → 提 CR（`问题/<角色>问题/cr-NNN.md`，写清两侧意图与影响）→ 集成工程师技术裁决（一轮内给结论）→ 仍僵持或涉及范围/优先级 → 主控裁决（改卡/改计划）→ 涉及产品取舍或工期 → 报用户。**不允许"谁先合谁说了算"**。

## §5 回滚与历史修复

### 5.1 `revert` vs `reset` 判据（选错就是事故）

| 场景 | 用什么 | 为什么 | 命令 |
|---|---|---|---|
| 提交**已推送/已合并**到共享分支，要撤销它 | **`git revert`** | 生成一条反向提交，历史只增不改——别人不用重拉，协作不断 | `git revert <sha>`（合并提交用 `git revert -m 1 <合并提交>`） |
| 提交**只在本地、未推送**，要撤销 | `git reset` | 本地历史改掉最干净 | `git reset --soft <sha>`（保留改动）／`--hard`（丢弃改动，**先确认没有别人需要它**） |
| 想"撤销最近一次提交但仍保留改动" | `git reset --soft HEAD^` | 改动回到暂存区，可重新拆成两个小提交 | — |
| 误删了分支/提交 | `git reflog` 找回 | reflog 是本地的"后悔药"（保留期有限，别指望长期） | `git reflog` → `git branch <名> <sha>` |
| 已推送的历史要"改" | **几乎都该改用 revert** | 改写已推送历史 = 全队重拉/可能重写他人工作 | 仅限"密钥泄露清理"等特殊场景（§5.3） |

### 5.2 已经合并、已经发版的错误怎么退（代码侧 + 生产侧）

1. **生产侧先止损**：按运维的《发布前清单》与回滚计划（`skills/运维工程师/SKILL.md` §6）做**镜像回滚/切流**——秒级生效，与代码仓库无关；启用生产运维契约的项目，切流/应急剧本以 `契约/生产运维.md` 与 运维工程师 skill §8 为准（定档/切流点/回滚判据/演练门禁）；prod 的任何数据写操作仍走 **SQL 修改申请单**审批（`契约/环境.md`）。
2. **代码侧留痕**：在 `master` 上 `git revert -m 1 <该卡合并提交>`（或对具体提交 `git revert`），提交信息写清"回滚 card-NNN 的原因 + 事故号"，随后走正常发布路径。
3. **不允许**"把 `master` 用 `reset --hard` 退回去再强推"——那会让所有基于其后的提交全部错位。
4. 事故与回滚动作分别记 `记忆/变更日志.md`(c-xxx) 与卡片「经验沉淀」；**踩坑即加规则**（写进 `契约/代码复查规则库.md` 一条检查点）。

### 5.3 历史中误入密钥的处理（**轮换 > 改历史**，顺序不可颠倒）

| 序 | 动作 | 说明 |
|---|---|---|
| ① | **立即轮换/吊销该凭据** | 最关键一步。密钥一旦推送，就要当作"已泄露"；改历史不能收回已泄漏的凭证，**轮换能** |
| ② | 评估暴露面 | `git log --all -p -S'<关键词>'` 找出引入与删除的提交；确认远端是否真的收到（`git ls-remote`/平台事件）、仓库可见性、有多少人克隆过 |
| ③ | 从**当前版本**移除 | `git rm --cached <文件>` + 写进 `.gitignore` + 提交（这一步立即可做，不影响他人） |
| ④ | 视风险决定是否改历史 | `git filter-repo --path <文件> --invert-paths`（推荐 filter-repo；filter-branch 慢且易错）；**改完全队必须重新克隆**，fork/克隆副本仍留着旧历史 → **先与用户确认窗口期** |
| ⑤ | 留档 | 处置过程与影响写 `记忆/变更日志.md` + 安全审计记录；规则沉淀进 `契约/代码复查规则库.md`（域5） |

| 反例 | 真相 |
|---|---|
| "改完历史就安全了" | 历史改了密钥仍然有效——**没轮换 = 没处置**。顺序必须是先轮换 |
| "我把 `.env` 删了并提交" | 老提交里还在，`git log -p` 一查就出来。删文件≠删历史≠撤销泄露 |
| "先改历史，轮换回头再说" | 窗口期内密钥一直可用；且改历史要全员重新克隆，成本远高于轮换 |

## §6 与卡卷宗 / 证据的联动

### 6.1 卡片 frontmatter 记录分支与提交（对账锚点）

```yaml
---
card: card-101
status: done
branch: feat/card-101-报表导出          # 本卡的工作分支（一卡一分支）
commits: [a1b2c3d, e4f5a6b]             # 本卡的关键提交（首提交 + 合并提交，可再加中间提交）
---
```

- 分支名与 `branch` 字段不一致 = 对账失败（`git_audit.py` 会核分支号与卡目录是否存在）
- 合并完成后在卡片「交付」区块补**合并提交 sha**，这样"验收结论 ↔ 代码版本"是钉子钉死的

### 6.2 证据里放什么（`需求卡/card-NNN/证据/<角色>/`）

| 文件 | 生成命令 | 作用 |
|---|---|---|
| `git-diff-stat.txt` | `git diff --stat master...HEAD > git-diff-stat.txt` | 本卡改动的文件与规模（范围纪律取证） |
| `git-log.txt` | `git log --oneline master..HEAD > git-log.txt` | 本卡的提交清单（含卡片标记） |
| `自验输出.txt` | 本卡自验命令的完整输出 | 对齐"证据三要素：环境 + 命令 + 结果" |

> 大产物（>5MB 的录像/构建日志）留 `产物/` 或代码域，卡卷宗只放指针（v3.17.0 卡卷宗纪律）。

### 6.3 主控批次收口核对（**卡 done 但分支未合并 = 悬空交付**）

```bash
# ① 列出未合并分支（悬空候选）
for d in repos/*/; do echo "== $d"; git -C "$d" branch --no-merged master --format='  %(refname:short)'; done
# ② 列出 done 卡声明的分支
grep -rn "^branch:" project-state/需求卡/*/card.md
# ③ 一键版（对每个代码根跑，GIT-009/GIT-003e 直接给未合并分支与脱节卡号）
python scripts/git_audit.py repos/workbench
```

核对规则：**每张 done 卡的分支要么已合并（可从分支列表消失），要么在卡上写明"未合并原因 + 预计合并时点"**——既没合并又没说明 = 悬空，主控在批次收口清单里列名并回退对应角色处置。时点与 `scripts/path_audit.py` 一致：**接管 / 批次收口 / 里程碑收口 / 用户要求**，结果写 `project-state/运行日志.md`。

### 7.2 脚本用法与退出码

```bash
python scripts/git_audit.py repos/workbench                                  # 只报告
python scripts/git_audit.py repos/workbench --branch-model project-state/契约/Git工作流.md
python scripts/git_audit.py repos/workbench --commits 30 --json               # 机器可读
```

| 退出码 | 含义 |
|---|---|
| 0 | 无 findings（严重/高/中 均为 0；"提示"不影响退出码） |
| 1 | 有 findings（严重/高/中 ≥ 1）——按报告「建议」列回退对应角色处置 |
| 2 | 用法错/环境错（路径不存在、git 不可用、`--branch-model` 指的文件不存在） |

检查项：① 是否 git 仓库（不是 → **GIT-001 未接入版本控制**，最高优先级）② 远端配置（有无/是否云效/push 地址）③ 当前分支合规 + 是否在保护分支上直接开发 ④ 工作区是否干净 ⑤ 最近 N 条提交信息 ⑥ 可疑入库（密钥文件/密钥关键词/大文件）⑦ 未合并分支清单 + 与主分支偏离度 ⑧ `.gitignore` 基线（`git check-ignore` 实测生效性）+ 已入库却被忽略的文件 ⑨ 提交身份是否配置。

### 7.3 未覆盖（脚本明说不判，别当成已核）

服务端保护分支策略 · 提交者身份真实性 · **历史里删过的密钥**（需 `git log --all -p -S'<关键词>'`）· CI 是否真跑 · **合并"合得对不对"**（只能靠 §4.5 回归复跑）· LFS 对象是否真上传（需 `git lfs fsck`）· 代码内容质量（归 `契约/代码复查规则库.md` 十域）。
