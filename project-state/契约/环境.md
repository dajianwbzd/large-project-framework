# 环境清单（Environment Manifest）

> 运维工程师产出并维护（项目初始化时创建，此后随契约变更更新）。
> **环境即代码**：任何角色（开发/测试/集成/安全）开工前必须先确认环境就绪，一切验证证据必须在指定环境真实执行后记录。
> 环境混乱 = 效果天壤之别。本文件是"哪台机器、哪个版本、哪些服务、怎么验证"的唯一事实来源（source of truth）。光靠模型内部推理解决不了运行问题，必须靠真实环境的实测反馈。

## 环境分级（三环境 = 三数据库，v3.8.0 数据模型）

大项目统一按 **dev / test / prod** 三环境建模，**每个环境一个独立数据库（或独立 schema）**，环境间数据强隔离、禁止跨库引用。**v3.8.0 起三环境数据模型（用户定案）**：

| 环境 | 位置/形态 | 用途 | 数据来源与口径 | 变更纪律 | 使用角色 |
|------|----------|------|---------------|---------|---------|
| **dev（本地开发）** | 本地独立库 | 前后端日常编码/调试/单测 | 随意读写、随意 seed，不保证与生产一致 | 无限制（本地随意） | 前端/后端开发 |
| **test（云端测试）** | 云端独立库 | 集成/验收/回归专用 | **定期从 prod 同步正常功能数据（脱敏）**，同步不可得时用 seed 补充；可重置 | 由运维维护同步任务，禁止向 prod 回写 | 测试/集成/安全审计 |
| **prod（线上生产）** | 生产独立库 | 真实用户流量运行 | 真实数据 | **任何变更必须提交 SQL 修改申请单**（目标表/变更内容/影响范围/回滚方案），经运维 + 项目经理审批后才可执行；未获批禁止改库；日常只读巡检 | 运维（见 `代码/部署/`） |

**三库三套数据铁律（v3.8.0）**：

- **三库强隔离**：dev/test/prod 各自独立库（或独立 schema），`DATABASE_URL`/端口互不相同；任何角色禁止跨环境引用数据库，禁止把 dev 数据"借到" test，禁止把 test 数据灌进 prod
- **验收证据只认 test**：测试/集成/安全报告一律标注执行环境，且验收证据必须来自 **test 环境**；禁止用"我在本地 dev 能跑"代替 test 环境证据
- **test 数据以 prod 同步为主**：运维维护「prod → test 定期同步」任务（脱敏脚本：手机号/证件/密钥等敏感字段脱敏），同步记录时间戳与范围；同步不可得时用 seed 补充，但验收口径以同步数据为准
- **prod 严格管理（SQL 修改申请单）**：任何角色对 prod 库的**写操作（修复/删改/迁移）必须先提交 SQL 修改申请单**——写明目标表、变更内容、影响范围、回滚方案，经运维 + 项目经理审批后才可执行；未获批禁止动 prod 数据；日常只做只读/健康检查/一致性核对/告警巡检
- **dev 随意**：dev 库可脏、可随意 seed、可任意删改，前后端自由调用开发和测试；dev 证据不得顶替 test 验收
- **快速模式（vibe coding）**：至少保证 dev 环境可一键启动、自检全绿；验证证据在 dev 执行并记录（仅快速模式允许以 dev 为准）
- 任何人发现"文档环境 vs 实际环境"不一致 → 立即提交 issue/CR，不默默适配

## 环境清单

### 运行时与依赖

| 组件 | 版本 | 安装方式 | 验证命令 |
|------|------|---------|---------|
| Node.js | <如 22.x> | <下载/包管理器> | `node -v` |
| npm / pnpm | <如 10.x> | 随 Node | `npm -v` |
| Python | <如 3.12> | <下载/包管理器> | `python --version` |
| Go | <如 1.22> | <下载/包管理器> | `go version` |
| 前端依赖 | <锁定 lockfile> | `npm ci` | `npm ls <关键包>` 无 missing |
| 后端依赖 | <锁定 requirements/pyproject> | `pip install -r requirements.txt` | `pip check` |

> 依赖一律锁版本（lockfile / requirements 固定版本），禁止"能装上就行"。

### 基础设施服务（Docker Compose 统一锁版本）

| 服务 | 镜像:tag | dev 端口 | test 端口 | 数据卷 |
|------|---------|---------|-----------|--------|
| PostgreSQL | postgres:16 | 5432 | 5433 | pgdata |
| Redis | redis:7 | 6379 | 6380 | - |
| <其他服务> | <镜像:tag> | <端口> | <端口> | <卷名> |

> 基础设施一律由 `project-state/代码/部署/docker-compose.yml` 启动，锁镜像版本。禁止"我机器上装的是另一版本"——版本不一致是"效果天壤之别"的头号来源。

### 环境变量

- `.env.example` **已提交**（模板，无真实密钥）；`.env` **不入库**（各环境各自填充）
- 必填变量清单：`DATABASE_URL` / `REDIS_URL` / `JWT_SECRET` / <按项目补充>
- 参考 agent-skills ci-cd-and-automation 环境管理约定：CI 只用测试密钥，绝不拥有生产密钥

### 端口分配

| 服务 | dev | test | prod |
|------|-----|------|------|
| 前端 | 5173 | 5174 | <按网关> |
| 后端 | 8000 | 8001 | <按网关> |
| PostgreSQL | 5432 | 5433 | <按生产> |
| Redis | 6379 | 6380 | <按生产> |

> 三环境端口/库名/`DATABASE_URL` 必须互不相同，防止跨环境串数据。

## 安装与配置步骤（一次性，运维产出脚本）

1. 安装运行时（版本见上表）
2. 启动基础设施：`docker compose -f project-state/代码/部署/docker-compose.yml up -d`
3. 安装应用依赖：前端 `npm ci` / 后端 `pip install -r requirements.txt`
4. 复制并填充环境变量：`cp .env.example .env`
5. 数据库迁移：`npm run migrate`（迁移可回滚）

## 环境自检（每次开工/验收前执行）

运行 `project-state/代码/部署/环境自检.sh`（Windows 用 `环境自检.ps1`），逐项检查并记录结果。**三环境各自有独立自检**：
- **dev 自检**：开发/调试/单测前跑（可脏数据）
- **test 自检**：集成/验收/回归前跑（测试与集成/安全验收的强制前提）；种子数据可重置
- **prod 自检（只读巡检）**：上线前或定期跑——只读健康检查/连接探测/一致性与告警探活，**禁止写库/删数据**

| 检查项 | 命令 | 预期 |
|--------|------|------|
| 运行时版本 | `node -v` / `python --version` | 与「运行时与依赖」一致 |
| 依赖已安装 | `npm ls <关键包>` / `pip check` | 无 missing / OK |
| 数据库可连 | `pg_isready` / curl 管理端点 | ready |
| 端口无冲突 | `netstat -ano` | 与「端口分配」一致 |
| 后端健康检查 | `curl :<env端口>/health` | 200 |
| 前端可访问 | `curl :<env端口>` | 200 |

- **自检全绿才允许开始开发/验收**；任一项失败先修环境，禁止"跳过自检直接跑"
- **test 自检全绿是集成/验收/回归的强制前提**；违反即视为证据无效，打回重验
- **prod 自检 = 只读巡检**：只验证健康/连接/一致性，绝不执行写库、删数据、压测
- 自检结果记入验收报告 / 卡片「经验沉淀」，可追溯，并标注执行环境

## 验证证据记录（反馈闭环核心）

一切验证必须**真实执行**并记录三要素：**环境 + 命令 + 结果**。

- 卡片「验收标准」的"如何证明"必须写明：在 **<环境>** 执行 **<命令>** 得到 **<结果>**
- **三环境证据各自留证**：dev 自测证据在 dev / 回归验收证据在 test（以 prod 同步脱敏数据为准）/ prod 只做只读巡检证据在 prod（变更须 SQL 修改申请单）——三者不混用，尤其禁止用 dev 证据顶替 test 验收
- 测试/集成/安全报告必须标注：执行环境（dev / test / prod）+ 环境自检结果（全绿/异常项）
- 环境问题（依赖缺失/版本不符/端口冲突/数据不干净）记入卡片「经验沉淀」与 `记忆/变更日志.md`，不静默绕过
- 禁止：凭印象断言"应该能跑"；用 dev 环境证据代替 test 环境验收；在 prod 上做写库/删数据/压测类验证

## 环境变更纪律

- 运行时/依赖/服务版本升级 = **契约变更**：更新本文件 + docker-compose + `.env.example`，走 CR 评审
- 变更记录到 `记忆/变更日志.md`（c-xxx）
- 环境变更后，所有依赖该环境的卡片需重新自检并注明
