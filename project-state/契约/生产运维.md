# 生产运维契约（Production Operations Contract）

> 维护人：**运维工程师**（项目初始化时定档 → 上线前定稿 → 每次拓扑/发布方式变更后更新并记 `记忆/变更日志.md`）
> 上位与关联文件：`契约/环境.md`（有哪些环境）、`契约/数据模型.md`（迁移登记）、`完成定义.md` §6/§7（发布就绪）、`契约/配置中心.md`（环境变量）
> 本文件回答环境清单回答不了的问题：**上线之后怎么稳住、出事怎么处置**。版本：**v3.22.0 新建**。

## 为什么有它（治什么问题）

| 现状（v3.21.0 及以前） | 后果 | 本文件的对策 |
|---|---|---|
| 只有"数据库改动走 SQL 申请单"，**代码改动没有变更通道** | 生产改代码靠传文件/直接重启，无审批、无留痕、无观察窗口 | §2 变更分级（三类合一）+ §3 发布流程 |
| 出事故靠直觉选"切流 / 回滚 / 热修" | 选错方向比不动作更糟（数据已前滚却退代码 → 新结构读不了） | §4.2 决策序 + 真值表（判据可判定） |
| 回滚只回代码不回数据 | 状态更糟：数据前滚、代码后退，新旧结构互读失败 | §4.5 数据与代码配对原则（**数据只前滚不后退**） |
| 从未演练，第一次回滚发生在真事故里 | 记错命令/权限不足/软链顺序错，止血时间翻倍 | §6 演练为上线门禁（首次上线前必须演练留证） |
| 事故后不复盘、不沉淀 | 同一个坑踩第二次 | §5 复盘 → 规则沉淀（规则库/检查点） |

**适用档位**：A/B/C 三档（v3.16.0）都必填本文件——**A 档可简化到最小集**（§0 定档 + §1 健康检查与备份 + §4 分级与决策序 + §6 演练），但 §4.5「数据只前滚不后退」与 §2「生产禁手改」在任何档位都不得裁剪。

## §0 项目定档区（先定档，再谈机制）

### 0.1 交付形态（决定"有没有切流点"）

| 交付形态 | 判定 | 出事时的处置能力 | 依据 |
|---|---|---|---|
| **云端服务** | 有服务器/域名，代码可远程替换 | 可切流、可回滚、可热修 | 本节 0.2 |
| **桌面交付物** | 用户装机 exe/安装包 | **无切流点**：只能发新版或请用户装旧版 | 本节 0.3 |
| **二者兼有** | 桌面端 + 云端后台 | 两条剧本并存，分别演练 | 0.2 + 0.3 |

> ⚠️ 定档直接决定 §4 决策树的分支：**桌面/移动等分发型交付物没有服务器侧回滚点**，多数情况只能"往前修"，因此它的纪律前移到发布前（灰度、内测、旧版包留档、数据结构向前兼容）。

### 0.2 生产拓扑与切流点（云端形态填此表）

| 拓扑元素 | 真实取值 | 是否切流点 | 判据命令（看到什么算对） |
|---|---|---|---|
| 对外入口 | `<域名/IP:端口>`，`<nginx/reverse proxy 版本>` | 否（入口） | `curl -sI <URL>` → `<HTTP 200 + Server 头>` |
| 反代 / 静态 | `<root 指向>`，`<upstream/端口>` | 是（可摘节点/改 upstream） | `nginx -t` → `syntax is ok`；`curl -s <URL>/api/health` → `"ok":true` |
| 应用进程 | `<systemd unit / pm2 / docker>`，监听 `<127.0.0.1:PORT>` | 否（重启单元） | `systemctl is-active <unit>` → `active` |
| **版本切换点** | `<软链 current / 蓝绿端口 / 镜像 tag>` | **是（首选切流点）** | `<readlink -f current>` → 指向目标版本目录 |
| 数据存储 | `<SQLite 文件绝对路径 / PostgreSQL 实例>` | 否（回滚红线） | `<DB 健康探测>` → `db:ok` |
| 备份位置 | `<备份目录 / OSS 路径>` | 否 | `ls -l <备份>` → 文件存在且大小 > 0 |

**切流点唯一性**：一次事故只允许**一个**切流动作（切软链 **或** 改 upstream，不叠加）；叠加 = 无法归因。

## §1 稳定性基线（上线前必须就位）

### 1.1 健康检查与判定

| 项 | 取值 | 正确判据 | 假绿风险（必读） |
|---|---|---|---|
| 服务健康端点 | `<GET /api/health>` | 返回体含 `"ok":true` **且** `"db":"ok"`，HTTP 200 | **进程活着 ≠ 功能正常**：真实实测中"管理台改坏"版本的健康端点仍返回 `ok:true`（见 §4.6 附录 C） |
| 就绪 vs 存活 | `<readiness 判据 / liveness 判据>` | 就绪 = 依赖（DB/缓存/磁盘）可用 | 只探进程 → 依赖挂掉仍被调度 |
| 静态/入口可达 | `curl -sI <URL>` | 200 | 静态 200 也不能证明前端资产是新的 |
| **版本指纹（v3.22.0 新增）** | `sha256sum <入口文件>` 或关键资产内容计数 | 与本次发布单登记值一致 | 版本号字符串常多年不变（实测 `version:"0.1.0"`），**不能定位构建** |
| 关键链路冒烟 | `<命令：登录→上传→下载 的 curl 脚本>` | 每步断言成功且**非空** | "空 = 空"比较会假通过 |

**判据纪律**：一切断言必须能失败——取值先判非空、再比内容；"应为 0 的东西"要显式反向断言。

## §2 变更分级与审批（把"申请单"从数据库扩成三类）

| 变更类型 | 例子 | 申请单 | 审批 | 观察窗口 | 留痕位置 |
|---|---|---|---|---|---|
| **常规代码变更** | 功能迭代、依赖升级、配置模板改动 | **发布单** | 主控 | ≥ `<N 分钟>`（默认 10） | `问题/变更申请单/` + `记忆/变更日志.md` |
| **紧急代码变更（hotfix）** | 生产 P0/P1 | **紧急变更单（可事后 24h 内补）** | 主控 + **用户知会** | 实时盯到指标恢复 | 同上 + `问题/事故报告/` |
| **数据/配置变更** | 加列/改口径/改配置/改密钥 | **SQL 修改申请单**（沿用 v3.8） | 主控 + **安全审计（风险评审）** | 按影响面（见 §4.5） | 同上 + `契约/数据模型.md` 迁移登记 |

**口径澄清（v3.22.0，对 v3.8 的修订）**：v3.8 原文写"经运维 + 项目经理审批"。本版明确为 **运维发起 → 主控放行 + 安全审计做数据/配置风险评审 → 项目经理登记与知会**。理由：项目经理在本框架中"不参与技术决策"（见 `skills/项目经理/SKILL.md`），把技术审批压在它身上与角色定义冲突；**门禁语义不变**（未获批禁止动 prod）。迁移动作：新申请单一律走新口径；已按旧口径批准且执行完的申请单不追溯；`契约/环境.md` 与既有 skill 的旧表述在下次模板同步时统一替换。

### 2.1 申请单必填字段（三类通用骨架，细则见模板文件）

1. 单号 / 类型 / 级别（P0~P3 或 常规）/ 日期时间 / 发起人
2. 变更内容：改了什么（文件清单 + **sha256**；SQL 要给完整语句）
3. 影响面：受影响功能 / 数据表 / 用户范围 / 是否不可逆
4. **回滚方案**：回滚动作 + 回滚判据 + 回滚耗时预估（**必填，写"无"= 不予批准**）
5. 备份证据：备份文件路径 + 校验结果
6. 观察窗口与判据（看到什么算成功 / 看到什么要回滚）
7. 审批栏（主控 / 安全审计 / 用户知会时间）
8. 执行留痕栏（实际执行时间线、命令、输出、结论、偏差）

### 2.2 红线（禁止事项，命中即停手并上报）

1. **禁止无备份直接改数据**（含"先改了再补备份"）
2. **禁止在生产手改代码**，一切代码改动走发布/热修流程（改完必须留 sha 与申请单）
3. **禁止在生产跑测试数据 / seed / 压测 / 删数据**
4. **禁止无回滚方案直接发布**（"出问题再说"不是方案）
5. **禁止一次发布夹带多个不相关变更**（无法归因 = 无法回滚）
6. **禁止在事故中同时做多个方向的动作**（先止血一个动作，观察，再下一个）
7. **禁止跳过观察窗口宣布成功**（未观察 = 未发布完）
8. **禁止把密钥/口令写进申请单、日志、聊天记录**（写"已轮换 + 存放位置"即可）
9. **禁止把业务对话与客户原件写进框架仓库（v5.24.1）**——框架仓库只收**指向框架自身缺陷**的一句原话（如「缺了一类测试」）；真实项目的业务对话、客户原始件、语音转写、截图一律留在**该项目工作区**的 `方案/原始资料/`（只进不改 + `清单.md` 逐行登记），需要跨项目引用时写指针而不是贴内容。判据：**这条内容搬到别的项目还有意义吗？**没有 = 不许进框架仓库
10. **禁止对 prod 执行迁移的 down 脚本**（数据只前滚不后退，见 §4.5）
11. **禁止无人知会地重启/停机**（P0 除外，但事后必须补记录）

### 2.3 机器核验（可跑）

```bash
# 申请单是否留下了可追溯的三个硬证据（sha256 / 备份路径 / 回滚动作）
grep -cE '^[0-9a-f]{64}' project-state/问题/变更申请单/*.md      # 每次发布 ≥1
grep -l '回滚' project-state/问题/变更申请单/*.md | wc -l          # 应等于申请单总数
grep -n '<[^>]*>' project-state/问题/变更申请单/<新单>.md          # 应无输出（占位符已替换）
```

## §3 发布流程（常规变更，从预检到留痕）

```
预检 → 备份 → 发布（整批 或 灰度）→ 观察窗口 → 全量/确认 → 留痕（发布单 + sha + 时间线）
```

### 3.1 预检清单（每条都能判定，不通过不许发布）

- [ ] **构建可复现**：从 `<构建命令>` 得到产物，产物 `sha256` 与本地一致（`sha256sum` 双端比对）
- [ ] **包内容合规**：不含 `node_modules/`、`data/`、`.env`、密钥、临时文件
- [ ] **迁移可回滚或向前兼容**：本次迁移是"只增"（旧代码能跑）还是"改结构"（旧代码会崩）——**改结构 = 禁止代码回滚**，必须写进申请单
- [ ] **备份已做**：备份文件存在 + 校验通过（记录路径）
- [ ] **回滚路径已备**：上一版目录/上一版安装包存在且可切（`readdir`/`ls` 证据）
- [ ] **回滚路径已演练**（首次上线/拓扑变更后必做，见 §6）
- [ ] **环境一致**：目标环境预检脚本无 FAIL
- [ ] **窗口与静默**：在允许窗口内，告警已静默/已知会
- [ ] **申请单已批**：审批栏已填（缺任一 → 停）

### 3.2 发布（整批 vs 灰度）

| 形态 | 可否灰度 | 做法 | 判据 |
|---|---|---|---|
| 单机软链版本目录 | 否（整批） | 解压新版本目录 → 切 `current` → 重启单元 | `readlink current` = 新版本 + 健康端点 ok |
| 多节点反代/upstream | 是 | 摘 1 个节点 → 发 → 观察 → 逐个放回 | 被摘节点健康 + 主流量 5xx 无上升 |
| 蓝绿端口 | 是 | 起绿环境 → 直连验证 → 切 upstream | 直连绿端口 ok 后再切 |

**发布动作与顺序不变量**（顺序错就出事）：
`备份 → 解压新版本目录 → 装依赖 → 校验版本目录可用 → 切 current（**必须在重启之前**）→ daemon-reload + restart → 反代 reload → 验证`

### 3.3 观察窗口与判据

| 观察项 | 判据（全部满足才算通过） |
|---|---|
| 健康端点 | 连续 `<N 次>` 200 且 `ok:true` + `db:ok` |
| 错误日志 | `journalctl -u <unit> -n 100` 无新增 ERROR/异常栈 |
| 错误率 | 5xx 率 ≤ §0.6 阈值 |
| 关键链路 | 冒烟脚本全过（含"下载内容 sha256 与上传一致"这类强断言） |
| 数据一致性 | `<行数/总额/外键>` 抽样核对无异常 |
| 版本指纹 | 生产资产指纹 = 发布单登记值（防止"部署了旧包"） |

窗口内任一不满足 → 按 §4.2 决策序处置（刚发布完时数据通常尚未前滚，多数情况落到动作 C **回滚到上一版**）；**不要凭"直觉先回滚"**，先过 Q1/Q2。

### 3.4 留痕（发布单 + sha + 时间线）

发布单必须含：版本目录名、产物 `sha256`、**生产资产指纹**（入口文件 sha256）、迁移登记指针、备份指针、回滚目标、观察窗口结论、执行时间线（HH:MM 动作 → 输出摘要）。

## §4 紧急修复剧本（Hotfix Runbook）——本契约核心

### 4.1 分级（P0~P3 判据表）

判据三要素：**用户可见程度 × 数据风险 × 有无绕过方案**（三者同时成立才定该级）。

| 级别 | 判据（可判定） | 响应时限 | 汇报对象与节奏 | 决策人 |
|---|---|---|---|---|
| **P0** | 全体/多数用户不可用，**或数据正在被写坏且仍在扩大**，**且**无绕过方案 | 立即动作（≤15 分钟开始处置） | 主控 + 用户，立即；每 15 分钟更新 | 主控（数据类动作需用户拍板） |
| **P1** | 核心链路不可用但**有绕过**（如子集用户/单模块），无数据损坏 | ≤30 分钟定方向 | 主控 + 用户，首次 30 分钟内；每小时更新 | 主控 |
| **P2** | 非核心功能/单模块异常，无数据风险，用户可绕过 | ≤1 工作日 | 记入变更申请单，日报 | 运维 + 主控知会 |
| **P3** | 体验/文案/视觉缺陷，功能可用 | 下一发布窗口 | 变更日志 | 运维 |

**升级规则**：影响面扩大一档即升级（P2 → P1 → P0），**只升不降**；降级需连续 `<N 分钟>` 指标正常。

### 4.2 三选一决策树（止血 / 回滚 / 热修前滚）

#### 4.2.1 五个判据（全部可判定）

| # | 判据 | 怎么判（命令/证据） |
|---|---|---|
| **Q1** | 数据是否**已前滚**（新结构/新口径已被写入） | 迁移版本号 ≥ 回滚目标期望版本（真实列名与样例见 §4.5）；或 `PRAGMA table_info(<表>)` 看到新列且该列 `SELECT COUNT(*)` 有非空数据 |
| **Q2** | 错误在**旧版是否也存在**（回滚是否无用） | 用上一版目录在隔离环境复现同一操作（`<命令>`）；旧版同样失败 → 回滚无用 |
| **Q3** | 影响是否**仍在扩大** | 5xx 率/失败量/写入量的时间序列是否上升（相邻窗口对比）；"还在涨"= 是 |
| **Q4** | 修复是否 **≤30 分钟且低风险**（不新增迁移、不触数据写入路径、改动 ≤3 文件/≤30 行） | 看 diff：`git diff --stat`；含迁移或改数据结构 → 直接判"否" |
| **Q5** | 是否有**可用回滚点**（上一版目录/上一版安装包存在，且旧版能读当前数据） | `readlink -f current` 指向存在目录；`ls <上一版>`；桌面端见 §0.3 兼容性约束 |

#### 4.2.2 决策序（顺序执行，先命中先得结论——这就是互斥性保证）

```
第 1 步  Q3 影响扩大中？ 是 → 【动作 A 止血】：摘流量/切维护页/停写（只做一个动作）→ 观察 → 回第 2 步
第 2 步  Q1 数据已前滚？ 是 → 【动作 D 热修前滚】：禁止回滚代码 → 跳第 4 步
第 3 步  Q2 旧版也错？   是 → 【动作 D 热修前滚】：回滚无用 → 跳第 4 步
第 4 步  Q4 修复≤30min 且低风险？ 是 → 【动作 B 热修前滚】：改 → 5 分钟验证 → 观察
                                  否 → Q5 有回滚点？ 是 → 【动作 C 回滚代码】
                                                      否 → 【动作 E 无回滚点】：只能往前修/重建，
                                                             P0 升级 + 用户拍板（含数据损失告知）
```

#### 4.2.3 真值表（条件 → 动作；**互斥且完备**，机器可核验）

止血（动作 A）是**前置动作**而非终态——做了止血后，条件的"影响是否扩大"已变为"否"，再按下面四行判定终态动作。因此终态动作的判定域是 `Q3=否`：

| 终态动作 | 触发条件（互斥） | 一句话判据 |
|---|---|---|
| **B 热修前滚** | `Q1=否 AND Q2=否 AND Q4=是` | 没前滚、旧版也不背锅、修得快 → 直接修 |
| **C 回滚代码** | `Q1=否 AND Q2=否 AND Q4=否 AND Q5=是` | 数据干净且回滚点可用 → 切回上一版最稳 |
| **D 热修前滚（禁止回滚）** | `Q1=是 OR Q2=是` | 数据已前滚 或 旧版也错 → 回滚必然无效或更糟 |
| **E 无回滚点（只能往前修/重建）** | `Q1=否 AND Q2=否 AND Q4=否 AND Q5=否` | 想回滚却没有回滚点 → P0 升级 + 用户拍板 |
| **A 止血（前置）** | `Q3=是` | 影响还在扩大 → 先切断扩大源（摘流量/停写），再回上表 |

**完备性**：四个条件组合（Q1 是/否 × Q2 是/否 × Q4 是/否 × Q5 是/否 = 16 组）全部落入上表四行之一；**互斥性**：任一组合只满足一行（先判 `Q1∨Q2`，再判 `Q4`，再判 `Q5`，顺序判定即保证唯一）。

**机器核验（本表的自测脚本）**：

```python
# 遍历全部条件组合，验证"恰好一个终态动作"（互斥 + 完备）；改判据后重跑
import itertools
from collections import Counter

def action(q1, q2, q3, q4, q5):          # Q3 是前置门；Q1/Q2/Q4/Q5 决定终态动作
    if q3: return "A_先止血"              # 止血后按 Q3=False 重判
    if q1 or q2: return "D_热修前滚_禁止回滚"
    if q4: return "B_热修前滚"
    return "C_回滚代码" if q5 else "E_无回滚点"

combos = list(itertools.product([False, True], repeat=4))     # q1,q2,q4,q5
hits   = [action(q1, q2, False, q4, q5) for q1, q2, q4, q5 in combos]
print("终态判定组合数:", len(combos), "| 分布:", dict(Counter(hits)))
assert len(combos) == 16
assert set(hits) == {"B_热修前滚", "C_回滚代码", "D_热修前滚_禁止回滚", "E_无回滚点"}   # 完备
assert all(action(q1, q2, True, q4, q5) == "A_先止血" for q1, q2, q4, q5 in combos)     # 止血门
# 场景自测（S1~S4，见 4.2.4）
assert action(True,  False, False, True,  True ) == "D_热修前滚_禁止回滚"   # S1 数据已前滚
assert action(False, True,  False, True,  True ) == "D_热修前滚_禁止回滚"   # S2 旧版也错
assert action(False, False, True,  False, True ) == "A_先止血"              # S3 影响扩大（止血后 → C）
assert action(False, False, False, False, False) == "E_无回滚点"            # S4 桌面端无切流点
print("PASS: 16 组组合互斥完备；S1~S4 判定与 4.2.4 一致")
```

#### 4.2.4 四个自测场景（决策树回归用例，改判据后必须重跑）

| 场景 | 条件 | 判定路径 | 结论动作 |
|---|---|---|---|
| S1 | 数据已前滚 + 错误仅新版有 | 第1步否 → 第2步**是** → 动作 D | **热修前滚**（禁止回滚代码） |
| S2 | 数据未动 + 错误新旧都有 | 第1步否 → 第2步否 → 第3步**是** → 动作 D | **热修前滚** |
| S3 | 影响扩大中 + 修复需 2 小时 | 第1步**是** → 动作 A 止血 → 第2/3步否 → 第4步否 → Q5 是 → 动作 C | **先止血 → 回滚代码** |
| S4 | 桌面端已分发坏版本 | 第1步否（用户侧）→ 第2步：用户数据是否被新版写坏？未坏则否 → 第3步否 → 第4步否 → Q5 **否（无切流点）** → 动作 E | **动作 E：只能发新版 + 通知用户**；若旧版能读数据且用户愿意重装，可**降级为动作 C'（用户侧回滚：发旧版包 + 卸载重装）** |

> S4 说明：分发型交付物的"回滚点"= 旧版安装包 **且** 用户愿意配合 **且** 数据结构向前兼容，三者缺一即判"无回滚点"。

### 4.3 热修纪律（动作 B/D 的执行规矩）

| 纪律 | 要求 | 判据 |
|---|---|---|
| 最小改动面 | 只改必要行；≤3 文件 / ≤30 行；不夹带重构与格式化 | `git diff --stat` 输出留档 |
| diff 留痕 | diff 或文件 sha256 贴进紧急变更单 | `sha256sum <改动文件>` |
| 补回归用例 | 修完必须有一个"无此修复即失败"的用例 | 用例命令 + 修复前失败/修复后通过的两次输出 |
| **5 分钟内可验证已修好** | 验证命令必须能在 5 分钟内跑完并给出明确判据 | 见下方模板 |
| 事后补正 | 24 小时内补：紧急变更单 + 事故报告 + 回归用例入正式集 + 规则沉淀 | `ls 问题/事故报告/` + 申请单 |
| 单一变量 | 一次只改一处，不同时上调/下调阈值与改代码 | diff 单主题 |

**5 分钟验证命令模板（照抄改地址）**：

```bash
U=<https://...>            # 或 http://127.0.0.1:<PORT>
# ①非空前置 + ②健康字段 + ③状态码 + ④版本指纹（四件套）
H=$(curl -fsS -m 5 "$U/api/health"); [ -n "$H" ] || { echo "FAIL: health 空"; exit 1; }
echo "$H" | grep -q '"ok":true' || { echo "FAIL: ok 非 true"; exit 1; }
echo "$H" | grep -q '"db":"ok"' || { echo "FAIL: db 非 ok"; exit 1; }
C=$(curl -fsS -m 5 -o /dev/null -w '%{http_code}' "$U/<坏掉的那个页面>"); [ "$C" = "200" ] || { echo "FAIL: 页面 $C"; exit 1; }
F=$(curl -fsS -m 5 "$U/<关键资产>" | grep -c '<修复后应出现的字符串>'); [ "$F" -ge 1 ] || { echo "FAIL: 指纹未命中"; exit 1; }
echo "PASS: 修复已验证（$(date '+%H:%M:%S')）"
```

> 通用要求：**容器存活不算修好，健康端点 ok 也不算修好**——必须有一条**断言到坏掉的那个功能**（页面/接口/资产指纹）的判据。

### 4.4 切流/回滚剧本（按拓扑给命令与判据）

| 拓扑 | 切流/回滚动作 | 判据（看到什么算成功） | 回滚后必做 |
|---|---|---|---|
| **软链版本目录** | `ln -sfn <releases/旧版> current` → `systemctl restart <unit>` | `readlink -f current` = 旧版目录；健康端点 `ok:true`+`db:ok`；版本指纹回到旧值 | ①关键链路回归 ②数据核对 ③告警确认 ④记录回滚耗时 |
| **nginx upstream / 站点** | 摘节点：注释 upstream 行 / `rm sites-enabled/<站>` → `nginx -t && systemctl reload nginx` | `nginx -t` 输出 `test is successful`；5xx 归零；静态资源指纹回到旧值 | 同上 + 恢复前先修好再放回 |
| **蓝绿端口** | 改 upstream 指向旧端口 → reload | `curl <旧端口>/health` ok；公网入口 200 | 绿环境保留 `<N 天>` 供取证 |
| **桌面/移动交付物** | **无切流点**：发新版包 + 用户通知；旧版可回退时发旧版包 | 用户侧 `DisplayVersion` / exe `sha256` | ①保留旧版包 ②兼容性检查 ③通知话术见 §5.3 |

**回滚前 3 个必查**（缺一不可）：①数据未前滚（Q1 已判）②备份已完成 ③回滚目标目录存在且可读。
**停机类动作**：`stop` 容易、`start` 难——回滚过程中**能不停机就不停机**（换软链 + restart 通常 <10 秒）。

### 4.5 数据与代码的配对原则（写死，不得裁量）

1. **数据只前滚，不后退**：生产**不执行**迁移的 down 脚本；不用备份覆盖来"回滚代码"。
2. **若数据已前滚 + 新代码已写入新结构 → 禁止回滚代码**，只能热修前滚（对应 §4.2.3 真值表「D 热修前滚（禁止回滚）」行）。
3. **识别方法（三条都要跑；下方为真实项目实测样例）**：
   - 迁移版本：`SELECT version, name, applied_at FROM schema_migrations ORDER BY version;`
   - schema 探测：`PRAGMA table_info(<表>);`（列增删）/ `PRAGMA table_list;`（表增删）
   - 写入痕迹：新表/新列是否有非空数据、旧列是否仍有默认值

   ```text
   $ PRAGMA table_info(schema_migrations)  => version,name,applied_at          # 表结构确认（实测）
   $ SELECT * FROM schema_migrations       => [{version:1,name:"init_accounts_and_points",applied_at:"…"},
                                               {version:2,name:"add_skills_and_purchases",…},
                                               {version:3,name:"add_settings_and_skill_doc",…}]
   $ PRAGMA table_list                     => settings,purchases,skills,point_transactions,sessions,
                                              schema_migrations,users,…                  # 表增删一览
   ```
   **判读**：回滚目标（旧版代码）期望的 schema 版本 < 当前 `schema_migrations` 最大版本 → **数据已前滚**，进入第 2 条红线（禁止回滚代码）。
4. **允许代码回滚的唯一条件**：数据未前滚 **且** 旧版能读当前数据（用旧版目录对当前库跑一次只读冒烟即为证据）。
5. **备份不是回滚手段**：恢复备份 = 丢弃备份点之后的全部真实数据，只有用户书面确认才可执行，且必须写进事故报告（含损失窗口与估算）。
6. **结构变更必须"向前兼容一次"**：加列可空/加表/加默认值 → 允许回滚代码；改列类型/删列/改口径 → **禁止回滚**，发布单必须显式标注"本次不可回滚，只能前滚"。

#### 附录 B：5 分钟处置剧本（"管理台改坏了"，真实可执行）

> 场景：管理台某模块打不开/列表空白/接口 404，用户已开始反馈。**T+0 起计时**。

| 时刻 | 动作（命令） | 判据（看到什么算对） | 不符时的下一动作 |
|---|---|---|---|
| **T+0:00** | `systemctl status skill-platform --no-pager` | `Active: active (running)` | 若 `failed`/`activating` → 直接跳 T+2:30 回滚 |
| **T+0:20** | `curl -s -m 5 http://127.0.0.1:3210/api/health; echo` | `"ok":true` 且 `"db":"ok"` | 若 `db` 非 ok → 转 §4.5（数据类，禁止回滚代码） |
| **T+0:40** | `journalctl -u skill-platform -n 50 --no-pager \| tail -20` | 无新增异常栈/无 `SQLITE_` 报错 | 有异常栈 → 记下时间戳，判断是否本次发布引入 |
| **T+1:00** | `readlink -f /opt/skill-platform/current && ls -1 /opt/skill-platform/releases/` | 指向当前版本目录，且**至少还有一个上一版目录** | 只有一个版本 → 无回滚点 = 动作 E，立即升级 P0 并告知用户 |
| **T+1:20** | `sha256sum /opt/skill-platform/current/public/admin.html`（或 `grep -c '<模块 id>' .../admin.html`） | 与本版发布单登记值一致 | 不一致 → 线上根本不是这个版本（附录 A 偏差），先确认真实版本再动 |
| **T+1:40** | `curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1/admin.html` | `200` | 非 200 → nginx 侧问题，看 `/var/log/nginx/*.error.log` |
| **T+2:00** | **决策**：走 §4.2 决策序（Q3→Q1→Q2→Q4→Q5） | 得出 动作 B/C/D/E 之一 | — |
| **T+2:30** | 备份：`sqlite3 $DB "VACUUM INTO '/opt/skill-platform/backup/platform-$(date +%F_%H%M).db'"` | 备份文件生成、大小 > 原库、`PRAGMA integrity_check` = ok | 无 sqlite3 CLI → `systemctl stop` + `tar -czf` 打 `data/`；**禁止直接 cp 主库文件**（附录 D） |
| **T+3:00** | 回滚：`systemctl stop skill-platform && sudo -u skillplatform ln -sfn /opt/skill-platform/releases/<上一版> /opt/skill-platform/current && readlink -f /opt/skill-platform/current && systemctl start skill-platform` | `readlink` 输出 = 上一版目录；`systemctl is-active` = `active` | 起不来 → `journalctl -n 80`，必要时切回被回滚版本（回到起点，不再连错两次） |
| **T+3:40** | 复验（4 件套）：健康端点 + 坏掉的那个页面 200 + 资产指纹回到旧值 + 关键链路冒烟 | 全过 | 任一不过 → 不是版本问题，转 §4.5/数据线，P0 升级 |
| **T+4:20** | 数据核对：`SELECT COUNT(*) FROM <关键表>`、抽样比对最近记录 | 数据未丢/未串 | 异常 → 停服保护数据，用户拍板 |
| **T+5:00** | 留痕：写紧急变更单 + 启动事故报告；用户在 `§5.3` 口径下得到一句话说明 | 申请单有 sha/时间线/回滚目标 | 24 小时内补齐事故报告与规则沉淀 |

> **实测耗时参照**：本机隔离沙箱内完整走完"发现坏版本 → 切软链 → 重启 → 复验"为 **5 秒级**（附录 C）；服务器侧含登录与确认，5 分钟是含判据核对的保守预算。

#### 附录 C：本机隔离演练实测（回滚机制真跑，2026-09-10）

沙箱：`%TEMP%\v322_drill`（隔离目录，未触碰项目与生产）。用发布包 `skill-platform-20260910.zip` 作"好版本"，另造一个"坏版本"（删掉导航项 `id="sa-nav-users"` + 把 `/api/admin/users` 打成 `/api/admin/userz`），以目录切换（Windows 用 junction，Linux 等价物 `ln -sfn`）模拟 `current` 软链。

```text
===== STEP 1: 部署好版本 20260910 =====
health      : {"ok":true,...,"db":"ok","uptime_seconds":3}
admin.html  : 200
nav-users id: 1
userz path  : 0
===== STEP 2: 部署坏版本 20260911 =====
health      : {"ok":true,...,"db":"ok","uptime_seconds":3}   ← 假绿！
admin.html  : 200                                            ← 静态照样 200
nav-users id: 0                                              ← 只有资产指纹抓到
userz path  : 4
===== STEP 3: 回滚（current 切回 20260910）=====
health      : {"ok":true,...,"db":"ok","uptime_seconds":3}
admin.html  : 200
nav-users id: 1
userz path  : 0
```

**三条实测结论**：
1. **健康端点抓不到前端/功能级坏**（坏版本 `ok:true` 依旧）→ 观察窗口必须含"资产指纹 + 坏掉那个功能的断言"，见 §1.1 与 §4.3。
2. **回滚 = 一个指针 + 一次重启**，秒级生效；前提是**上一版目录还在**（§1.3 要求保留 ≥2 个版本）。
3. 演练必须**造一个能被判据抓到的坏**（改真实文件），不能只演练"切指针"——否则演练通过而真实事故照样抓瞎。

#### 附录 D：备份正确性实测（SQLite WAL 的真陷阱）

```text
db file size before: 4096          # 主库文件只有 4KB
（同目录 platform.db-wal = 127752 字节）
integrity_check: ok
backup snapshot size: 86016
backup integrity_check: ok
tables: point_transactions,purchases,schema_migrations,sessions,settings,skills,sqlite_sequence,users
```

**结论**：库开着 WAL 时，**直接 `cp platform.db` 很可能只拿到 4KB 的空壳**（真实数据在 `-wal` 里还没 checkpoint）→ 备份必须用 `VACUUM INTO`（在线、一致、不停服）或 **停服后整体打包 `data/`**（含 `-wal`/`-shm`）。**备份后必须验**：`PRAGMA integrity_check` = ok 且表清单与预期一致，否则备份等于没有。

## §5 事后复盘与沉淀

### 5.1 事故报告（P0/P1 必写，P2 可简写）

必填：级别 / 时间线（发现→止血→恢复，含时区）/ 影响面（用户数、功能、数据）/ **根因（至少问到"为什么没被拦住"）** / 处置动作与命令 / 损失（时长 + 数据 + 商务）/ 待改进项（每条带 owner + 期限）/ 规则沉淀指针。
模板：`问题/事故报告/事故报告模板.md`；演练记录用同模板（`演练-<日期>.md`）。

### 5.2 规则沉淀（不沉淀 = 白出一次事故）

| 沉淀去向 | 何时写 | 判据 |
|---|---|---|
| `契约/代码复查规则库.md` 新检查点（踩坑即加规则） | 根因是代码/复查遗漏 | 新增条目含来源/踩坑人/时间/坑背景（对齐 v3.11.0 纪律①） |
| `完成定义.md` 新检查点 | 根因是流程缺环（本版新增 §6 演练门禁即此类） | 具体到可勾选项 |
| 本契约（§0~§6）更新 | 拓扑/切流方式/备份策略变化 | 变更记 `记忆/变更日志.md` |
| `测试卡` 覆盖维度 | 该缺陷本应由系统级测试拦住 | 下一轮测试卡矩阵新增该维度/用例 |
| `记忆/角色/<角色>.md` | 本角色踩坑/约定 | 收工追加（只追加不回改） |

### 5.3 用户可见说明（面向客户/用户的口径）

模板（**先结论、不甩锅、给下一步**）：

> 【发生了什么】<一句话，用户视角>。【影响谁】<范围与时长>。【已恢复】<时间点 + 当前状态>。【数据影响】<有/无，若有：影响什么、怎么补偿>。【为什么没影响更多】<一句话>。【我们改了什么】<防复发措施>。【需要你做什么】<无 / 请升级到新版 / 请重新登录>。

纪律：①发布前经**主控确认**（对外口径统一）；②不写内部术语与命令；③**不隐瞒数据影响**（隐瞒 = 商务风险，比事故本身更贵）；④桌面端事故须附**升级步骤与旧版包路径**（§0.3）。

## §6 演练要求（**上线门禁**）

| 时点 | 必须做的演练 | 通过判据 | 留证 |
|---|---|---|---|
| **首次上线前** | ①回滚演练（切软链/摘节点全流程）②备份恢复演练（恢复到一个隔离位置并校验） | 演练真实执行（有命令与输出）、恢复后关键链路可用、**耗时记录 ≤ RTO** | `问题/事故报告/演练-<日期>.md` |
| 每次改动拓扑（切流方式/存储/入口/进程管理） | 重演对应剧本 | 同上 | 同上 |
| 每次发布流程或回滚方式变化 | 重演 | 同上 | 同上 |
| 每 `<N 周>`（常态） | 备份恢复抽查 | 恢复库 `integrity_check` = ok + 抽样比对 | 演练记录追加 |

**演练硬纪律**：
1. **演练必须在隔离环境做**（副本目录/副本库/`tmp/`），**不得在生产上"试一下"**；生产只做只读探测。
2. 演练要**真造一个能被判据抓到的坏**（附录 C 教训），只切指针不算演练。
3. **演练失败 = 不允许上线**（不是"记个待办先上"）；失败原因修完重演。
4. 演练记录含：日期/环境/剧本编号/执行人/时间线/命令与输出/结论（通过 or 失败 + 失败项）/RTO 实测值。
5. 演练产物（副本目录、临时库）用后归位或清理，**不留在生产目录**（`tmp/` 唯一临时区，v3.14/3.18 路径纪律）。

**机器核验**：

```bash
ls project-state/问题/事故报告/演练-*.md            # 上线前应 ≥1，且内容非模板占位
grep -c '<[^>]*>' project-state/问题/事故报告/演练-*.md   # 逐份应为 0（占位符已填）
# 本契约的"待填项计数"：对**已定稿的项目副本**跑，应为 0；框架模板本身含占位符，命中数 = 还有几处没定档
grep -c '<[^>]*>' project-state/契约/生产运维.md
```

## §7 高可用与故障转移（v4.0.0，生产项目）

> **为什么有它**：§1.3 管"容量够不够"、§6 管"回滚/恢复演练"，但**高可用与故障转移**（多实例、单点、实例/可用区故障）此前无要求——属于"出大事才想起没有"的缺口。本节点补上，并与 §1.3/§6 衔接（不重复定义容量阈值与回滚演练）。

### 7.1 单点清单（逐项列，不允许"没想过"）

| 组件 | 是否单点 | 故障影响（业务/数据） | 处置（消除 / 接受 + 理由） |
|---|---|---|---|
| 入口（LB/反代/域名解析） | <是/否> | <全站不可用?> | <双入口/多 A 记录/切换脚本> |
| 应用实例 | | | |
| 数据库 | | | |
| 缓存 | | | |
| 消息队列/定时任务节点 | | | |
| 存储/对象存储 | | | |
| 外部依赖（第三方 API/模型/支付） | | | <降级或熔断策略> |

**接受单点必须写理由**（成本/业务容忍度/临时性），不能空着。

### 7.2 高可用要求（按档取舍）

- **应用无状态化**：会话外置（Redis/DB/令牌），多实例可横向扩，健康检查 + 自动重启/驱逐
- **入口冗余**：负载均衡/反向代理不只一个实例；DNS 切换方案与 TTL
- **数据层**：主从/副本 + **复制延迟监控**；只读副本可用性；故障切换后**一致性校验**（数据工程师 skill §8 联动）
- **依赖降级**：第三方不可用时降级或熔断（不能一挂全挂）

### 7.3 故障转移剧本与演练（纳入 §6 门禁）

- 每个单点给"故障发生时的动作 + 判据命令 + 切换后校验"，与 §4.4 切流/回滚剧本同格式
- **首次上线前至少演练一次故障转移**（实例/入口级；无法演练的能力**标注"未验证"**，不得默认可用）
- 演练记录与 §6 同口径（`问题/事故报告/演练-*.md`；隔离环境执行，生产只做只读探测）

### 7.4 与 §1.3 / §6 的边界

- **容量阈值与水位**归 §1.3（本节不重复定义）；扩容触发阈值进 `契约/配置中心.md`
- **回滚与备份恢复演练**归 §6；本节只管**高可用与故障转移**
- **库侧容量与副本一致性**由数据工程师出实测数字（其 skill §8）
