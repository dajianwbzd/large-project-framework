# 代码风格与命名一致性（Code Style Contract，v3.22.0 → **v5.5.0 补齐判据与覆盖面**）

> 架构师产出。在 **②a 期一次性定档**（与 `技术栈.md` / `配置中心.md` / `数据模型.md` 同期），定档后即为**本项目命名的单一事实来源**。
> **治什么问题**：多角色并行（前端/后端/集成/测试各写一套）时命名必然漂移——同一项目里 `camelCase` 与 `snake_case` 混用、表名/列名/接口路径/常量/文件名各写一套、同一个字段在 DB/Python/JSON/TS 四层里四个名字、重构与新增互相打架。风格不统一不阻塞编译，却让每次改动都要先"考古"一遍，让复查无从判"对错"——**没有定档的风格，任何命名都是对的，于是全都不一致**。
> **机器核验**：`python scripts/style_audit.py <项目根>`（**只报告不改动**）——读本文 §0 的 JSON 定档块做判据；**文件缺失或定档块缺失时退回框架默认风格，并在报告首行明确标注"判据来源=框架默认（非项目定档）"**，不假装是项目契约。
> **v5.5.0 补齐了什么**（2026-09-19 代码风格打磨）：① §0.2 里 8 个"声明了但脚本从不读"的键（`json_field`/`path_param`/`env_var`/`synonyms`/`conversion.*`/`sql`/迁移模板）**全部接上判据**；② 覆盖面补 `.vue` / `.scss|.less` / `.gd` / `.c|.h` / `.sh|.bat` / `.ps1` / Dockerfile / compose / CI / `.env`；③ 加 `--since`（本卡新增口径）与**行内豁免**；④ 加 `scripts/tests/test_style_audit.py`（变异对拍 + 反向对拍）——此前它是唯一没有回归测试的检查器。
> **L0 摘要**：本项目语言清单 → 每语言命名风格 → DB/接口/JSON 各层风格 → **位置判据（positions）** → 转换层位置 → 基础设施文件（infra）→ 例外登记表。改风格属**结构变更**。
> 配套：`api设计规范.md`（接口怎么设计，含 JSON 字段风格）· `配置规范.md`（怎么配置）· `配置中心.md`（配置什么）· `数据模型.md`（表/列定义）· `代码复查规则库.md` 域 8（本文件的验收判据）。

## 0. 定档区（②a 期一次性定档；定档后新增代码一律照此）

### 0.1 定档表（架构师填，报用户确认）

| 项 | 取值 | 定档人 | 日期 |
|---|---|---|---|
| 语言清单 | <如 python / javascript(ts) / sql / css / **gdscript / c / shell**> | <架构师> | <YYYY-MM-DD> |

| 跨层转换层 | <如 `后端/api/serializers.py` + `前端/src/api/adapters.ts`> → **必须同步写进 §0.2 的 `conversion`** | <架构师> | <YYYY-MM-DD> |
| 位置判据 | <`positions.*` 是否按 §0.2.1 全部启用；`json_field` 的载荷边界是否要额外加白 `files`> | <架构师> | <YYYY-MM-DD> |
| 基础设施文件 | <是否采纳 `infra.*`（Dockerfile/compose/CI/shell 命名）；不采纳则显式写 `any`> | <架构师> | <YYYY-MM-DD> |

> **语言清单必须钉到项目实际会写出来的语言**：`design_profile: game` 的项目要显式定档脚本语言（GDScript `.gd` / C# / C++），否则"风格线"对该项目等于没有（实测：某游戏工程 1234 个 `.gd` + 1209 个 `.c` 在旧版判据里一条都不查）。
> **不采纳某项也要写 `any`**——留空与 `any` 是两件事：前者是"没定"，后者是"定了不检查"。

### 0.2.1 v5.5.0 新增的三块判据（此前"契约写了、脚本不读"）

> 背景（2026-09-19 代码风格打磨）：用覆盖率审计回查 970 行的 `scripts/style_audit.py`，发现 §0.2 里有 **8 个键"声明了但从不读"**——`json_field` / `path_param` / `env_var` / `synonyms` / `conversion.modules` / `conversion.files` / `sql` / 迁移模板。这正是"假保护"（同型缺陷在本框架史上已出现两次：`workspace_hygiene` 的硬保护、`guide_audit` 不读 `guidance`）。v5.5.0 把这些判据全部接上，并补齐覆盖面。

| 键 | 判什么 | 取值口径 |
|---|---|---|
| `positions.json_field` | JSON 字段 casing（**只在可判定的载荷边界内**：目录名 ∈ api/clients/serializers/responses/dtos/adapters、或文件名以 serial/response/payload/dto/adapter 开头、或含 client；判不出就不判） | `camelCase`（须与 `api.yaml` 逐字一致） |
| `positions.env_var` | 环境变量的**定义处**（`.env*` 键 / `os.getenv` / `process.env` / `import.meta.env` / compose `environment:` 块 / Dockerfile `ENV`） | `UPPER_SNAKE`；`allow` 列平台自带变量（`SystemRoot` 等，项目无权改名） |
| `positions.error_code` | 错误码常量值 + 响应体 `"code"` 值（**只在代码文件内**，不判证据/结果 json） | `UPPER_SNAKE`（依据 `api设计规范.md` §2） |
| `positions.config_key` | 配置键字符串（`config.get("a.b")` / `CFG["a.b"]`） | 全小写，点分**可选**（`api.paths.auth_login` 与 `timeout` 都合规；反例 `api.paths.authLogin`） |
| `positions.event_name` | 事件 / topic 名（`publish/emit/subscribe/dispatch` 实参） | 全小写，点分可选（反例 `UserCreated`、`user_created_event`） |
| `positions.cache_key` | 缓存 key 字面量（`cache/redis.get(...)`） | `<域>:<标识>` 小写（`cache:user:42`；反例 `Cache_User_42`） |
| `positions.prompt_id` | 提示词资产首行 `<!-- id: … -->` + `配置中心.md` 的 `prompt.*` 注册表 | `<域>.<用途>.vN`（`scan.classify.v3`） |
| `positions.path_param` | 路由参数名（`:x` / `{x}`） | 随宿主语言：py/gd/c `snake_case`、js/ts `camelCase` |
| `conversion.modules` / `conversion.files` | **唯一允许的转换点**：同文件里 snake/camel 双写，只有落在名单内才不报；跨文件并存时两侧都不在名单才报 | 模块名或相对路径（支持 glob） |
| `synonyms` | 禁用同义词出现在标识符/字段名里即报（`memberId`、`member_id` 命中；`membership` 不命中） | `{"采用名": ["禁用词", …]}` |
| `infra.*` | 基础设施文件命名：Dockerfile 的 `ENV/ARG/LABEL` 键与多阶段 stage 名、compose 服务名、CI job 名、shell 函数名 | 见 §1.5 |

**`where` 的合法取值**（写错会被报告出来而不是静默忽略）：`json_key` / `env_file` / `getenv` / `compose_env` / `error_code` / `config_key` / `event_topic` / `cache_key` / `prompt_header` / `prompt_registry` / `route_param`。
**casing 词表**（写错同样会被报告）：`snake_case` / `camelCase` / `PascalCase` / `UPPER_SNAKE` / `kebab-case` / `flat` / `cobol` / `lower_dot` / `cache_key` / `prompt_id` / `any`（多值用 `|`）。

### 0.3 一条纪律（写在最前，因为它最常被违反）

1. **定档后，新增代码一律照此**——包括"临时写的""先跑通的""下版再收拾的"代码。风格债不因"以后会改"而免罚。
2. **改风格 = 结构变更**：走 CR + 用户确认 + 同步更新本文件 §0.2 + 记 `记忆/变更日志.md`（c-xxx）+ 重跑 `style_audit.py` 并留证，**不许在新卡里顺手换一种风格**。
3. **例外必须登记**（§4）——**没有登记的例外就是违规**，复查按 `代码复查规则库.md` 域 8 打回。
4. 存量代码与新定档冲突时：**不要求一次性重写**（那是范围夹带），按"新增照新规、触达即改"执行，并把存量违例登记为 §4 例外（带到期时间）或立专项卡。
5. **判据要么真查、要么写明不查**（v5.5.0）：任何写进 §0.2 的键都必须有机器判据；做不到就用 `any` 显式声明"不检查"，**不许留一个"看起来在管、实际不查"的键**（这类假保护比没有更危险——人会照着它放心）。casing 词与 `where` 采集位写错会被报告出来，不静默忽略。
6. **本卡新增口径**：`--since <git-ref>` 只报本次新增/改动的命中（契约 §3.3 清单要求的是"**本次新增**无未登记命中"，拿全量结果去对会扯皮：存量问题会被算到本卡头上）。**存量命中不因"是历史代码"而免责**——要么登记 §4 例外，要么立专项卡。
7. **行内豁免**（`style-audit: off[: rule]` … `on`，**只在注释里生效**）用于单行误报，颗粒度到行；它与 §4 例外表（颗粒度到文件/规则，需理由 + 批准人 + 到期）是两套。**行内豁免必须在该行写明为什么**——报告会单列"行内豁免"清单供集成工程师复核，**不写理由等于把违规藏起来**。

## 1. 命名规则矩阵

### 1.1 语言内命名（取值 + 正例 + 反例）

| 类别 | 取值（本档） | 正例 | 反例（为什么错） |
|---|---|---|---|
| 变量 | python/DB `snake_case`；js/ts `camelCase` | `cover_sub`（py）/ `coverSub`（js） | `coverSub` 出现在 Python、`cover_sub` 出现在 JS（跨语言串味，读的人以为层搞错了） |
| 函数 / 方法 | python `snake_case`；js/ts `camelCase` | `build_cover_page()` / `buildCoverPage()` | `buildCoverPage()` 写在 `.py`、`build_cover_page()` 写在 `.js`（同目录混用即判漂移，见域8 检查点 4） |
| 类 | 全语言 `PascalCase` | `class CoverSpec` / `class CoverSpec {}` | `class cover_spec` / `class coverSpec` |
| 接口（抽象/协议/类型） | 全语言 `PascalCase`（js/ts 类型另可 `I`/`T` 前缀须统一） | `interface CoverRenderer`、`class CoverRepo(Protocol)` | 同一项目里 `ICoverRenderer` 与 `CoverRenderer` 并存（两套前缀 = 两种约定） |
| 常量（模块级、值不再变） | `UPPER_SNAKE` | `MAX_COVER_TITLE_LEN = 24` | `maxCoverTitleLen = 24` / `max_cover_title_len = 24`（模块级常量用变量风格，改的时候没人敢动） |
| 枚举类型 | `PascalCase` | `class ExportFormat(Enum)` | `class EXPORT_FORMAT` |
| 枚举成员 | 全语言 `UPPER_SNAKE` | `ExportFormat.PDF`、`ORDER_STATUS.PAID` | `ExportFormat.Pdf`、`ORDER_STATUS.paid`（成员值可以小写，**成员名**要 UPPER） |
| 模块 / 文件名 | python `snake_case.py`；js/ts `kebab-case.js`；sql `snake_case.sql` | `export_center.py`、`export-center.js` | `exportCenter.py`、`export_center.js` 混在同一目录 |
| 目录名 | `kebab-case` 或 `snake_case`（**同项目择一，同级不混**） | `services/`、`team-config/` | 同级出现 `team_config/` 与 `team-config/`（两个同义目录，半年后没人知道该进哪个） |
| 测试函数 | python `test_<被测>_<场景>`；js `any`（描述式） | `def test_compress_keeps_original_when_flagged()` | `def test1()`（名字不表意，失败时无法定位） |

### 1.2 数据库命名（唯一事实来源 = `数据模型.md`）

| 类别 | 取值 / 模板 | 正例 | 反例 |
|---|---|---|---|
| 表名 | `snake_case`，**复数**，业务前缀不加（非多租户系统不写 `t_`/`tb_`） | `point_transactions`、`team_invites` | `PointTransactions`、`pointTransaction`、`t_point` |

### 1.4 跨语言示例（同一个概念在四层里各叫什么 —— 本档一次性给定）

概念：**封面副标题**（`数据模型.md` 中的列 / `api.yaml` 中的字段 / 后端变量 / 前端变量 / 样式名）

| 层 | 名字 | 依据 |
|---|---|---|
| DB 列 | `cover_sub` | §1.2 |
| Python（模型/服务） | `cover_sub` | §1.1 |
| API JSON 字段 | `coverSub` | `api设计规范.md` §1（转换点在序列化层，见 §2） |
| TypeScript / JS | `coverSub` | §1.1 |

## 2. 跨层映射与转换纪律（最易漂移处）

**唯一允许的转换点**：写入 §0.2 `conversion.modules` / `conversion.files` 的模块。默认 = 序列化层。
**这份名单是判据、不是文档**（v5.5.0 起）：`style_audit.py` 读它——
同文件里 snake/camel 双写、只有落在名单内才不报；跨文件两版并存、两侧都不在名单才报；
**名单里写了却找不到对应模块**（`conversion-blindspot`）也会报，治"填了不算数"。

| 边界 | 谁转 | 禁止 |
|---|---|---|
| DB 列（`snake_case`）→ 领域对象（Python `snake_case`） | ORM / 数据访问层 | 业务代码手写列名映射 |
| 领域对象（`snake_case`）→ API JSON（`camelCase`） | **序列化层**（`serializers.py` / `adapters.ts`，**唯此一处**） | 在 service / router / 组件里手拼 `{"coverSub": row["cover_sub"]}` |
| API JSON（`camelCase`）→ 前端状态（`camelCase`） | 前端 API 客户端（`src/api/*`） | 组件里对响应字段做 `snakeToCamel(response)` |
| 前端 → 请求体 | 同上 | 在事件处理里拼 DB 字段名 |

**纪律条目**：

1. **转换只在一个地方做，且那个地方要知道两个名字**——转换点之外出现 `snake_case` 与 `camelCase` 的同义双写，即判跨层漂移（域 8 检查点 2）。
2. **禁同义多词**：同一实体全项目一个名字，三选一后写进 §0.2 `synonyms`（形如 `{"user": ["member", "account"]}` = 采用 `user`、禁用后两个）。反例：`user` / `member` / `account` 指同一张表；`cover_sub` / `subtitle` / `sub_title` 指同一列。发现第二套叫法 → 走 CR 统一，不并存。
3. **禁止"双份字段兼容"**：同一响应同时返回 `cover_sub` 与 `coverSub` 属**契约违规**（向后兼容靠版本化，不靠双份字段，见 `api设计规范.md` §4）。
4. **字段新增的落地顺序**（顺序错就是漂移）：`数据模型.md` 列名 → `api.yaml` 字段名（camel）→ 序列化层映射 → 前端类型定义 → 前端使用。四步走完才算落地；只改了其中两三处 = 契约漂移（域 1 + 域 8 双命中）。
5. **配置键不随 JSON 变**：配置键与 JSON 字段是两套命名空间，不要为了"看起来一致"把配置键改成 camelCase（会破坏 `配置中心.md` 的键族一致性）。

## 4. 例外登记表

**纪律：没有登记的例外 = 违规。** 每条例外必须有理由、有批准人、有到期时间——**永久的例外不是例外，是没定的风格**（要么改风格定档，要么改代码）。
`style_audit.py` 会读本表：登记项不再作为违规报告；**到期日已过的例外重新报告为命中**。

| 路径（glob 或 `文件:行`） | 违反的规则 | 理由（为什么会这样） | 批准人 | 到期时间 |
|---|---|---|---|---|
| `<repos/legacy/old_export.py>` | 常量命名（历史遗留 snake 模块常量） | 存量文件待专项重构 card-0xx | <架构师> | <YYYY-MM-DD> |

> 写法：`路径` 支持 glob（`repos/legacy/*.py`）；`违反的规则` 填 `代码复查规则库.md` 域 8 的检查点名或 `style_audit.py` 的规则名（如 `const-naming`、`env-var-casing`、`json-field-casing`、`docker-env-key`；规则名与族见 `style_audit.py` 的 `RULE_LABEL`/`RULE_FAMILY`）；多条同名规则的例外要分行写。
> 到期处理：到期前由架构师裁决「改代码 / 续期（须再报用户）/ 升格为正式风格（改 §0.2 + 过用户确认）」，**不许默认续期**。
> **与行内豁免的分工**（v5.5.0）：本表**颗粒度到文件/规则**、需理由+批准人+到期，用于存量；单行误报用代码里的 `style-audit: off[: rule]` … `on`（**只在注释里生效**），报告会单列清单供复核。**两处都要求写清理由**——不写理由的豁免，验收时按违规处理。
