# 上下文规范（Context Engineering）

> 版本：v3.12.0（随大型项目开发框架 v3.12.0 模板复制到项目）
> 本文件规定**整个框架如何组织与读取上下文**（记忆/契约/思路/进度/需求卡都是上下文）。规范是"怎么组织"，`契约/上下文索引.md` 是"具体有哪些上下文 + 各自的 L0/L1"——两者配套，同 `配置规范.md` vs `配置中心.md`。
> 设计来源：借鉴 **OpenViking**（volcengine/OpenViking，self-evolving context database，`viking://` 虚拟文件系统）的核心思想——**L0/L1/L2 三层按需加载**、**目录递归检索**、**可观测检索轨迹**、**会话提交→自动提炼记忆**。适配到本框架"人可读 markdown + agent-managed 共享工作区"的形态。**不引入 OpenViking 运行时/CLI/SDK**（AGPL-3.0 传染性 + docker/web-studio/Rust 部署重量，见架构评估——本规范是纯"文档怎么写 + 怎么读"的约定，不添外部服务）。

## 1. 核心原则：上下文是预算

- 每个 token 都要花在刀刃上：**先判断相关性，再决定读多深**——读摘要就能决定的事，绝不读全文。
- 上下文分层是**预算纪律**，不是文档格式要求：它是写给读的人（主控/子代理）看的读取策略。
- 上下文贵在"够用"，不在"全"：给下个角色塞太多细节 = 污染上下文、挤占关键事实。

## 2. 三层分级（L0 / L1 / L2，内容深度而非优先级）

| 层 | 全称 | Token 预算 | 内容 | 什么时候读 |
|----|------|-----------|------|-----------|
| **L0** | Abstract 摘要 | ≈100 | 一句话"这份文档是什么、讲了什么结论" | 判断相关件性：要不要深入（扫 `上下文索引.md` 的 L0 列） |
| **L1** | Overview 概述 | ≈2k | 关键点/结论/适用场景/取舍（保留骨架，去掉细节论证） | 已确认相关：要掌握它讲了什么，但不需要每个细节 |
| **L2** | Detail 详情 | 按需 | 文档全文（例子/证据/展开论证/边界） | 需要落地细节/证据/边界时，才读全文 |

> **优先级 ≠ 深度**：`加载优先级`（高/中/低，见 `记忆/` 条目，约 200/100/50 tokens）回答"该不该读"；`L0/L1/L2` 回答"读到多深"。两者正交——一张记忆条目同时标（优先级 + 建议深度），检索时先按优先级决定是否纳入，再按深度决定读多细。

## 3. 每种上下文的 L0/L1 写法（怎么给文档打头）

各文档**顶部**加 L0 一行（`> L0 摘要：…`）；关键文档另加 L1 概述（`> L1 概述：…` 或正文要点段）；全文 = L2。未标注 L0/L1 的旧文档由主控在首次读取时补齐（按"先补最常被读的"排序，不阻塞开发）。

| 文档 | L0（≈100t，一行） | L1（≈2k，要点） | L2（全文） |
|------|-----|-----|-----|
| `记忆/决策日志.md` | 本条决策 + 一句话理由 | 决策背景/取舍/影响面 | 完整 ADR 论证 |
| `记忆/知识沉淀.md` | 本条沉淀的主题 + 一句话结论 | 结论/适用场景/示例 | 完整案例 |
| `记忆/变更日志.md` | 变更对象 + 一句话影响 | 变更内容/影响/回滚 | 完整 diff/上下文 |
| `记忆/角色/<角色>.md` | 本角色本项目的"习惯怎么做"一句话 | 固定约定/踩坑/风格各 2-3 条 | 全档案 |
| `契约/<契约>.md` | 本契约管什么 + 一句话要点 | 关键定义/约束/边界 | 全文 |
| `需求卡/card-NNN/思路-<角色>.md`（系统级测试轮：`测试卡/tc-NNN/思路-<角色>.md`） | 本卡本角色"怎么想、为什么"一句话 | 方案取舍/结果与偏差 | 六段全文 |
| `测试卡/tc-NNN/覆盖矩阵.md`、`发现项.md` | 本轮系统级测试覆盖了什么、发现几项 | 维度结果/发现项归属 | 全文 |

## 4. 目录递归检索（从目录命中再深入，而非平铺全扫）

- **先读索引**：主控/子代理检索上下文时，先读 `契约/上下文索引.md`（集中所有上下文 L0 摘要，token ≈ 一次 L0 全量），在**目录层面**定位目标（记忆/契约/思路/代码…）。
- **目录命中 → 逐层下钻**：确定在哪个子目录后，打开该目录下候选文档的 L0 → 判相关性 → L1 → 需要细节才 L2。逐层逼近，不一次把全部文档塞进上下文。
- **禁平铺全量**：禁止把 `记忆/`、`契约/`、`思路/` 下所有文档一次性读完再筛（等于放弃预算纪律）。

## 5. 可观测检索轨迹（retrieval trajectory）

- 每次重要检索都**留轨迹**：`读了哪个索引 → 命中哪个子目录 → 打开哪些文档（L0/L1/L2）→ 是否采用`。
- 轨迹写入：卡片「进展记录」或 思路文档 ② 段（"读过什么"），供 `契约/审核规范.md` S1（取证）与主控核查——**能追溯"为什么用了上下文 X"**（对齐"证据而非感觉"）。
- 无轨迹 = 无法证伪：检索结论也要指到"我是在哪份文档看到这个事实的"。

## 6. 会话提交→自动提炼记忆（session self-extraction）

每张卡完成（子代理收工 / 角色置 `done`）时，先跑一次**自提炼**再落盘，把"过程经验"沉淀为"可复用记忆"：

1. **提炼内容三问**：①本卡产生了什么**用户偏好/新约束**（用户反馈/口径调整/决策）；②本角色学到了什么**可复用模式**（更好做法/新踩坑/契约变更）；③是否有值得**升格**的（卡 → 角色档案 → 知识沉淀）。
2. **写成 L0 + L1**：提炼结果先写 L0（一句话结论）再写 L1（要点），落 `记忆/决策日志.md`（d-xxx，决策类）、`记忆/知识沉淀.md`（k-xxx，模式类）、`记忆/角色/<角色>.md`（本角色追加记录）。
3. **防遗忘/防静默**：提炼是**接卡必含步骤**，与"没有落盘 = 没干"同构——done 卡缺对应记忆条目（d-/k-/档案追加）视为未完成沉淀，主控打回。

## 7. 统一上下文视图（Context Index）

- `契约/上下文索引.md` 是**唯一入口**：集中每个上下文文档的 L0 摘要 + 路径 + 建议深度，主控/子代理一次读取即掌握"工作区有什么、在哪、读多深"。
- 索引与 记忆/契约/思路 同步：新增/变更文档 → 更新索引 L0（主控统一维护，参照 agent-managed storage 规则）。
- **先索引后文档**：任何"找上下文"动作，先读索引定位，不直接 grep/平铺翻文件。

## 8. 预算红线（red lines）

1. 读上下文前不先判断相关性（拿到就全读）= 放弃预算纪律。
2. 把 `加载优先级`（该不该读）和 `L0/L1/L2`（读到多深）混为一谈。
3. 一次检索不记轨迹（读了哪些、为何采用）——检索结论不可证伪。
4. 收工不提炼（done 卡无 d-/k-/档案追加）——经验不沉淀，下张卡重踩。
5. 索引与实际文档脱节（索引旧/不全）——回退"平铺全扫"。

## 9. 自检清单（写/改上下文时逐项对照）

- [ ] 新增 记忆/契约/思路 文档是否带 L0 一行（≈100t）？关键文档是否带 L1 概述（≈2k）？
- [ ] `契约/上下文索引.md` 是否已登记该文档（路径 + L0 + 建议深度）？
- [ ] 检索是否"先索引定位 + 目录命中再深入"，而非平铺全量？
- [ ] 重要检索是否留轨迹（读了哪、为何采用）？
- [ ] 收工是否先提炼（用户偏好/可复用模式/升格）再落盘？
- [ ] 是否遵守预算（L0≈100t / L1≈2k / L2 按需）？

## 10. 编辑流（如何落地）

- 主控/角色按「工作区约定」维护：缺索引补索引、缺 L0/L1 补 L0/L1（优先补最常被读的：记忆/契约 头部）。
- **不引入新运行时**：本规范只约定"文档怎么写 + 怎么读"，不引入 OpenViking 服务/CLI/SDK。
- 后续项目若真到"几千份文档/跨整库检索"量级，可在**该项目**把 OpenViking 作为可选加速器（记忆仍落 markdown 事实源），属项目级选型、非框架核心。
