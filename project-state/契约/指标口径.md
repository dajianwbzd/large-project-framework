# 指标口径（Metric Spec）

> 数据工程师产出并维护（v3.22.0）。**一个指标一行，本文件是指标口径的唯一事实源**——同一个指标名在全项目只允许一套算法。
> **治的问题**：同一个"活跃用户数"在两个页面算出两个数（口径无人定义）——页面/接口里的算法是「实现」，本文件是「口径」，二者不一致即 bug。
> 与 `契约/配置中心.md`（v3.11.0 零硬编码）配套：口径涉及的**阈值/枚举/默认值**不在公式里写魔数，登记配置中心后引用（如 `biz.register_bonus`）。
> 用法：先定口径 → 再写只读 SQL → 再出报表 → 与用户确认口径。**跳过本文件直接出报表 = 返工。**

## 1. 字段说明（每行一个指标的固定列）

| 列 | 含义 | 硬性要求 |
|---|---|---|
| 指标 id | 稳定标识（`M-NNN`），永不复用、永不改号 | 废弃标 `deprecated`，不删行 |
| 中文名 | 报表/页面展示名 | 全项目唯一，两个页面叫同一个名 = 必须同口径 |
| 业务定义 | 一句话人话（业务方看得懂） | 不许写"就是那个数" |
| 计算公式 | **可执行 SQL**（或可执行伪代码），含取整/去重/聚合规则 | **必须实跑过**并把结果登记进附录 B |
| 数据源 | `表.字段`（多表列全），标明主表（粒度由主表定） | 不许只写"数据库" |
| 粒度与维度 | 主表粒度（用户/订单/天）+ 可下钻维度（按天/按团队/按 skill） | 去重方式显式写明（`COUNT(DISTINCT ...)` / 主键计数） |
| 时间口径 | **自然日 or 滚动 N 天/月**；**时区**（存储 UTC / 展示本地 / 报表按哪个时区日切）；边界规则（含首含尾） | 跨时区不指定 = 日切数字漂移，直接打回 |
| 排除规则 | 测试账号 / 内部用户 / 已删除（软删）/ 已禁用 / 退款单 等的排除清单 | 写"排除测试账号"必须给可执行判据（如 `username LIKE 'test_%'`） |
| 负责人 | 口径解释与变更的责任角色（数据工程师 + 业务侧确认人） | 争议时以此人为准 |
| 版本 | 从 `v1` 起，口径变更递增 | 变更必须留痕（见 §3） |
| 变更记录 | 谁 / 何时 / 为何改 / 历史是否回溯 | 见 §3 纪律 |

## 2. 指标清单（一个指标一行）

| 指标 id | 中文名 | 业务定义 | 计算公式（可执行 SQL / 伪代码） | 数据源 | 粒度与维度 | 时间口径 | 排除规则 | 负责人 | 版本 | 变更记录 |
|---|---|---|---|---|---|---|---|---|---|---|
| M-101 | 注册用户数 | 当前可登录的注册账号总数 | `SELECT COUNT(*) FROM users WHERE disabled = 0` | `users.id, users.disabled` | 用户（去重=主键计数）；维度：按 `users.created_at` 日/月 | 累计值（无窗口）；时区=存储 UTC，报表按本地日切（显式声明） | 排除 `disabled = 1`（禁用）、`username LIKE 'test_%'` | 数据工程师 + 产品确认 | v1 | v1 2026-01-01 数据工程师 初版 |
| M-102 | 交易额（成交口径） | 已成交订单的实付金额合计（含退款前） | `SELECT COALESCE(SUM(price_paid),0) FROM orders WHERE status IN ('paid','shipped')` | `orders.price_paid, orders.status, orders.created_at` | 订单行；维度：按天/按 `orders.team_id` | 滚动 30 天 or 自然月（**口径字段必须二选一并写死**）；时区=UTC 存储、报表指定日切时区 | 排除 `status='cancelled'`、测试账号；**退款不扣减**（另立"净交易额"指标，不混用） | 数据工程师 + 财务确认 | v1 | v1 2026-01-01 初版 |
| M-103 | 次日留存率 | 新注册用户次日仍有业务行为的比例 | 分子 `COUNT(DISTINCT user_id) FROM events WHERE day = 注册日 + 1`；分母 `COUNT(*) FROM users WHERE 注册日 = D`；留存率 = 分子/分母（分母为 0 记 `NULL` 不记 0） | `users.created_at`、`events.user_id, events.created_at` | 用户（去重）；维度：按注册日分组（cohort） | 自然日（**cohort 按注册日**，非滚动）；时区=UTC 存储，day 边界按声明时区 | 排除 `disabled=1` 与测试账号；被删用户不计入分母 | 数据工程师 + 产品确认 | v1 | v1 2026-01-01 初版 |

## 3. 口径变更纪律（改口径 = 变更，四件事缺一不可）

| # | 动作 | 具体要求 |
|---|---|---|
| 1 | 记版本 | `版本` 列递增：语义/算法变更 → `v1→v2`；仅措辞澄清、示例补充 → `v1→v1.1`。**旧行不删**，变更记录写明一行 |
| 2 | 写变更记录 | `谁 / 何时 / 为何改 / 改了什么`（例：`v2 2026-03-01 数据工程师 排除测试账号，因 M-101 与报表差异 12`） |
| 3 | 通知消费方 | 按 §4 消费方登记表**逐个通知**（CR 或卡片），消费方未同步即线上两个数——通知记录进卡片「进展记录」 |
| 4 | 声明是否回溯 | **回溯**：按新口径重跑历史报表并在报表上标注差异；**不回溯**：在口径行写清「新旧口径分界日期」。二选一必写，不许含糊 |

**禁止清单**：
- ❌ 不通知消费方就改算法（含"顺手优化 SQL"）
- ❌ 两个指标名、同一算法（应合并为一条，避免两处维护）
- ❌ 一个指标名、两套算法（**必须拆分或废弃其一**——这正是"同一个数字两个数"的根因）
- ❌ 公式写"约""大概""视情况"；口径里出现不可执行描述
- ❌ 口径 SQL 与报表 SQL 不是同一条（报表必须引用口径公式，不许各写各的）
- ❌ 只改报表不改口径表（口径表反向漂移）

## 4. 消费方登记（谁在消费这些口径）

| 指标 id | 消费方（页面/接口/报表） | 消费方式 | 最后同步版本 |
|---|---|---|---|
| M-101 | `<前端页面 / 后端接口路径 / 报表文件>` | `<接口字段 / SQL 引用 / 报表 SQL>` | `v1` |

> 口径变更时按本表逐个通知；**消费方登记不全 = 变更通知不全 = 制造"两个数"**。

| M-001 | 注册用户数 | 当前可登录的注册账号数 | `SELECT COUNT(*) FROM users WHERE disabled = 0` | `users.id, users.disabled` | 用户（主键计数）；维度：按 `users.created_at` 日月、按 `users.team_id` | 累计值；存储 UTC（`...T..:..Z`），报表日切时区须显式声明 | 排除 `disabled=1`；测试账号须补判据（当前库无前缀规范） | 数据工程师 + 产品确认 | v1 | v1 2026-09-10 初版（来源 `schema_migrations` v1~v6 建表） |

### A.1 同名不同算法的真实案例（本库实测，正是"两个页面两个数"）

| 叫法 | 算法 | 实测值 | 差异根因 |
|---|---|---|---|
| 活跃用户数（页面 A：登录口径） | `SELECT COUNT(DISTINCT user_id) FROM sessions WHERE created_at >= <30天边界>` | **4** | 只要点过登录/刷新过会话就算 |
| 活跃用户数（页面 B：业务口径） | `SELECT COUNT(DISTINCT user_id) FROM point_transactions WHERE created_at >= <30天边界>`（即 M-005） | **2** | 必须有积分流水才算 |

> **结论**：两者都"没错"，错在**同名**。处置二选一——①拆成两个指标名（`活跃用户数(登录)` / `活跃用户数(业务)`）并各自登记；②定唯一口径、另一个页面按口径改。**不许两个页面各叫"活跃用户数"**。

### A.2 对账发现（真实 finding，交责任角色处置）

账实相符检查：`users.points`（主表余额）vs `SUM(point_transactions.delta)`（流水累计）：

```sql
SELECT u.id, u.username, u.points,
       COALESCE(SUM(t.delta),0) AS ledger_sum,
       u.points - COALESCE(SUM(t.delta),0) AS diff
FROM users u LEFT JOIN point_transactions t ON t.user_id = u.id
GROUP BY u.id ORDER BY u.id;
```

实测（2026-09-10）：`user 1 admin diff=0` · `user 2 lawyer1 diff=+405` · `user 3 lin2 diff=+60` · `user 4 zhouran diff=-825`

| 项 | 结论 |
|---|---|
| 差额 | 4 个用户中 3 个不为 0（最大 -825） |
| 可能原因 | 注册赠送初始值未入流水（user 3 完全无流水但 `points=60`）/ 历史回填 / 重复发放（`register_bonus` 同一用户出现 5 次） |
| 处置 | **数据工程师只出结论与证据，不改数**——交后端核对事务与回填逻辑；需修数据则提 SQL 修改申请单 |
| 状态 | 未闭环（登记为 finding，责任人：后端开发） |
