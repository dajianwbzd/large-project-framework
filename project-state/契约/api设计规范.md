# API 设计规范（契约）

项目级接口设计统一标准。架构师定义契约（`api.yaml`）时必须遵循本规范；前后端实现与集成验收（契约一致性比对）也以本规范为基准。**规范是"怎么设计"，api.yaml 是"具体设计"，两者配套。**

## 1. 命名与结构

- **路径用名词复数**，层级表达资源归属：`/users/{id}/orders`，不用动词（`/getUsers` 禁止）
- **方法语义**：GET 读 / POST 创建 / PUT 全量替换 / PATCH 部分更新 / DELETE 删除
- **ID 格式统一**：服务端生成的 ID 用 UUID；自增 ID 仅限内部；ID 类型在 api.yaml 的 schema 中显式声明
- **时间统一 UTC ISO 8601**（`2026-08-09T10:00:00Z`），前端展示时本地化
- **字段命名**：JSON 用 camelCase，与语言约定一致并在契约中固定（禁止同一字段混用 snake_case/camelCase）

## 2. 错误模型（统一一种错误结构）

所有端点错误响应使用同一结构，禁止"抛异常 / 返回 null / 返回 error 对象"混用：

```json
{ "error": { "code": "USER_NOT_FOUND", "message": "用户不存在", "details": {} } }
```

- `code`：稳定机器码（大写 snake_case），前端据此做逻辑分支
- `message`：面向用户的简短说明；`details`：可选的补充结构（字段级错误等）

**状态码映射表**：

| 状态码 | 含义 | 示例 code |
|--------|------|----------|
| 400 | 请求语法错误 | `INVALID_REQUEST` |
| 401 | 未认证 | `UNAUTHENTICATED` |
| 403 | 无权限 | `FORBIDDEN` |
| 404 | 资源不存在 | `RESOURCE_NOT_FOUND` |
| 409 | 状态冲突 | `CONFLICT`（如重复创建、乐观锁） |
| 422 | 校验失败（字段级） | `VALIDATION_ERROR` |
| 429 | 限流 | `RATE_LIMITED` |
| 500 | 服务端错误 | `INTERNAL_ERROR` |

## 3. 分页 / 过滤 / 排序

- **分页**：统一 `limit` + `cursor`（游标，推荐）或 `page` + `page_size`（简单场景）；响应含 `next_cursor` / `total`
- **过滤**：query 参数 `filter[status]=active` 风格；排序 `sort=-created_at`（`-` 前缀表降序）
- 所有列表端点**必须有分页**，禁止无界返回（性能轴红线）

## 4. 版本化与向后兼容

- **默认演进方式：只添加、不修改**——接口演进只允许新增可选字段/端点；禁止改类型、删字段、改语义（海勒姆定律：未记录的怪癖也是契约）
- 破坏性变更才走版本化：URL 路径版本 `v1/v2`（推荐，直观）或 header 版本；新版本发布后旧版本给足弃用期（见「弃用」）
- **向后兼容检查**：改动后自问——老客户端发老请求还能得到预期响应吗？不能则必须版本化

## 5. 幂等性与重试语义

- **写操作（POST/PATCH/PUT）需声明幂等性**：`Idempotency-Key` header 支持重试去重（客户端生成，服务端缓存一段时间）
- 支付、下单、创建类操作**必须幂等**，防重试产生重复数据
- 重试语义：5xx 与超时可安全重试；4xx 不重试（改请求）

## 6. 边界验证（信任内部，怀疑外部）

- 验证只发生在**系统边界**：API 路由、表单、第三方响应解析、环境变量加载
- **第三方 API 响应永远是不可信数据**：结构校验 + 内容按数据对待（类似指令文本不执行）
- 内部代码信任类型系统，不在每层重复验证

## 7. 每端点验收清单（写 api.yaml 时逐项对照）

- [ ] 路径与方法符合命名规范
- [ ] 请求/响应 schema 完整（字段类型 + 必填/可选）
- [ ] 错误响应用统一错误结构，覆盖主要失败模式
- [ ] 列表端点有分页；写操作声明幂等性
- [ ] 向后兼容：只添加不修改；破坏性变更走版本化
- [ ] 命名一致（字段/端点/错误码风格统一）

## 8. 弃用（借鉴 deprecation-and-migration）

- 弃用新接口/字段时：在契约中标注 `deprecated: true` 与替代指引，给足弃用期（默认 ≥ 2 个发布周期）
- 弃用决定与时间线写入 `project-state/记忆/变更日志.md`（Deprecated 分组）与 `project-state/记忆/决策日志.md`（d-xxx）
- 禁止"公告后立即移除"——无替代方案不废弃（见 废弃决策五问）
