# 安全与数据规范（Security & Data Standard）

> 版本：v1（随大型项目开发框架 **v4.0.0** 模板复制到项目）
> **L0 摘要**：本规范定义项目级的**权限模型与审计日志、加密与密钥管理、敏感数据与隐私（PII 分级/数据出境/保留与删除）、依赖许可与 SBOM**四件事——它们是横切关注点，**必须有一个设计者**（架构师定档），否则安全审计与测试卡有判据、判据本身却无人定义。
> **适用判定**：§0 定档区逐项声明；**涉及认证/授权、敏感数据、合规目标、对外交付的项目不得整篇留空**（留档并在 §0 写明"不涉及"的理由，不得删除本文件）。
> **为什么有它**：v4.0.0 前的实测诊断——12 个角色 SKILL 与全部契约文件里「权限模型 / 审计日志 / 加密 / 密钥轮换 / PII / 数据出境 / 许可证 / SBOM」**几乎全部零命中**：后端只"按卡实现认证与权限控制"、架构师的数据模型只有表/字段/索引/约束，于是**测试卡 ⑤ 要测"权限与越权穿越"、安全审计要"审计认证和授权机制"，判据来源（权限矩阵）却没有定义者**。本文件补的就是这个定义者与载体。
> **与 `代码复查规则库.md` 的关系**：本文件是"设计成什么样"（契约）；域5 安全与资源、域10 异步与消息是"代码里查什么"（判据）。二者配套。
> **与 `审核规范.md` 的关系**：审核规范判"他说的是不是真的"（蒙混/幻觉/不落盘）；本文件判"安全与数据该定的有没有定、该做的有没有做"。

## §0 定档区（项目初始化时由主控 + 架构师填，结论写入 `config.json`）

| 项 | 取值 | 不填的后果 |
|---|---|---|
| **① 是否涉及认证/授权** | `是` / `否` | 是 → §1 权限矩阵与审计日志必填；否 → 写明理由 |
| **② 是否处理敏感数据（PII/密钥/财务/健康）** | `是`（列数据类别）/ `否` | 是 → §3 必填，且备份/日志/测试数据都按敏感物处理 |
| **③ 加密要求** | 传输 / 静态 / 字段级（可多选）+ 算法与密钥来源 | 是 → §2 必填；**不得以"内网""后端不对外"为由省略传输加密** |
| **④ 合规目标** | `无` / 个保法 / GDPR / 等保 / 行业规范（列条目） | 有目标 → 逐条给出落点（谁做什么证明符合） |
| **⑤ 是否对外交付代码或依赖清单** | `是` / `否` | 是 → §4 依赖许可与 SBOM 必填（甲方/开源合规审计会要） |
| **⑥ 是否含客户端交付（桌面/移动/游戏）** | `是` / `否` | 是 → 发布与分发按 `生产运维.md` §3 发布流程 / §0.3 分发型交付物清单 与 运维工程师 skill「发布与分发」执行 |
| **⑦ 数据出境** | `不涉及` / `涉及`（目的地 + 依据） | 涉及 → §3.3 必填；不确定 → question CR，**不默认传输** |

## §1 权限模型与审计日志（涉及认证/授权必填）

### 1.1 角色矩阵（唯一事实源，越权测试的判据来源）

> **禁止只在代码里散落 `if role == ...`**：权限判定必须有矩阵定义，代码实现与矩阵逐格对应。

| 资源 / 操作 | 角色A | 角色B | 未登录 | 资源属主 | 说明 |
|---|---|---|---|---|---|
| `GET /orders` | ✅ | ❌ | ❌ | 仅本人列表 | <一条说明> |
| `DELETE /orders/:id` | ✅ | ✅ | ❌ | 本人 | 属主可删自己的 |
| <...> | | | | | |

- **判定点**：认证方式（session/JWT/OAuth/API key）、令牌有效期与刷新、注销与失效；**每个受保护端点必须有一个判定点**，不得默认放行
- **资源归属校验**：越权不止"角色不对"，还有"角色对但不是自己的资源"——矩阵的「资源属主」列必须逐行填
- **多租户**：若有，写清租户隔离键与查询强制注入方式（跨租户读取 = Critical）
- **权限变更路径**：谁能改角色、改完如何生效（即时/下次登录）、如何审计

### 1.2 审计日志（记什么 / 留多久 / 谁能读）

| 事件类别 | 必记字段 | 保留期 | 可读角色 | 落盘位置 |
|---|---|---|---|---|
| 登录/登出/失败 | 时间、账号(掩码)、来源 IP、结果、关联 ID | <如 180 天> | 安全审计 / 运维 | <表或文件> |
| 权限变更 | 操作者、被改账号、旧角色、新角色、时间 | <不限/依法> | 安全审计 | |
| 敏感数据读写 | 操作者、对象、动作、结果、关联 ID | | | |
| 管理操作（配置/开关/发布） | 操作者、变更项、前后值 | | | |

- **审计日志与业务日志分离**：审计日志**只追加、不可改**（应用账号无 UPDATE/DELETE 权限）
- **不得记录**：明文密码、完整密钥/令牌、完整卡号、完整 PII（掩码规则见 §3.2）
- **失败也要记**：认证失败、越权拒绝必须留痕（否则无法发现暴力破解与探测）

## §2 加密与密钥管理（有加密要求必填）

| 场景 | 算法/协议 | 密钥来源 | 轮换周期 | 责任人 |
|---|---|---|---|---|
| 传输（对外） | TLS 1.2+（生产禁明文 HTTP） | 证书颁发/续期方式 | 证书到期前 <N> 天续 | 运维 |
| 静态存储（敏感表/备份） | <如 AES-256-GCM> | KMS / 环境变量托管 | <周期> | 运维 + 数据工程师 |
| 字段级（如身份证/卡号） | <算法> | | | 后端 |
| 口令/凭据存储 | bcrypt/argon2 等**加盐慢哈希**（禁 MD5/SHA1/明文） | — | — | 后端 |

- **密钥绝不入库、不入日志、不进提示词、不下发前端**（与 `配置中心.md` 环境变量清单、`代码复查规则库.md` 域5/域9 一致）
- **密钥轮换剧本**：如何换、换时服务如何不中断（双密钥并行窗口）、换完如何验证旧密钥失效——**密钥误入仓库时按"先轮换 → 再移除 → 视需要改历史"顺序**（`agent.md` 注意事项 23，禁倒序）
- **前端/客户端红线**：任何长期密钥不得打包进客户端（打包产物可被下载解包），模型 key 走服务端代理或短期票据

## §3 敏感数据与隐私（处理 PII 必填）

### 3.1 PII 分级表（字段级，唯一事实源）

| 字段/数据类别 | 级别（公开/内部/敏感/特敏感） | 存储要求 | 可见性（谁能看全值） | 日志/测试数据脱敏方式 |
|---|---|---|---|---|
| 手机号 | 敏感 | <加密/掩码> | <角色> | 保留后 4 位 |
| 身份证号 | 特敏感 | | | 全掩码 / 假值 |
| 邮箱 | 敏感 | | | 部分掩码 |
| <...> | | | | |

### 3.2 全链路脱敏纪律

- **日志**：默认**不落 PII 原文**（落则掩码 + 保留期）；错误体/堆栈同样脱敏
- **测试数据**：test 库数据必须来自 prod 同步**脱敏**数据或合成数据（`agent.md` 注意事项 14/15），**禁止把 prod 真实数据直接当测试样本**
- **导出/报表**：对外报表按 §3.1 的可见性列脱敏；报表文件本身按敏感物管理（落 `交付/` 时更需注意）
- **备份**：含 PII 的备份本身即敏感物（加密 + 访问控制 + 恢复演练时同样脱敏）

### 3.3 数据出境评估（涉及必填）

- 目的地/接收方、数据类型、依据（合同条款/告知同意/安全评估）、传输方式（加密）、留存与删除约定
- **不确定 → question CR，不默认发送**（与 `Prompt规范.md` §0⑤"用户数据可否发给第三方模型"同源：第三方模型调用同样属于数据出境/第三方处理）

### 3.4 保留与删除

- 每类数据的**保留期**（到期自动清理机制，不靠人记得删）
- **删除请求流程**（被遗忘权/注销）：谁能发起 → 删哪些表（含软删除、备份、日志、第三方副本）→ 多久完成 → 如何留证
- **注销 ≠ 逻辑删一条**：必须写明关联数据（订单/日志/缓存/检索索引/备份）的处置口径

## §4 依赖许可与 SBOM（对外交付或合规项目必填）

> **为什么有它**：`安全审计` 的"依赖审计"覆盖的是**漏洞面**（npm audit/pip-audit）；**许可证兼容性与组件清单**此前无主（`代码解析师` 的"依赖纪律五问"含许可证，但该角色声明"项目尚无源代码时不适用"，新项目与交付级清单缺人）。

- **许可证策略**：白名单（可自由使用）/ 灰名单（需评估，如 LGPL/MPL 的链接方式）/ 黑名单（禁入，如无许可/自定义限制条款）；**copyleft（GPL/AGPL）用于分发型产品前必须评估传染范围并留下结论**
- **SBOM 生成**（CI 中执行，产物留 `产物/`，对外版本落 `交付/`）：
  - Node：`npm sbom --sbom-format cyclonedx`（或 `npx @cyclonedx/cyclonedx-npm`）
  - Python：`pip-audit` 的依赖清单 + `cyclonedx-bom`；Java：`gradle cyclonedxBom`；Go：`go version -m` / `syft`
  - 无工具时**零依赖兜底**：锁定文件（`package-lock.json`/`poetry.lock`/`go.sum`）即最小清单，人工补许可证列并标"未用工具生成"
- **核查**：新增依赖必须在 `契约/技术栈.md` 或本表登记（名称/版本/许可证/引入理由）；引入黑名单许可证 = 打回；**"忘了看许可证""应该没事"不属于可忽略情形**
- **对外交付**：甲方要求时输出组件清单 + 许可证 + 已知漏洞结论（"跳过/未生成"必须显式标注，**跳过 ≠ 通过**）

## §6 机器核验（开发/审计照跑，输出贴卡卷宗 `证据/`）

```bash
# ① 无明文密钥/令牌入库（对照 git_audit.py 与 代码复查规则库.md 域5）
git grep -nE "(api[_-]?key|secret|password|token)\s*[:=]\s*[\"'][^\"']{8,}" -- . ':!*.example'
# ② 生产/对外地址不得明文 HTTP（除 localhost）
git grep -nE "http://(?!localhost|127\.0\.0\.1)" -- . || true
# ③ 敏感字段是否登记（PII 表 vs 代码/模型）
grep -rnE "(id_card|phone|mobile|email|bank_card)" 代码/ | head -50   # 逐条能在 §3.1 找到登记
# ④ 依赖许可证核对（Node 例；Python 用 pip-licenses）
npx license-checker --summary 2>/dev/null || echo "未安装 license-checker：标注「未验证」，不得当通过"
# ⑤ 密码哈希不得用弱算法
git grep -nE "(md5|sha1)\(" 代码/后端/ || true
```

**判定**：每条命中要么修复、要么走《忽略决策记录》（`问题/审核记录.md`），**无记录 = 未处理**。工具缺失/未安装时**显式标注"跳过"**，跳过不计入通过。
