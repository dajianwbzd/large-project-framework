# 代码复查规则库（域 1~10 可验证规则 + 踩坑即加规则 + 主动忽略决策闸门）

> **定位与分工**：本库是 `完成定义.md`「质量」维度的展开、集成工程师「五轴审查」中「正确性」轴的具体检查标准、安全审计的隐性 bug 补充、**UI设计师设计还原走查的客观判据（域7，v3.19.0）**、**代码风格与命名一致性的客观判据（域8，v3.22.0）**、**Prompt 与对话链契约的客观判据（域9，v3.22.0）**、**异步与消息的客观判据（域10，v4.0.0）**。
> 与 `审核规范.md` 的区别——**审核规范判"他说的是不是真的"（蒙混/幻觉/不落盘，他律）；本库判"代码本身好不好"（规则对/错）**。两条线独立：代码写得诚实但仍有隐患 → 本库抓；代码写得漂亮但撒谎 → 审核规范抓。二者都要过，才算验收。

## 一、怎么用（谁在什么时候跑）

| 使用方 | 时机 | 做法 |
|---|---|---|
| 开发角色（后端/前端） | 置 `done` 前自验 | 对照本库「与己相关的域」逐条自查，命中即修复；命中但决定忽略 → 写忽略决策记录（前端另必过 **域7**） |
| **开发角色（后端/前端，v3.22.0）** | **置 `done` 前自验 + 新增文件/表/接口/常量时** | **对照 域8 逐条自查**——命名是否照 `契约/代码风格.md` 定档、DB/接口/JSON 名是否符合模板、跨层转换是否只在序列化层、有无未登记例外（跑 `python scripts/style_audit.py <项目根>` 取证，**只报告不改动**） |
| **后端开发（含大模型交互的卡，v3.22.0）** | **置 `done` 前自验** | **对照 域9 逐条自查**——提示词 id/版本/单一事实源、输出契约与解析降级、注入防护、参数与理由、评测集回归记录（架构师负责对话链契约，测试工程师负责评测集与回归留痕） |
| **后端开发（含异步/消息/定时任务的卡，v4.0.0）** | **置 `done` 前自验** | **对照 域10 逐条自查**——消费幂等、重试上限、死信/失败归属、顺序与分区、定时任务防重、事务与消息一致性、背压、可观测、消息体版本与脱敏（设计归架构师，见 `契约/安全与数据.md`） |
| 集成工程师 | 五轴审查的「正确性」轴 | 对照本库逐域过一遍，输出 finding + 严重度（见其 skill 分级前缀） |
| 安全审计 | OWASP 之外的隐性 bug 面 | 本库补充安全未覆盖的并发/事务/空值/资源隐患（共同构成"上线前别翻车"清单） |
| **UI设计师** | **设计还原走查（`ui: true` 卡，⑥ 验收期）** | **以 域7 为客观判据**，在真实运行界面上逐条核 UI 还原与设计令牌一致性，结论落 `需求卡/card-NNN/验收-设计.md`（v3.19.0） |
| 主控 | 验收前置检查 | 抽查 done 卡是否有「复查记录」或「忽略决策记录」，缺失 = 未完成复查 |

**判定标准（每域通用）**：
- 条目**满足** = 通过；
- **不满足**但有明确反例/边界论证 = 修复，或走「主动忽略决策闸门」；
- **无证据** = 存疑，不静默放过（适用 `审核规范.md` 取证四问 S1，先取证再定）。

## 二、可验证规则域（域 1~10）

每域若干检查点，每条含四要素：**检查什么 / 为什么 / 怎么验证 / 严重度**。
> 严重度沿用框架全局标准：无前缀 = 必须修复；Critical = 阻塞上线；High = 尽快修；Medium = 中等；Low = 最佳实践差距。与 `集成工程师` 的五轴分级前缀一致。

### 域 1：需求对齐（requirements-review）

| 检查点 | 为什么 | 怎么验证 | 严重度 |
|---|---|---|---|
| 实现与卡片「验收标准」逐条可反查对应 | 多做的功能是浪费，遗漏的功能是违约 | 每条 AC 反查代码路径，AC 与代码双向可指 | 无前缀 |
| 无静默偏离契约（改了接口/字段/行为未经确认） | 契约是唯一真理来源，漂移=返工+联调崩 | diff 逐字段对照 `api.yaml` / `数据模型.md` | 无前缀 |
| 无范围夹带（改了任务外文件） | 顺手改=夹带变更，出问题无从定位 | git diff 文件清单 vs 卡片任务范围 | 无前缀（适用 S8） |

### 域 2：并发安全（concurrency）

| 检查点 | 为什么 | 怎么验证 | 严重度 |
|---|---|---|---|
| **check-then-act 竞态**（先检查状态再修改，中间被并发穿插） | 并发下重复/丢更新，"过了检查但被插队"是高发 | 解析读-判-写路径，找有无原子守卫/锁/事务 | Critical |
| 读-改-写非原子（`i++`、计数器、余额扣减、库存） | 并发叠加丢更新 | 定位自增/累加/扣减处，确认用了 `SELECT ... FOR UPDATE`/原子操作/乐观锁 | High |
| 共享可变状态无同步/无锁/无不可变设计 | 多线程改共享集合/单例/缓存 | 定位共享对象写入点，确认锁/原子类型/不可变 | High |
| 异步/重试重复执行（幂等性） | 重试造成重复扣减/重复下单 | 写操作有幂等键/唯一约束/去重 | High |
| 锁顺序一致（多把锁路径） | 锁顺序不一 → 死锁 | 枚举所有多锁路径是否同一顺序 | High |
| 缓存与 DB 一致性（先更缓存还是先库、失效策略） | 缓存与库不一致 | 确认双写顺序/失效/一致性策略 | Medium |
| 并发上限/线程池无界 | 无界并发 → 资源耗尽、雪崩 | 并发路径有线程池上限/信号量/限流 | Medium |

### 域 3：事务边界（transaction）

| 检查点 | 为什么 | 怎么验证 | 严重度 |
|---|---|---|---|
| 事务边界正确（一组写操作原子，全成或全滚） | 半成功 = 数据不一致 | 异常路径是否回滚；跨写操作是否同一事务 | High |
| 事务作用域过大/过小 | 大事务占连接长锁；小事务拆坏原子性 | 确认事务函数粒度；事务内是否有远程调用/耗时操作 | Medium |
| 不吞异常造成「假成功」 | catch 吞了 DB 异常却返回成功，数据其实没落 | 查异常捕获是否返回成功/吞异常 | High |
| 隔离级别与业务匹配（脏读/幻读对业务影响） | 隔离级过低读脏/不一致 | 按业务选取隔离级并说明理由 | Medium |
| 读改写一致（读旧值、写新值，须同事务/带版本） | 读与写不在同一事务 → 覆盖并发写入 | 乐观锁/版本号/或把读改写作进同一事务 | High |
| 重试幂等（事务重试重复扣减/插入） | 重复执行产生重复数据 | 幂等号/唯一约束/无则补 | High |

### 域 4：空值与边界（null-safety / edge cases）

| 检查点 | 为什么 | 怎么验证 | 严重度 |
|---|---|---|---|
| 可空返回链式调用 NPE | 最常见运行时崩溃 | 找链式 `.a().b().c()` 可空处，加 `?.`/null 检查 | High |
| 空集合 / 0 长度处理（遍历、first、取整、分页=0、平均） | 空输入路径崩 | 用空数组/空列表跑一次 | Medium |
| 字符串/数字边界（空串、负数、超长、精度、溢出、浮点比较） | 边界输入产生错误结果/崩 | 边界值测试（0/负/超大/精度） | Medium |
| 分页/游标（offset 越大、limit 越界、last_page 重复、页码越界） | 分页参数边界崩溃或性能 | 分页参数边界值测试 | Medium |
| 枚举/状态机非法转换、未知值默认分支 | 未知枚举导致异常/静默错误 | switch/if 全分支是否都有 default | Medium |
| off-by-one（循环、区间、索引起止） | 差一个位置 | 边界索引值测试 | Medium |
| 异常路径返回值与主路径一致（失败到底返回什么） | 失败路径返回诡异值/崩 | 检查错误处理路径的返回值 | 无前缀 |

### 域 5：安全与资源（security & resources）

| 检查点 | 为什么 | 怎么验证 | 严重度 |
|---|---|---|---|
| 注入（SQL/命令/模板/XSS） | 最高危 | 参数化/转义 —— 深扫点向 `安全审计` skill | Critical |
| 密钥/凭据泄漏（硬编码、日志、仓库） | 直接事故 | 扫 `.env`/`*.key`/`*.pem`/日志；提交前卫生 | Critical |
| 认证/授权缺失（越权、默认放行、未校验当前用户资源归属） | 越权访问 | 每个接口确认鉴权 + 资源归属校验 | Critical |
| 资源泄漏未释放（DB 连接、文件句柄、游标、socket、线程、锁） | 连接耗尽 → 系统崩溃 | try-with-resources / finally / 显式关闭 | High |
| 外部输入当指令（目录穿越、反序列化、提示注入） | 安全边界被突破 | 不可信输入一律校验/白名单 | High |
| 无界增长（无 limit 查询/循环、缓存无上限、日志无节流） | 内存/DB 膨胀 | 查询/循环有无 limit；缓存上限；日志限流 | Medium |
| 错误信息泄露内部细节（堆栈、表名、SQL、内部 URL） | 泄露架构信息 | 对外仅返回通用错误码 | Medium |

### 域 6：配置驱动（config-driven，零硬编码）

> **依据 `契约/配置规范.md`**：业务代码零硬编码——接口名与常量统一从 `契约/配置中心.md` + 各栈配置模块载入，代码只引用配置符号。三类值：跨模块接口名/业务常量 → 配置中心；环境值/密钥 → `.env`；仅此一处用值 → 允许内联（由架构师裁决）。

| 检查点 | 为什么 | 怎么验证 | 严重度 |
|---|---|---|---|
| 接口名非字面量内联（端点路径/路由前缀/事件 topic/表字段名/缓存 key 前缀） | 同一路径散落 N 处，改一次漏多处；接口名漂移 = 联调崩、契约不符 | grep 关键字面量（如 `"/users"`、`"/auth/login"`）定位内联处，确认经配置模块/常量表引用 | 无前缀 |
| 无魔法数字/业务常量内联（分页/超时/重试/限流/TTL/边界值） | 魔数无法统一调参、验收无法判定是否达标 | grep 裸数字/阈值，确认来自 `pagination.*`/`cache.*`/`timeout.*`/`limit.*` 配置 | 无前缀 |
| 状态/错误码/枚举/文案键从配置或常量表引用 | 枚举字面量漂移、错误码与契约不一致 | 查 `enum.*`/`code.*` 配置表与代码引用是否一致，错误码 vs `api.yaml` 对齐 | Medium |
| 同一接口名/常量未重复定义 | 多源定义必然漂移，改一处漏一处 | 同一路径/常量只在一处定义（配置中心），其余引用；重复定义即打回 | 无前缀 |
| 密钥/凭据走环境变量，无硬编码明文 | 直接事故 | 扫 `.env`/`*.key`/日志/代码字面量，git 历史无明文 | Critical |
| 新增配置已登记配置中心 | 未登记的配置 = 孤儿值，下个代理无从复用、无从统一调参 | 新增 key 与 `契约/配置中心.md` 对齐；缺登记即回退 | Medium |
| 配置中心与 api.yaml / 数据模型一致 | 契约与配置漂移导致实现左右矛盾 | 配置中的接口名/错误码 vs `api.yaml`、表/字段名 vs `数据模型.md` 逐项比对 | Medium |

### 域 7：UI 还原与设计令牌一致性（ui-fidelity，v3.19.0；v3.21.0 按设计域分叉）

> **依据 `契约/DESIGN.md`**：界面实现只引用**设计令牌符号**（`text-primary` / `spacing.md`），不把裸值抄进代码。
> **适用范围**：含用户可见界面的卡（`ui: true`）。**判据按设计域换**（见 `契约/设计域.md` §三）——§另注：
> - `web` / `mobile-native`：下表全部适用（含 WCAG 对比度、断点）
> - `desktop`：Web 部分沿用，另加**平台 HIG 遵从 · 快捷键表完整无冲突 · 窗口行为 · UIA/AX 辅助功能树可读（`aria-*` 不是唯一手段）**
> - `game`：**WCAG 静态对比度与浏览器断点不适用**；替换为**动态可读性（录像抽帧核）· 输入映射与重映射 · HUD 宽高比安全区 · 色盲模式与特效可关闭**
> **使用方**：前端置 done 前自验、**UI设计师设计还原走查（验收期主判据）**、集成工程师（界面相关卡）。
> **为什么有这一域**：域1~域6 全不看"界面是否照设计做"——设计规范写完没人回头核，样式漂移、漏状态、丢断点、a11y 缺失会一路漂到上线（v3.19.0 补此域前，全框架检索"还原/走查/视觉回归"零命中）。

| 检查点 | 为什么 | 怎么验证 | 严重度 |
|---|---|---|---|
| 视觉值引用令牌，无裸色值 | 裸 hex 散落各处则无法统一调色，改主题必漏；令牌是色彩的唯一事实源 | grep 十六进制/rgb（如 `#[0-9a-fA-F]{3,8}`、`rgb(`），确认来自令牌文件而非组件内联 | 无前缀 |
| 间距/圆角/阴影只用刻度值 | 自创值（`padding: 13px`）破坏节奏，无法随刻度统一调整 | grep 尺寸值，比对 `DESIGN.md` spacing/radius/shadow 刻度；刻度外即命中 | 无前缀 |
| 字体层级引用令牌（不散落 `font-size` 裸值） | 字号/行高漂移让视觉层级混乱 | grep `font-size`/`line-height`，确认来自 typography 令牌 | Medium |
| 组件取自组件库（无同类组件重复造） | 同语义两套按钮 = 样式与行为必然漂移 | 对照 `DESIGN.md`：同语义组件只有一处实现 | Medium |
| **状态三态齐备**（loading 骨架屏 / empty 引导 / error 可重试） | 只做默认态 → 空列表白屏、请求失败无反馈，是上线后最高频的用户投诉 | 在**真实界面**触发三态（清空数据 / 断网 / 慢网），确认有对应渲染；只有 spinner 顶替空态不算 | 无前缀 |
| 适配无溢出/断裂（**按域**） | 撑破视口/被裁切是最直观的交付事故 | web：320/768/1024/1440 四档截图核断点；desktop：窗口缩放/最小尺寸/多显示器/系统字号；game：**宽高比矩阵**下 HUD 不被裁切；mobile：安全区无遮挡 | High |
| a11y 属性落地（图标按钮 `aria-label`、表单错误关联、浮层焦点管理、可见 focus） | 无障碍是法律要求，且直接暴露"设计稿写了、实现没做" | 键盘 Tab 走一遍；查图标按钮 DOM 有无 `aria-label`；弹窗打开看焦点去向 | High |
| 对比度达标（正文 ≥4.5:1，大号 ≥3:1） | 浅灰字看不清 = 真实用户流失 | 取**实际渲染色值**算对比度（非只信令牌表声明） | Medium |
| 文案无占位残留（Lorem ipsum / TODO / 示例文本） | 占位文案上线是"未完成"的明证 | grep 前端文案资源与硬编码文案 | Medium |
| 颜色非状态唯一载体 | 色盲用户无法区分状态 | 错误/成功/选中除颜色外有图标或文本 | Medium |
| **设计稿标注项全部实现**（无"设计写了没做"） | 走查的核心对象就是设计与实现的一致性 | 对照该卡 `UI资源/designs/*.md` 的「走查对照点」逐项核 | 无前缀 |

**忽略决策**：域7 的"裸值"命中若属项目明确允许的例外（如第三方组件库强制的内联样式），走「主动忽略决策闸门」并写明是哪个第三方约束，不得口头放过。**纯审美偏好（圆角再大 2px 更好看）不属于本域检查点**，记建议项、不阻塞。

### 域 8：代码风格与命名一致性（code-style，v3.22.0）

> **依据 `契约/代码风格.md`**：命名风格在 ②a 期**一次性定档**（语言清单 + 每语言命名风格 + DB/接口/JSON 各层风格 + 转换层位置），定档后新增代码一律照此；**改风格属结构变更**（过用户确认 + 变更日志 c-xxx）。
> **为什么有这一域**：域1~域7 全不看"名字起得一致不一致"——多角色并行（前端/后端/集成/测试各写一套）时命名必然漂移：同一项目 `camelCase` 与 `snake_case` 混用、同一字段在 DB/Python/JSON/TS 四层里四个名字、"顺手改个名"与新增互相打架。**风格不统一不阻塞编译，却让每次改动都要先考古一遍，让复查无从判"对错"**——没有定档的风格，任何命名都是对的，于是全都不一致。
> **机器核验**：`python scripts/style_audit.py <项目根>`（**只报告不改动**）——输出按文件分组的 `文件:行 | 规则 | 现状 | 期望 | 建议` + 按规则汇总 + 退出码（0 无命中 / 1 有命中 / 2 用法错）；契约 §4 例外登记项不再报告，**到期已过的例外重新报告为命中**。
> **使用方**：后端/前端置 done 前自验（对照契约 §3.3 提交前清单）· 集成工程师五轴（**「可读性」轴 + 「风格一致」轴**）· 代码解析师（接手旧代码先出风格基线）· 主控批次收口。

| 检查点 | 为什么 | 怎么验证 | 严重度 |
|---|---|---|---|
| **命名风格与定档一致**（变量/函数/类/常量/枚举成员/模块名，逐语言） | 定档的意义在于"新增代码不必再做选择题"；一处通融、处处通融 | 跑 `style_audit.py`：`func-naming` / `class-naming` / `const-naming` / `file-naming` 命中即核契约 §1.1；**同目录同时出现 camel 与 snake 函数 = 风格漂移**（`func-style-mixed`） | 无前缀 |
| **DB 命名符合模板**（表/列/索引/外键/迁移文件） | 表名猜不到内容、索引名对不上表名 → 排障时"看名字找不到东西" | `style_audit.py` 从 `*.sql` / 迁移 / schema 字符串提 `CREATE TABLE` / `ADD COLUMN` / `CREATE INDEX`；`db-index-template` 要求索引名的表名段**能对上真实表名**（允许省略 `_id`/`_at` 后缀），对照 `数据模型.md` | 无前缀 |
| **跨层转换集中在序列化层**（业务代码不得手写字段改名） | 同一字段四层四个名字 + 各处手写转换 = 改一次漏三处（真实案例：`cover_sub` 与 `coverSub` 在同一业务文件里双写） | `style_audit.py` 的 `json-crosslayer-drift`（同文件双写 → Medium；跨文件且无转换设施 → Medium；有转换设施 → Low 待确认）；人工复核后落 `问题/审核记录.md` | Medium |
| **接口路径与 JSON 字段风格统一**（含路径参数写法） | 同一套接口两种拼法 = 前端路由表与接口文档对不上 | `api-path-style`（路径段风格）/ `api-path-mixed`（同仓连字符与下划线并存）/ 对照 `api.yaml` 与 `api设计规范.md` §1；**Express `:id` 与 FastAPI `{id}` 属框架语法强制，不算漂移**（契约 §1.3 反例） | 无前缀 |
| **无未登记例外**（例外表即欠债台账） | "这个文件先这样"没有记录 = 下次没人知道它为什么不合规，也没人回收 | 读契约 §4：命中项是否在表内、是否写明理由/批准人/**到期时间**；`style_audit.py` 的 `exception-expired` 报过期项 = 必须裁决（改代码 / 续期须再报用户 / 升格为正式风格） | 无前缀 |
| **新增文件/目录命名合规 + 禁同义多词** | 同级两种拼法的目录并存、同一实体两套叫法（`user`/`member`/`account`）→ 半年后没人知道该进哪个、该用哪个 | `style_audit.py` 的 `file-naming` / `dir-naming` / `dir-style-mixed`；对照契约 §2「禁同义多词」与 §1.4 跨语言示例表 | Low（风格）/ 无前缀（同义多词） |
| **格式工具已跑**（black/ruff、prettier/eslint） | 格式噪音淹没真实 diff，评审看不清改了什么 | 跑契约 §3.1 命令至无格式 diff；`.editorconfig` 在项目根就位 | Low |

**忽略决策**：域8 命中若属**存量历史代码**（非本卡引入），走「主动忽略决策闸门」时必须回答"登记进契约 §4 例外（写到期的日期）还是立专项重构卡"——**不接受"历史遗留"当理由**；命中若属本卡新增代码，**不允许忽略**（新增即照定档，没有商量的余地）。

### 域 9：Prompt 与对话链契约（prompt-chain，v3.22.0）

> **依据 `契约/Prompt规范.md`**：提示词属 v3.11.0 定义的"配置"范畴——每条提示词 = **一个 id + 一个版本 + 一处正文**（单一事实源），在 `契约/配置中心.md` 的 `prompt.*` 注册表登记，代码只引用符号；输出**结构化优先**，失败有降级；用户输入**绝不直拼系统指令**；改动**必须过评测集**。
> **适用范围**：含大模型交互的卡（`Prompt规范.md` §0 定档 = 是）。无大模型交互的项目本域不适用（在 §0 写明"否"即豁免，豁免须经得起核对）。
> **使用方**：后端开发置 done 前自验、集成工程师（正确性/契约轴）、安全审计（注入面）、测试工程师（评测集与回归留痕）。
> **编号说明**：本域定为 **域 9**（域 8 由并行治理块占用）；即使某个副本里 域 8 尚未并入，**编号也不回退**——域号一旦被卡片、报告、忽略决策记录引用过（"域9"）就不再复用/重排，避免引用漂移。
> **为什么有这一域**：域 1~7 全在看"代码结构对不对"，**没有一条看"发给大模型的那段文本"**——提示词散落硬编码、输出格式靠"求"、解析失败才发现、用户输入直拼系统指令、改一句没人知道影响什么（真实项目实测：同一条图片分类提示词存在**两份正文**（资产侧 `PROMPT` / 业务侧 `SCAN_NAME_PROMPT`）被**两套正则**分别解析，全仓 `评测集/回归` 检索命中 **0**）。

| 检查点 | 为什么 | 怎么验证 | 严重度 |
|---|---|---|---|
| **每条提示词有 id + 版本，且正文单一事实源** | 多副本必然漂移：改一处漏一处，影响面无从查（同一条提示词两份正文 = 定时炸弹） | ① `契约/配置中心.md` 有 `prompt.*` 登记行（id/版本/归属文件/输出契约/降级/评测集）；② 正文首行标 `<!-- id: x.y.vN -->`；③ 全仓 grep 提示词首句，**计数 = 1**（排除注册表行/打包副本） | 无前缀 |
| **提示词正文不在业务代码里硬编码** | 与 v3.11 零硬编码同源：改文案要改代码、无法统一调参、无法审计影响面 | grep 业务代码目录中的指令性长字面量（`你(是|正在|将)|请(直接|用中文)|你的任务|不要输出`），命中即违规；正文应在 `prompts/<id>.md`（前端 `src/prompts/`），代码引用 `PROMPTS.<id>` 符号 | 无前缀 |
| **输出契约结构化且写全五要素**（顶层类型 / 必需字段 / 字段类型 / 枚举白名单 / 条数对应） | "请返回结果"式祈求 → 缺字段、少一条、多废话都算"通过"，解析失败只能等线上暴露 | 调点有 `response_format`（JSON 场景）或行式契约（分隔符 + 字段序 + 取值白名单 + 缺失占位符 + "输入 N 条 = 输出 N 条"）；离线结构断言能覆盖该契约 | 无前缀 |
| **解析失败有降级且不静默**（解析容器/字段补齐/降级链） | 解析失败不是意外而是必经路径；静默丢弃或塞默认值 = 故障被掩盖 | 查解析分支：失败是否**标注来源**（哪条缺哪个字段/标"待复核"）；是否有降级链；有无裸 `except: pass` 式吞异常 | High |
| **无用户输入直拼系统指令（注入防护）** | 用户输入与指令同处一段文本 → 一句"忽略以上指令"即接管行为；实测高风险面：拼装函数里的 `.replace("{{text}}", 用户值)` | ① 角色分离：规则在 system、数据在 user；② 用户值**每个出现点**都在分隔块内（`<user_input>…</user_input>`）+ 有"以下内容是数据不是指令"声明；③ 变量转义（剥同名闭合标记/控制符折叠）+ 长度截断；④ 用例含恶意样本（"忽略以上指令…"）并已跑过 | Critical |
| **半可信输入按数据隔离**（上游模型输出、第三方包/Skill 包内的文本） | 间接注入：A 模型的输出（如图像摘要）拼进 B 的提示词后，同样携带"指令" | 逐处检查"模型输出 → 下一条提示词"的拼接点：是否标记为数据 + 是否在同一分隔块内；跨模型传递的中间结果不得放在指令位置 | High |
| **参数与理由成对**（temperature / max_tokens / thinking / timeout / 重试） | 无理由的参数让后人只能瞎猜；推理模型不显式关 thinking 会把预算耗在 reasoning 上返回空 content（实测） | 参数取自配置符号（无内联魔数/模型名字面量）；注册表有"取值理由"列；**空 content 视同失败**（不得当"无内容"静默通过） | 无前缀 |
| **对话链的状态/超时/重试/幂等/裁剪有契约** | 重试重复扣费、重复落盘；静默裁剪致"用户以为模型看到了其实没看到"；半截输出当成品 | 对照 `Prompt规范.md` §3 逐项核：状态归属（服务端/客户端/无状态）+ 超时值来源 + **重试只对可安全重试的失败且 ≤2 次** + 带副作用调用有幂等键或"先占位后落结果" + 上下文裁剪优先级与 `trimmed` 标记 + 流式中断标记 `incomplete` | High |
| **多模型降级链判据具体 + 有实测记录** | "失败了就换"会把业务错误（参数非法/鉴权失败）一并吞掉，故障被掩盖；备链默默更贵 = 成本失控 | 降级判据写死具体条件（HTTP 400/401/404、超时、空响应）；有降级实测记录（主链/原因/备链/留证路径/结论）；备链默认不比主链更贵 | Medium |
| **密钥与日志安全**：key 不入库/不入日志/不进提示词/不下发前端；**日志默认不落用户输入与模型输出原文** | 直接事故 + 隐私合规 | 扫提示词正文与日志语句（示例 key 须为占位 `sk-xxx`）；key 只走环境变量；日志落的是 id/版本/模型/耗时/token/长度等元数据，落原文需开关 + 掩码 + 保留期（供应商错误体同样脱敏） | Critical |
| **改动有评测集回归记录（前后对比）** | 改一句可能让另一类输入全崩——没有回归就没有证据 | 抽查卡卷宗 `证据/`：评测集运行输出（`python scripts/prompt_regression.py --cases … --adapter offline`）+ **前后对比**（用例数/通过/失败/跳过、结构断言、语义抽样、新增入集样例）；评测集覆盖五类（正常/边界/恶意/多语言/超长）且达条数下限；**只有 diff、没有评测记录 = 未完成**（视同 S4 不落盘） | 无前缀 |
| **跳过 ≠ 通过** | 无 key/无网络就标"通过"= 假装验证；语义断言被当成结构断言过关 | 评测记录里 SKIP 项必须有补跑计划或书面豁免依据；语义断言（准确度/语气）由抽样人评或模型评给出结论，不用离线脚本冒充 | Medium |

**忽略决策**：域9 的命中若确属不适用（如项目在 `Prompt规范.md` §0 定档"不含大模型交互"、或某条提示词被判定为"仅此一处、永不改"的临时探针），走「主动忽略决策闸门」并写明依据与重新触发条件。**"提示词太短不值当建契约""评测集以后补"不属于可忽略情形**——它们是未完成，不是豁免。

### 域 10：异步与消息（async & messaging，v4.0.0）

> **依据 `契约/技术栈.md` 与 `数据模型.md`**：项目一旦引入消息队列/异步任务/定时调度/事件总线，**投递语义、幂等、重试与死信就是需要设计的架构件**，不是"发出去就完了"。规则详见 `契约/安全与数据.md`（安全面）与后端 skill「异步基础设施」。
> **为什么有这一域**：域2/域3 看的是**同步路径**的并发与事务；**异步路径**的五类事故（重复消费、重试风暴、消息丢失、乱序、积压雪崩）此前无判据——真实事故高发于非幂等的消费者 + 无上限重试 + 静默丢弃。
> **使用方**：后端开发置 done 前自验 · 集成工程师（正确性/契约轴）· 安全审计（消息体敏感数据）· 数据工程师（对账类定时任务）。

| 检查点 | 为什么 | 怎么验证 | 严重度 |
|---|---|---|---|
| **消费者幂等**（同一消息重复投递不产生重复副作用） | at-least-once 是常态，重复消费必然发生；扣费/发券/落单重复即事故 | 找消费入口：有幂等键 / 去重表 / 唯一约束 / 状态前置条件？**重放同一消息，结果不变即通过**（写测试证明） | Critical |
| **重试策略明确且有上限**（退避 + 上限；不可重试错误不重试） | 无上限重试 → 重试风暴、重复扣费；对 400/参数错重试毫无意义 | 读重试配置与代码：次数上限、退避与抖动、**可重试 vs 不可重试分类**（超时/5xx/429 可重试；400/401/404 不重试）；上限落配置而非写死 | High |
| **失败有归属，不静默丢弃**（死信队列或失败落盘 + 可重放） | 消费失败直接 `except: pass` 或只打日志 = 消息永久丢失且无人知 | 消费失败路径：进 DLQ / 落失败表 / 告警？有重放手段？**无 → 打回** | High |
| **幂等的边界写清**（幂等键来源、有效期、冲突时行为） | "有幂等"但键是随机 UUID 每次不同 = 假幂等 | 幂等键是否来自业务唯一标识（订单号/消息 ID）；重复时返回原结果还是报错（须一致） | High |
| **顺序性按需处理**（分区键 / 可容忍乱序 / 显式拒绝乱序） | 同一实体的事件乱序 → 状态机穿越、余额错乱 | 需要顺序的流是否同分区键路由？乱序时消费端是否有版本/时间戳保护？ | High |
| **定时任务不重复执行**（多实例并发、重入、漏跑补偿） | 多副本部署下定时任务并发跑 N 次（对账/结算重灾） | 分布式锁 / 单飞（single-flight）/ 幂等执行；错过的调度有无补偿策略；**任务执行记录可查** | High |
| **事务与消息一致性**（禁"先发消息再落库"无补偿） | 消息发出但事务回滚 → 下游消费到不存在的业务 | 用本地消息表 / 发件箱（outbox）/ 事务后发；确需先发必须有补偿与对账 | Critical |
| **背压与资源上限**（队列/线程/批量无界） | 无界积压 → 内存/连接耗尽、级联雪崩 | 队列长度上限、批量上限、并发消费者上限、超限策略（拒绝/降级而非 OOM） | Medium |
| **可观测**（关联 ID / 积压 / 失败率 / 重试次数） | 出问题看不出是哪条消息卡住 | 消息带关联 ID 并能串起日志；有积压与失败率指标（对齐完成定义 §6 可观测性与 `运维` 告警） | Medium |
| **消息体契约版本化 + 向后兼容** | 生产者升级字段、老消费者崩溃 | 消息 schema 变更只增不改；有版本字段与消费端兼容策略（对齐 `api设计规范.md` §版本化） | Medium |
| **敏感数据不得明文入消息/日志** | 队列与消费日志常被忽视，成为 PII/密钥泄漏面 | 消息体含 PII/密钥？是否加密/脱敏/只传 ID 由消费者回查；队列日志同样脱敏（对照 `安全与数据.md` §3） | Critical |

**忽略决策**：域10 命中若项目**确实无异步路径**（无队列/无定时任务/无事件），在 `技术栈.md` 注明即豁免；**"以后可能要加"不构成需要**，反之**已引入异步却无幂等/无死信 = 未完成，不属于可忽略情形**。

## 三、踩坑即加规则（持续增长协议）

> 借鉴 `code-review-gate` 的"踩一个坑，加一条规则"。本库不是写一次就完的静态文档，而是**随真实事故持续迭代的项目故障知识库**。

- **触发**：任何角色（开发/测试/集成/安全/运维）在**本项目的真实环境**（尤其 prod / test 验收）遇到一次**线上问题或隐性 bug**（重复事故、生产翻车、验收才发现的偏差），事件闭环后必须沉淀一条新规则：
  - 新增到本库**对应的域**下（没有合适域 → 新增一个域）；
  - 修复代码 + 加规则**约定同一张卡/同一次提交**，不允许"只修代码不留规则"（否则下个代理重踩）。
- **规则条目元数据（每条必填，装进规则表扩展列或条目旁）**：
  | 字段 | 含义 |
  |---|---|
  | `来源/踩坑人` | 哪次事故/哪个角色踩的（可追溯） |
  | `添加时间` | 入库日期 |
  | `坑背景` | 一句话：当时发生了什么（为什么值得记） |
  | `关联` | 关联 需求卡 card-xxx / 记忆 k-xxx（闭环到知识沉淀） |
- **防重复**：加规则前先在本库搜索是否已有同类；已有时只补坑背景/来源，不重复建条目。
- **升格路径**：本库重复命中的高价值规则 → 升格到 `记忆/知识沉淀.md`（k-xxx，项目级复用）；跨项目通用的规则 → 反哺框架层模板（本文件），让框架本身越用越强。

## 四、主动忽略决策闸门（ignore-decision）

> 借鉴 `code-review-gate` 的 `ignore-decision`：规则命中但决定**忽略**时，不能无声跳过——忽略必须是**有记录、可追溯、经拍板的主动决策**，否则等于没检查。

- **何时用**：复查发现一条规则命中，但你判断 **不适用**（误报 / 超出本卡范围 / 当前不构成风险）时。
- **必须写《忽略决策记录》**，至少回答以下问题，落盘到 `project-state/问题/审核记录.md`（追加一条「忽略决策」记录），并同步 `记忆/决策日志.md`（d-xxx）：

  ```markdown
  ## 忽略决策记录（<规则/检查点> 命中，决定忽略）
  - 规则/检查点：<本库哪一条>
  - 关联：需求卡 card-xxx / 位置 file:line
  - 误报？还是真命中但主动忽略？（真命中写"主动忽略"）
  - 忽略理由：为什么现在不适合处理（一句话）
  - 是否会/将影响用户？  （是 → 不允许忽略，必须修复或降级）
  - 是否列入 Backlog / 待办？  （否 → 这个忽略是永久的还是暂时的？）
  - 重新触发的条件？  （什么情况会回来）
  - 谁拍板：<角色/用户>
  ```

- **门槛**：若答案是「**会影响用户**」或「**不列入任何后续**」，则该忽略**不成立**，必须修复或提交 CR，不得忽略。允许忽略的典型场景：纯内部低风险、当前无此用户路径、被更高优先级阻塞、误报。
- **无记录 = 未处理**：rule 命中但既无修复、也无忽略决策记录 → 视同 S4 不落盘，打回。忽略决策与修复同等重要，是"复查过"的证据。
